# 智能体记忆的技术全景：从统一架构、端侧多模态到可审计自演化

本文按主题梳理智能体记忆的技术主线：先定位无状态模型到可管理、可演化经验层的问题，再展开统一架构、多模态与端侧实现、认知与自演化、可信治理与评估，以及成本感知调度、技能沉淀和记忆原生模型等路线。各报告的技术路线分别展开，主持串场只保留与主题相关的问题衔接。

## 智能体记忆的总体定位与统一架构演进

报告以“全景记忆”为题，把记忆放在智能体能否真正“把事做成”的核心位置。大模型本身是无状态的：一次推理结束，模型不会自动保留刚才发生过什么。因此在聊天阶段，核心问题是“能不能记得住”；进入 Agent 阶段后，记忆不再是可有可无的附加功能，而是完成多步任务、维持长期行为的必需能力，问题也随之变成“记忆该怎么管”。

这也是报告判断记忆正在发生形态变化的原因。2024—2026 年间，记忆正从中间件式的存储，转向对“经验”的承载。这里的“经验”不是简单堆积日志，而是能被后续任务调用、修正和沉淀的内容。报告引用 Gartner 的判断：到 2028 年，基本上一半以上的 Agent 会给记忆上图谱；并将其与 Anthropic 的 context graph、context scaling，以及 Agent 长期运行后带来的安全暴露联系起来。换句话说，记忆既要支撑更长上下文和更复杂的关联推理，也会因为长期积累而放大隐私、注入和污染等风险。

### 记忆层的位置与三项核心问题

在整体架构中，报告给出的分层是：下面是模型，上面是上下文，再上面是应用；记忆层跨在应用与上下文之间，属于模型之外的记忆层。这样的位置意味着，记忆既服务于应用层的任务编排，又通过上下文进入模型推理过程。报告也提示，后续还会讨论模型内化的记忆内容，而当前这条线索主要聚焦模型之外的记忆系统。

报告把记忆的核心事项概括为三件：

- **写入与更新，即可塑性。** 记忆要能被写入、修正和自演化，同时避免无节制膨胀。可塑性越强，系统越能适应新任务，但管理难度也越高。
- **跨会话、跨任务的一致性。** 记忆要在不同会话、不同系统迁移中保持连续，遇到冲突时能够消解，并持续更新，而不是形成互相矛盾的多个版本。
- **隐私与安全的可信性。** 记忆面临注入、污染、隐私窃取等风险，长期运行后安全暴露更明显，因此需要做到较好的可信。

与之对应，报告列出的评价指标包括检索准确性、记忆容量、召回、关系保真以及记忆质量等，这些指标都希望越高越好。但报告明确判断：现阶段在理论和评测方面还有很多可做的工作，记忆系统远未到指标体系统一的阶段。

### 从产品功能到独立基础设施

报告用几类产品形态说明记忆位置的变化。GPT 的 memory 主要解决“记住你是谁”，即 who you are；Claude 侧重记住“聊过什么”；Cloudflare 则把记忆做成通用的、独立的基础设施，即 memory 的 AI infrastructure。由此，记忆从单一产品功能逐步变成可共享的底层能力。

形态上还包括消费级云端助手、常驻智能体，以及本地优先也可上云的 Open Core、Hermes Agent、Meta Q 等。专用记忆层则有 Mem0、Zep、MemOS、insight 等；其中 insight 被描述为对世界经验、观察和观点的刻画，通过保留回忆和反思形成独特的记忆中间件。应用案例覆盖通用场景、个人场景和记忆中间件，这也进一步加固了“记忆层”作为独立架构层的地位。

### 统一架构的四级演进

报告把全局架构的演进概括为“从局部的记忆模块到统一的记忆空间”，大致可分为四级：

| 阶段 | 主要形态 | 关键特征 | 代表方向 |
|---|---|---|---|
| 即插即用模块 | 可插入 Agent 的记忆组件 | 作为外部模块随 Agent 迁移，解决记忆有无问题 | MemGPT、Mem0、MemoryOS |
| 结构化记忆图 | memory graph | 把扁平记忆转为实体、关系、事件等带时序的图谱，支持复用和复杂推理 | Zep 及 graph-based agent memory |
| 统一调度 | 借鉴操作系统抽象 | 对写入、检索、遗忘进行统一管理，使记忆操作具有一致性 | 部分 agent native memory |
| 统一记忆空间 | “记忆场”（memory field） | 以统一方式寻找数据碎片，追求统一表示与统一寻址 | 报告提出的演进方向 |

第一类即插即用模块解决的是“先有记忆”。它作为可插入组件，可以随 Agent 迁移，但记忆与具体系统之间仍偏局部。第二类结构化记忆图则不再把记忆当成扁平文本块，而是组织成实体、关系和事件，并保留时序信息，从而提升复用能力，支撑更复杂的推理。第三类统一调度借鉴操作系统的抽象方式，把写入、检索和遗忘纳入统一管理；从通用原理看，这类似于把记忆当作一种需要分配、回收和调度的资源，而不是散落各处的功能点。第四类“记忆场”进一步追求统一表示和统一寻址：不同来源、不同形态的记忆碎片要能被统一表示，并在需要时被统一找到。

整体趋势是从底部的记忆模块走向顶部的统一记忆空间，越来越统一化。但统一架构仍需要评价指标约束，检索准确性、记忆容量、召回、关系保真等维度都需要越高越好；应用也从通用、个人延伸到记忆中间件。报告同时强调，理论和评测仍有大量空白，这说明统一架构目前更像收敛方向，而不是已经完成的标准答案。

### 挑战框架与路线判断

报告用“十个趋势和挑战”组织后续内容，并将其分为三层：基础设施层决定记忆能长多高、放多大，包括记忆场、多模态统一和端侧演化；认知层包括驱动推理、生物认知机理、主动记忆，以及记忆的新陈代谢和演化；支撑层类似 Harness，目标是让记忆可以被协作和信任，包括可解释、跨 Agent 共享、质量评估和安全对抗。

在当前报告中，基础设施层被重点展开，认知层只给出方向，尚未进入细节。这个安排本身也反映了路线判断：智能体记忆首先要在表示、寻址、调度和评价上形成可管理的底座，才谈得上更复杂的认知机制与跨 Agent 治理。记忆正从“聊天时能不能记住”的附属能力，演变为 Agent 长期运行所依赖的基础设施；而统一架构的竞争，也将集中在能否把写入、检索、遗忘、评价和安全放进同一套可扩展的框架之中。

## 多模态记忆：从表征割裂走向跨模态统一

多模态记忆要解决的问题，可以先用一句话概括：把图像、文本、音频、视频对齐到统一表征，让智能体在长时间跨度上“记得住、找得到、用得上”。但跨模态数据高度异构，直接对齐并不容易。报告给出的工程思路是引入**记忆锚点**——关键词、关键句、关键事件——再把这些锚点统一到索引体系中，从“表征割裂”走向“跨模态统一”。围绕这条主线，相关工作报告了统一编码、隐空间记忆、长视频事件记忆、跨模态检索等路线，也明确了语义鸿沟、长程漂移、端侧轻量化等尚未解决的问题。

### 为什么需要多模态记忆

报告从两个视角解释动因。

从学术与机器学习视角看，人类生物体和真实世界的数据本身就是多模态的，模型可以从多模态数据中学到大量信息；多个模态合起来，往往能提供比单一模态更关键的信息。无论是模型预训练，还是智能体在实际使用过程中接触到的数据，很多都是多模态的。更进一步，模态之间的跨模态认知有利于 AI 系统未来进行持续学习。

从应用视角看，多模态记忆面向联想的多类产品，也面向智能座舱、汽车、智能眼镜等场景。这些产品的核心技术点包括多模态数据理解、模态之间的感知，以及形成多模态记忆来支撑后续 AI 应用。报告给出一个总体流程：智能体、人和环境交互，产生原始多模态信息；这些信息通过智能体的记忆系统写入多模态记忆；记忆再用于增强智能体的实际应用。

这里的关键问题是：多模态输入包含文本、大量视频帧、音频（例如人类交互中的语言、文字）等，如何把这些信息构建成一个个记忆单元，更好地支撑智能体应用。视频尤其突出——时间长、信息量大，不可能把所有帧都原样沉淀为记忆，必须决定抽取哪些关键信息。

### 统一表征的几条技术路线

报告把相关工作归纳为几类。它们的共同目标都是让不同模态进入一个可检索、可复用的记忆空间，但切入方式不同。

| 路线 | 主要做法 | 关注点 |
|---|---|---|
| 视觉语言模型中的记忆机制 | 在 VLM 中引入 memory 机制，做统一编码与对齐 | 跨模态表征如何对齐 |
| Memverse 一类工作 | 快速参数召回与分层检索，把不同模态写入统一、可检索、可复用的记忆嵌入空间，并在隐空间中进行 | 记忆的快速召回与分层组织 |
| 面向视频的记忆 | 处理视频记忆中的长程时序一致性 | 长视频中的时序一致与漂移 |
| 跨模态检索 | 以统一索引支持以文搜图、以图检索、以声换景等跨模态召回 | 统一索引如何支撑多模态召回 |

报告还提到字节的多模态 memory agent、M3 agent，以及 context/memory 类多模态 Agent；并指出 memories.ai 在端侧做得很多，而端侧本身有大量多模态场景。应用侧则包括 AI 眼镜、创作视频的 Agent、电商搜索和端侧手机。报告特别强调，在长程持续一致性等要求下，还希望检索能够减少资源消耗。

作为背景，这里的“隐空间”可以理解为模型内部的高维向量空间：不同模态的输入被编码成向量后，在这个空间里做检索和复用，而不是停留在原始像素、音频波形或文字表面上。这样做的价值是便于统一索引，难点则在于不同模态的语义是否真的能在同一空间中细粒度对齐。

### 以事件为锚点构建长视频记忆

在长视频场景中，报告选择“事件”作为核心锚点。原因很直接：从应用导向看，大多数应用关心的是视频里发生了什么事件、出现了什么人、这个人在做什么、遇到了什么事、现场是什么情景。智能眼镜、智能穿戴设备等场景，也常关心当前时刻或过往时刻发生了哪些事情。因此，事件可以成为关联不同模态信息的抓手。

一个事件可以对应视频信息，也可以对应文本、音频信息，还可以对应当时智能体与人的交互轨迹。以事件为抓手，可以把碎片化的多模态信息结构化规整，并在不同模态之间建立对齐，便于后续推理、问答和检索。

具体处理流程大致是：

1. 视频由一帧帧图像组成，系统每隔几分钟甚至几小时切分出若干上下文块；
2. 在每个块内提取关键语义信息，例如 caption、文本转录等，并抽取其中的事件；
3. 这些事件再经过分钟级、小时级以及更长时间级的摘要，形成以事件为中心的记忆单元；
4. 此时记忆单元仍然比较孤立，属于一条条多模态事件记录，除时间维度外没有完整的前后关联；
5. 系统再利用事件背后关联的人物、事件类型以及其他元素，形成 **event link 记忆图**。

event link 的动机来自一个很实际的问题：如果昨天遇到一件事、今天遇到类似的事，智能体若没有把相似事件关联起来，召回时可能不会主动意识到两件事相关。在构建记忆时以事件为抓手，让相关记录互相建立关联后，查询时就可以在图上进行关联检索和重排序，用于缓解多模态记忆内容稀疏、部分缺失的问题。

报告展示了 Benchmark 结果，与常规 RAG、长视频理解专有模型以及一些基于 memory 的基线进行比较，但现场没有展开表格细节。报告更强调实际视频处理中的高延迟问题：处理极长视频时，大模型可能需要非常久的时间才能真正处理完并构建记忆。该工作专门针对这一点做了优化，因此在效率、并发等方面有一定提升。报告还给出对比图：其工作 EM2 相比左侧基线，能更好地以事件为核心，把不同人物、背后的目标和相关地点等进行关联，结构化程度更好；结构化强的信息可以起到扩大召回的作用，最终提升效果。

### 异步分层架构与系统落地

真实场景中，只靠一个简单的记忆模块并不够。报告指出，记忆模块在实际使用中存在大量延时和时效性问题。因此团队设计了一整套异步分工架构：视频流进入后，按流式写入逻辑进行处理并送到后端，后端再用多个线程异步写入记忆，避免实时写入让用户等待过久。

背后是分层记忆系统，同时存储当前记忆上下文、短期记忆和长期记忆，目标是让不同时间尺度的问题在不同记忆单元中构建。报告称这是一个完整的端到端构成。

在上述工作基础上，团队开源了一个多模态记忆系统 **Light Memory ego**，包含短程记忆和背后的长期记忆功能。该系统被集成到智能眼镜上：眼镜从第一人称视角提供辅助视觉输入，帮助观察周围发生的事情，用户可以通过对智能眼镜提问来获得回答。系统也可以部署到手机上，并有简单的开源应用。目前系统可支撑大约长达一周的视频信息。报告补充了一个现实条件：通常不是 24 小时一直开启设备，而是从一天开始并持续一周，把一周内的视频和音频信息记录下来。

系统还支持可视化查询。用户如果发现记忆存在问题或不满意，可以查看当前记忆到底存了哪些内容，甚至可以增加、删除、修改或擦除部分记忆。这一点对记忆系统的可用性和可控性很重要。

### 应用示例

报告用几个场景说明多模态记忆如何工作。

- **智能眼镜短程记忆**：实验室同学戴上智能眼镜，背后运行记忆系统并持续记录信息。同学把水杯放到窗台上，这是一个典型事件；过了一段时间他想喝水，便询问杯子放在哪里。系统很快捕捉到短程记忆信息，通过语音播报和文本方式告诉他杯子的位置。
- **长程记忆**：某人在前一天接了一通电话，电话中提到第二天要开会；第二天他向智能体询问昨天提到的会议在什么时候，系统给出回答。交互可以使用自然语言、文本和音频等多种方式。
- **车载场景**：用户坐在车上，系统与车载设备结合，实时观测前方路况，记录去过哪些地方，背后是多模态时空记忆；还能记录前方情况、目的地，并总结整个路程中发生了什么事。报告提到这是当时在海宁一带的真实例子。
- **科学实验场景**：多模态记忆可以记住实验过程中的步骤。如果某个同学做了一次成功实验，可以把这段记忆存下来；下一个同学想复现实验或做新实验时，这段记忆可以提供参考。

这些例子共同说明，事件锚点不只是抽象的表征方法，它直接对应“找杯子”“回忆会议”“总结路程”“复现实验”这类具体查询。

### 局限与开放问题

报告对局限的说明比较明确：

- 跨模态对齐存在**语义鸿沟**，细粒度对齐精度仍然不足；
- 长视频存在**长程一致性**和**长程漂移**问题；
- 端侧面临**轻量化编码**的挑战；
- 在长程持续一致性要求下，检索还需要进一步减少资源消耗。

更前瞻的讨论集中在两点。其一，目前绝大多数多模态记忆仍属于**被动存储**机制。视频持续输入智能体时，并非每时每刻都有人在提问；智能体有时看到视频中的内容后，应主动向人类提供反馈，或主动探索环境并形成记忆。从未来视角看，主动认知或 proactive 记忆还有很多可以挖掘的点。其二，记忆系统无论参数化还是非参数化，变化都很快，技术演化也很快；记忆系统可以随环境自主演化，也就是记忆系统本身也可能存在类似 RSI 的机制。

这两点把问题从“如何存得统一、找得准确”推进到“记忆如何主动形成、如何随环境演化”，也是多模态记忆从工程模块走向长期智能体能力的关键方向。

## 端侧记忆的隐私约束与端云协同

端侧记忆的演化首先不是模型能力问题，而是隐私边界问题。报告给出的核心判断是：端侧记忆涉及大量个人化信息，原始数据不能出端，因此不能照搬“把记忆集中到云端”的做法，而必须重新设计端云拆分。换言之，隐私约束不是记忆系统建成后再附加的安全模块，而是决定端侧记忆能否演化、以什么方式演化的架构前提。

### 为什么端侧记忆必须先谈隐私

端侧设备——手机、PC、车机以及新型 personal agent——长期接触用户的个人上下文、偏好和历史交互。记忆的价值恰恰来自这种细粒度、连续性的个人化信息；但越细粒度，原始记忆出端的风险越高。报告把隐私称为“双刃剑”：保护不足不可接受，保护过度又会损害记忆的可用性，并带来额外开销。因此，端侧记忆面临的不只是“能不能记住”，而是“在数据不出端的条件下，记忆还能不能持续更新、跨设备演化并支撑推理”。

这也是端云协同被提出的原因。端侧不能简单地把原始记忆上传给云端，但端侧算力、存储和模型能力又有限；云端不接触原始记忆，却仍可承担一部分推理。端云之间需要一种受约束的分工和同步机制。

### 端云分工：端侧驻留敏感记忆，云侧做有限推理

报告描述的端云分工可以概括为：

- **端侧保留敏感记忆**，并承担本地训练、脱敏和隐私处理；
- **云侧不碰原始记忆**，但承担部分推理；
- 两端通过**同步回合**推进记忆演化，使系统从“满足隐私约束”逐步走向“可用演化”。

这里的“云侧不碰原始记忆”并不意味着云端不参与，而是参与方式受到限制：云端更多使用更新、脱敏后的表示或模型侧结果进行推理，而不是直接读取端侧原始记忆。端侧则保留敏感记忆的驻留权。同步回合的意义在于，它不是一次性上传或一次性下发，而是在多轮同步中逐步完成记忆的更新与可用化。每轮同步都同时受到隐私约束和可用性目标的牵制，因而端云协同本身就是一个持续权衡的过程。

从通用原理看，这种结构与联邦学习的基本动机相近：不移动原始数据，而移动模型更新或中间结果。但报告强调的不是一般联邦学习，而是面向记忆跨设备演化的“新型联邦学习”，其难点在于记忆更新如何在不同设备之间保持一致和可收敛。

### 四个技术方向

报告将端侧记忆的隐私约束拆成四个方向。它们不是彼此孤立的模块，而是共同组成一条从“数据不出端”到“记忆可用演化”的约束链。

| 方向 | 主要做法 | 要解决的问题 |
|---|---|---|
| 多设备本地训练、只传更新 | 设备本地训练，设备间只交换更新，实现记忆跨设备演化 | 在不集中原始记忆的前提下完成记忆演化，报告称之为新型联邦学习 |
| 可逆脱敏 | 通过替换、拦截等方式，使 personal identifier information（PII）不出端，并做到可逆、可还原 | 既隐藏个人身份标识，又保留必要时的还原能力 |
| 可验证隐私 | 通过差分隐私、加密等方式实现可验证的隐私保护 | 让隐私保护不只是口头声明，而能被验证 |
| 端云协同 | 在上述约束下组织端侧与云侧的推理和同步 | 从隐私约束走向可用演化 |

**第一，多设备本地训练、只传更新。** 记忆的跨设备演化不通过上传原始记忆完成，而是在各设备本地训练，只传输更新。这样既能利用多设备数据，又减少原始数据暴露。报告把这种方式称为新型联邦学习。它的直接好处是把“数据出端”转化为“更新出端”，但更新本身仍可能携带信息，因此还需要后面的脱敏、差分隐私和加密手段配合。

**第二，可逆脱敏。** 报告强调通过替换、拦截等方式，使 PII 不出端，并且做到可逆、可还原。这里的“可逆”不是让云端随意还原，而是指脱敏后的表示在受控条件下仍能恢复语义或对应关系。替换和拦截解决的是“敏感标识不随原始记忆出端”；可逆性解决的则是“脱敏后仍要支撑记忆和推理，不能把信息彻底破坏”。这两者需要平衡：还原能力越强，保护边界越需要严格控制。报告将其概括为“可逆脱敏”，核心是让 PII 不出端，同时避免脱敏后记忆不可用。

**第三，可验证隐私。** 报告提到用差分隐私和加密等方式实现可验证的隐私。从通用原理看，差分隐私通过噪声和隐私预算约束个体信息泄露，加密类手段则减少数据在传输或计算过程中的暴露；可验证性强调的是保护措施能够被检查，而不是仅靠信任。报告同时指出，这条路径仍有明显的开放问题：证明开销和通用性都还有很多工作要做。

**第四，在上述约束下完成端云协同。** 前三个方向分别处理更新传输、身份标识和隐私证明，但最终要落到端云系统上：端侧保留敏感记忆并做本地处理，云侧在不碰原始记忆的前提下承担部分推理，双方通过同步回合完成记忆的可用演化。端云协同不是第四个孤立技术，而是把前三个方向组织起来的系统层方案。

### 设备场景与仍未解决的问题

报告列举的设备场景包括 AI 手机、AI PC（如联想 AI PC）、车机以及新型 personal agent。这些场景的共同点是端侧持续产生个人化记忆，同时又存在云端推理需求，因此都需要端云拆分。不同设备的算力、存储、网络条件和数据分布差异很大，这也直接引出异构设备问题。

报告明确指出三个开放问题：

1. **隐私、效用和开销存在三角不平衡。** 增强隐私可能降低记忆效用，或增加计算、通信和证明开销；追求高效用可能触碰隐私边界；压缩开销又可能削弱保护强度。三者需要 trade-off，而不是单点最优。
2. **异构设备之间的记忆联邦如何收敛仍未解决。** 手机、PC、车机等设备在数据分布、算力和可用性上不同，只传更新的记忆联邦能否稳定收敛，仍是一个开放问题。
3. **可验证隐私的证明开销和通用性仍有很多工作可做。** 隐私保护要可验证，就会带来证明生成、验证和跨场景通用性的成本；这些成本能否被端侧系统接受，尚未解决。

总体来看，报告把端侧记忆的演化描述为一条受隐私约束的协同路径：原始记忆留在端侧，云侧以有限方式参与推理，设备之间只传更新，敏感标识经过可逆脱敏，隐私保护尽量可验证，最终通过同步回合把“不能出端”的约束转化为“可以逐步演化”的系统能力。其难点不在于某一个单点技术，而在于隐私、效用和开销之间的持续权衡，以及异构设备上的联邦收敛和可验证隐私的工程可行性。

## 认知层：检索—推理—更新—再检索闭环与脑启发机制

报告把智能体记忆的“认知层”放在 memory 与 RAG 密切相关的背景中讨论。这里的重点不是把记忆做成一个静态仓库，也不是只优化一次检索的召回率，而是把记忆放进智能体完成任务的过程：先检索，检索结果进入推理，推理产生新的判断与经验，这些内容再写回、修正或淘汰记忆，并影响下一轮检索。报告用“从检索到推理、再到更新、再回到检索”的认知闭环来概括这一过程。

这一闭环之所以必要，是因为在长程任务中，记忆与 RAG 并不是两个孤立模块。检索到的信息会影响推理，推理结果又会改变记忆状态；如果缺少更新和治理，记忆会积累噪声、出现前后不一致，长程成本也会上升。报告判断，这个闭环仍有大量可做的工作，当前进展呈现“部分解决”与“开放探索”并存的状态。

### 闭环中的几个关键动作

报告提到的闭环包含几类具体机制：

- **记忆图检索**：不是只做简单的文本片段匹配，而是以图结构组织记忆，支持关系化、多跳式的检索。从通用原理看，图结构适合表达实体、事件与关系之间的连接，使检索不只返回“相似内容”，还能沿着关系路径找到与当前推理相关的记忆。
- **用强化学习和反思驱动策略化读写与治理**：记忆的读、写、修改和治理不应完全被动发生，而可以由策略决定。强化学习适合优化多步操作中的读写策略，反思则可以把成功或失败的经验转化为下一轮记忆操作的信号。报告强调“策略化”的读写与治理，意味着系统需要判断何时检索、写入什么、如何修正，而不是把所有上下文无差别地存下来。
- **把上下文映射为可演化记忆**：对话或任务上下文需要被转化为可更新的记忆，而不是一次性拼接进提示后消失。这样，记忆才能随着任务推进而演化，并在后续检索中继续发挥作用。
- **通过逐轮精炼和压缩降低长程成本、增强上下文**：长程任务中，上下文会不断膨胀。报告提到逐轮精炼和压缩，目标是在多轮过程中保留关键信息、控制成本，并让增强后的上下文更有效。这里的压缩不是简单截断，而是与记忆更新、精炼结合的过程。

可以把这些动作理解为一条连续的认知链：检索为推理提供材料，推理产生新信息，更新机制决定哪些信息进入记忆、哪些需要修正，下一轮检索再基于更新后的记忆展开。闭环的难点不只在单点检索，更在多轮之间的一致性、成本和可治理性。

### 哪些环节已经推进，哪些仍然开放

报告对闭环中的若干问题给出了明确判断：

| 环节 | 报告中的判断 |
|---|---|
| 长程推理中的记忆噪声积累 | 已经有人处理，但没有完全解决 |
| 记忆更新中的因果一致性 | 已有探索，仍处于开放探索阶段 |
| 分层记忆结构与脑启发架构 | 生物学和脑启发研究为分层记忆结构提供基础 |
| 记忆巩固 | 把短期重要记忆固化，避免灾难性遗忘；早期 HippoRAG 等工作已在做类似事情 |
| 回忆与回放 | 通过回忆/回放激活相应记忆，在学新东西和“温故而知新”之间做平衡 |
| 遗忘与反学习 | 遗忘本身也是一种智能，forget 与 unlearn 是需要考虑的重要内容 |

其中，“记忆噪声积累”说明长程推理不是简单地把更多历史拼进上下文。多轮之后，错误、过时或无关信息可能被反复带入，影响后续判断。报告认为这个问题已被关注，但尚未完全解决。

“因果一致性”则指向记忆更新的更深层难点：更新一条记忆时，不能只看新信息本身，还要考虑它是否破坏已有记忆之间的因果关系。已有探索，但报告将其视为开放问题。从通用原理看，记忆更新若只是覆盖旧条目，容易造成前后矛盾；若要求因果一致，就需要判断更新影响范围，并可能触发连锁修正。

### 脑启发机制：分层、巩固、回放与遗忘

报告进一步把研究视角转向更底层的记忆生物学和脑启发架构。这类研究为分层记忆结构提供基础：不同时间尺度、不同重要性的记忆不必放在同一层，也不需要以同样方式读写。分层之后，系统可以区分短期工作记忆、长期稳定记忆和可被重新激活的经验。

记忆巩固是其中一个核心机制。报告提到，把很多短期重要的记忆固化下来，避免灾难性遗忘；早期 HippoRAG 等工作已在做类似事情。这里的“巩固”不是把所有短期信息都永久保存，而是选择重要内容进入更稳定的记忆层。它与灾难性遗忘相对：当模型或智能体学习新内容时，如果不加控制，旧能力或旧经验可能被覆盖；巩固机制则试图在学新东西和保留旧知识之间建立平衡。

回忆与回放是另一条机制。报告提到，通过回忆/回放激活相应记忆，在学新东西和“温故而知新”之间做平衡。从通用原理看，回放相当于在不直接重复全部历史的情况下，重新激活对当前任务有用的旧记忆，让新旧经验发生联系。它不是简单重复，而是有选择地提取和重组。

遗忘也被报告明确为一种智能。forget 与 unlearn 不是附属操作，而是记忆治理的重要组成。一个只会不断写入的系统，最终会被噪声和过时信息拖累；能够判断哪些记忆该淡化、哪些该删除、哪些需要反学习，才是“选择性代谢”的一部分。

报告用一句话概括这一方向的内核：希望把“无差别的存储”变成“选择性的代谢”。这也是生物/脑启发机制的核心。记忆系统的能力不仅在于存了多少，更在于选择什么进入长期记忆、什么时候激活、什么该退出，以及如何在更新中保持一致性。

### 应用探索与评估空间

报告还提到，机器人、认知辅助和数据合规等应用方向已有探索。这些方向说明认知层记忆不只是对话系统的附属功能，而可能进入具身任务、个人认知支持和数据治理场景。不过报告同时指出，这些方向的深度、影响范围以及如何做 benchmark，都还有进一步研究空间。

这也回到闭环的整体判断：检索—推理—更新—再检索不是一次性的架构图，而是一组需要持续治理的过程。记忆图检索、策略化读写、上下文演化、逐轮精炼与压缩，解决的是“如何让记忆参与认知”；分层、巩固、回放和遗忘，解决的则是“如何让记忆有选择地代谢”。两者结合，才构成报告所说的认知层闭环。

## 自演化与主动记忆：测试时学习与经验策略化

这条线索的核心判断是：记忆正在从“被动存储”走向“主动干预”。过去谈记忆，更多是把信息存起来，等任务来了再检索；报告强调的方向则是让记忆在恰当时间被生成或调用，也就是 just-in-time 的即时记忆。它不是简单地把检索提前，而是把“何时需要记忆、需要哪一类记忆、以什么形式介入当前任务”本身纳入决策。与之配套的是 test-time 的记忆运行时自演化：系统在测试和使用过程中边用边学，更新记忆及相关策略，尽量避免重新训练。再往前一步，是把成功与失败经验转成可推理的策略和技能，并用强化学习加以利用，最终对应到 RSI/递归自演进的讨论。

### 从“等待检索”到“即时干预”

被动记忆的典型形态是仓库：先写入，后查询，记忆系统等待一个检索请求。报告希望改变的是这种无差别存储方式，转向更有选择性的“代谢”，其中带有脑启发的意味——不是所有经历都同等重要，也不是所有记忆都应在同一时刻被调用。即时记忆的关键在于“恰当时间”：在任务推进中判断此刻是否需要补充记忆、是否需要调用过去经验，甚至是否需要即时生成一条新的记忆来支撑当前决策。这样，记忆就从背景资源变成了主动干预手段。

这也解释了为什么“主动”不是越多越好。主动记忆必须回答判别问题：哪些信息值得写入，哪些记忆值得调用，调用后是帮助还是干扰。报告在应用部分特别提到“记忆的判别和主动行为的深度、打扰程度如何控制”，说明主动干预的难点不只在技术上的“能不能”，还在交互上的“该不该”和“做到什么程度”。

### 测试时学习：把记忆运行时当作可更新系统

与即时记忆相对应的是 test-time 的记忆运行时自演化。它的基本思路是：系统不必等到离线重新训练才获得新能力，而是在测试过程中更新记忆和相关策略，做到边用边学。作为背景，这可以理解为一种面向使用阶段的持续适应：环境、用户偏好和任务上下文都在变化，完全依赖训练时固定下来的记忆与策略，容易出现滞后；而每次都重新训练，成本又过高。运行时自演化试图在两者之间找一条路。

但“边用边学”也带来新的约束。运行时更新的不只是记忆内容，还可能包括记忆的组织方式和调用策略；更新得对不对、会不会把偶然经验固化成错误偏好、会不会让系统越学越偏，都需要评估和治理。报告把“自演化记忆的评估和治理”列为需要进一步关注的问题，说明这条路线目前更像一个方向性判断，而不是已经解决的工程闭环。

### 经验策略化：成功经验与失败经验都要变成可推理的策略

另一条主线是经验的学习与策略化。报告强调，不仅需要成功经验，也需要失败经验。原因不难理解：成功轨迹告诉系统“什么可能有效”，失败经验则提供边界、反例和避坑条件；如果只沉淀成功，系统容易把偶然成功误当成普遍策略。关键动作是把这些经验转成可以进行推理的策略和技能，而不是停留在一堆原始轨迹上。随后再用强化学习去利用这些经验，让策略在反馈中改进。

这条线索再往前延伸，就对应 RSI/递归自演进：策略改进反哺记忆和行动，行动又产生新经验，新经验再被策略化。作为背景，RSI 通常指系统改进自身能力、并由此带来进一步改进的递归过程；在这里，记忆和策略的自演化被看作它的一个具体落点。但递归并不天然等于有效。报告特意提出“递归自演进自身的退化和效用如何保证”，意味着自我改进循环需要防止错误经验被反复放大，也要回答改进是否真的带来效用，而不是只在循环中自我确认。

### 应用场景与尚未回答的问题

报告举到的应用包括智能家居、健康管理，以及工作和投资过程中的 agent。这些场景的共同点是：agent 不只是单轮问答，而是要在长期上下文中辅助人，因而记忆的主动性和时机变得重要。比如在智能家居中，什么时候主动提醒、提醒到什么程度；在健康管理中，哪些历史信息值得在当下调用；在工作和投资 agent 中，过去的成功与失败经验如何转成可推理的判断策略，而不是简单复述历史。

围绕这些场景，报告留下了一组需要继续回答的问题：

- **何时应该主动行动**：主动记忆和主动行为需要有判别机制，不能把所有相关记忆都推送到当前决策中。
- **主动行为的深度与打扰程度如何控制**：主动干预可能带来帮助，也可能造成打断，需要控制强度、频率和呈现方式。
- **自演化记忆如何评估和治理**：运行时更新后，记忆质量和策略质量是否提升，更新边界如何约束，都需要评估与治理。
- **递归自演进的退化与效用如何保证**：自我改进循环要避免退化，并证明其实际效用，而不是只完成形式上的递归。

从报告给出的线索看，这一方向在 2025—2026 年已有若干相关工作被纳入讨论，每一块大约举了三个左右的工作来提示关注点。整体上，它把 self-evolving、test-time learning 和经验策略化串成了一条线：记忆不再只是被检索的静态仓库，而是可以在运行时更新、在恰当时机介入，并把成功与失败经验逐步沉淀为可推理、可强化的策略。与此同时，主动性、打扰控制、评估治理和递归效用，仍是这条路线必须回答的限制条件。

## 可审计记忆与跨 Agent 共享治理

当记忆从一次对话中的上下文，变成会持续写入、检索、派生和删除的系统状态后，问题就不只是“记得准不准”，而是“能不能信、能不能查、出事能不能控”。报告把这一转向概括为：需要一层 harness，把记忆过程从“黑箱”变成“可审计”，使记忆可溯源、可复核，也能被申诉和干预。这里的 harness 可以理解为包在记忆系统外部的运行、约束与评测框架，负责记录记忆如何进入系统、如何被使用，并在必要时支持回放、隔离和修正。

这一要求与跨 Agent 共享直接相关。系统不会长期停留在 single agent；一旦多个 Agent、多个用户开始共享记忆，记忆就不只是本地状态，而会成为跨边界的治理对象。可审计性解决“单条记忆是否可信”，共享治理则进一步解决“哪些记忆可以跨边界流动、由谁负责、污染如何不外溢”。

### 可审计记忆的四个层面

报告将可审计记忆拆成证据溯源、归因、可观测、合规与审计四个层面。四者不是并列的功能清单，而是覆盖记忆从写入到被使用的不同环节。

| 层面 | 要回答的问题 | 关键落点 |
|---|---|---|
| 证据溯源 | 这条记忆从哪里来、经过哪里、到哪里去 | 来源可查，保留写入来源、处理过程和使用去向 |
| 归因 | 为什么这次检索会得到这条内容 | 能解释检索结果与原始证据、任务需求之间的关系 |
| 可观测 | 系统当时按什么策略写入和检索 | 工程层面记录记忆写入、检索策略，支持回放和血缘关联 |
| 合规与审计 | 能否审核、写入、派生和删除 | 覆盖记忆生命周期，支持审计与必要的删除、撤回 |

证据溯源强调“来源可查”。一条记忆可能来自用户输入、工具返回、其他 Agent 的写入，也可能经过摘要、合并、改写等派生过程。如果只保存最终文本，而不保存它的来源和派生链，后续就很难判断它是否可靠，也无法在出现错误时定位问题。因此，溯源不只是记录“存在哪”，还要知道“从哪里来、经过哪里、到哪里去”。

归因则针对检索结果回答“为何如此”。记忆系统往往会在大量候选内容中选出若干条进入上下文；如果没有归因，用户或开发者只能看到结果，却不知道系统为什么选择了这些内容。归因需要把检索结果与证据链、检索条件和策略关联起来，使一次记忆使用可以被解释，而不是只给出一个看似合理的答案。

可观测是工程实现层面的支撑。报告强调要记录记忆写入和检索策略，支持回放以及血缘关联。对审计而言，普通的文本日志通常不够，因为需要知道某个时间点系统采用了什么策略、写入了什么、检索了什么、影响了哪些后续结果。只有具备结构化记录和回放能力，才能复核一次记忆行为，并在出现争议时还原过程。

合规与审计覆盖审核、写入、派生和删除。记忆不是只增不减的数据库；它需要支持审核，允许对不适当内容进行写入限制、派生控制和删除。对 mission critical 场景而言，这一点尤其重要：当记忆越来越自主，系统可能在没有明确人工指令的情况下总结、更新或复用经验，“信不信”就成为核心问题。报告因此强调，记忆要“可看懂、可被干预”，例如能够被检查、更正、撤回或隔离，而不是只能被动接受。

评估也需要对应这四个阶段设计关键指标，而不能只看最终回答准确率。来源是否完整、归因是否足以解释一次检索、日志是否支持回放、写入和派生及删除是否有审计记录，都是需要被衡量的对象。报告没有给出统一的数值标准，但明确指出这些阶段仍有很多待解决问题。

### 跨 Agent 共享：用“记忆护照”约束流动

跨 Agent 记忆共享的第一个问题是边界：多个用户、多个 Agent 之间，哪些记忆应该共享。不是所有记忆都适合跨边界流动；有些只属于某个用户，有些只在特定任务内有效，有些虽然可以共享，但需要脱敏或限制用途。报告提出“记忆护照”的概念，用身份、权限和来源三块信息来判断一条记忆能否“过关”。

- **身份**：这条记忆属于谁、由哪个 Agent 写入、在什么上下文中产生。
- **权限**：谁可以读、写、派生、共享或删除这条记忆。
- **来源**：记忆来自哪里，是否经过改写、合并或其他 Agent 的二次加工。

“护照”这一比喻强调的是：记忆跨 Agent 流动不是简单的数据复制，而是一次需要检查身份、授权和来源的跨边界操作。它也可以看作审计信息在共享场景中的携带方式——共享前先确认这条记忆是谁的、能不能给、来自哪里。

在此基础上，报告拆出四个问题。

**第一，协作边界。** 多用户、多 Agent 协作时，需要明确哪些记忆进入共享池，哪些保留在本地。共享范围过宽会带来隐私和污染风险，过窄则无法形成协作优势。边界问题不仅是权限设置，也涉及任务相关性：某条记忆对当前协作是否有用，是否应该被其他 Agent 看见。

**第二，协议互操作。** 记忆如何在 Agent 之间流动，需要协议支撑。报告指出，工具调用等领域已经有许多协议，但目前还没有专属记忆的协议。现有探索中，Universal Memory Protocol 这类工作试图讨论记忆互操作与协作协议，但整体仍处于开放或部分解决阶段。缺少专用协议，意味着记忆的格式、权限、来源和生命周期很难在不同框架之间一致表达。

**第三，治理与编排。** 谁来管理共享记忆，是跨 Agent 场景中的核心问题。报告引用“memory 管理变成 state 的 runtime”的说法，强调共享记忆不是静态存储，而是需要被治理的运行状态：写入什么、共享什么、何时失效、由谁负责，都要有策略。治理与编排要把共享记忆变成受治理的操作状态，而不是让各个 Agent 自行读写、事后无法追责。

**第四，隔离与防污染。** 共享记忆一旦被错误内容、恶意内容或过时内容污染，可能通过检索被多个 Agent 反复复用，造成扩散。因此一方面要“不出事”，通过权限、隔离和写入审查降低污染概率；另一方面要在出事后避免进一步扩散，例如隔离受影响记忆、限制传播范围、支持回滚和溯源。报告特别指出，这与 harness 密切相关：审计和可观测能力不仅用于解释，也用于控制事故半径。

### 评估与现有探索

跨 Agent 共享的评估不能只看共享后任务是否更快，还要看治理成本和安全边界。报告提到的指标包括：互操作成本是否更低、污染扩散半径是否尽量小、隔离开销是否较小。这三类指标之间存在取舍：共享越充分，复用收益可能越高，但污染传播面也可能越大；隔离越严格，风险越低，但协作成本和运行开销也会上升。

现有探索包括 CrewAI、LangGraph 等多 Agent 框架中的共享机制，以及 Universal Memory Protocol 这类记忆互操作或协作协议。它们提供了共享记忆的工程抓手，但报告判断这里仍有大量开放或部分解决的问题：记忆协议尚未统一，跨框架的身份、权限和来源难以一致表达，共享记忆的治理责任和污染控制也缺少成熟答案。

整体来看，可审计记忆与跨 Agent 共享治理指向同一个目标：让记忆从不可见的内部状态，变成可追踪、可解释、可授权、可隔离的运行对象。前者提供审计与干预的基础，后者则把这种能力扩展到多 Agent 边界；两者结合，才可能支撑 mission critical 场景下对记忆的信任。

## 记忆质量评估与可写记忆安全边界

在记忆能力走向实用化的过程中，质量评估与安全边界是两个相互咬合的约束：前者回答“记忆系统到底能做到什么样子”，后者回答“记忆可以被写到什么程度、写到什么内容仍然可信”。报告中把质量评估列为第九个挑战，把安全、隐私与可控性列为第十个挑战。二者共同指向一个变化：记忆不再只是“能不能召回”的问题，而是要在演化、长程、交互和可写条件下，变成可评估、可治理的基础能力。

### 评估重心：从召回走向记忆质量

报告首先强调，benchmark 在很大程度上决定了系统“到底能做到什么样子”。如果评测只看少数静态指标，系统能力就容易被这些指标定义。早期记忆评测更重视 recall/召回，以及真实性、时效性和相关性；这些维度仍然重要，但已经不够。报告主张继续下探到记忆过程中的幻觉、操作层面的漂移等问题。

这里的“幻觉”不只是生成回答时的编造，也可以理解为记忆在写入、更新、检索和使用过程中产生了与事实或状态不一致的内容；“漂移”则更偏向操作和过程层面，指随着交互推进、状态变化或时间拉长，记忆表示和行为逐渐偏离原本应当保持的内容。评估如果只看最终答案是否命中，就很难发现这类过程性问题。因此，评估对象需要从“结果对不对”扩展到“记忆过程是否可靠”。

### 三类具体评估关注

报告给出了三个具体方向。

第一是状态追踪和不断演化的记忆评测。核心问题是系统能不能记住新东西。真实交互中的记忆不是一次性建好的静态库，而是会不断出现新事实、新状态和新约束。评测需要构造状态变化，观察新信息是否被写入、旧状态是否被正确更新或失效、冲突信息是否得到处理。只测固定知识库上的召回，无法回答“演化中的记忆是否成立”。

第二是更长程中的漂移，也就是“记得久”是否成立。长程评估不能简单等同于把上下文拉长，而要观察经过多轮交互或较长时间后，记忆是否仍然保持可用、稳定和一致。报告指出，这类评估的成本较高，尤其是特别长程、长上下文的评估，以及重新构建评估环境的成本都比较高。

第三是交互和策略使用：系统是否确实用了记忆。检索到了相关内容，不等于系统在决策或回答中真正使用了它。报告提出通过消融实验说明记忆确实起作用。从通用评估方法看，可以移除、冻结或打乱记忆模块，再比较任务表现；如果性能没有明显变化，就说明记忆没有被真正调用，或者当前任务并不依赖记忆。这类实验比单独报告召回率更能说明记忆机制的实际贡献。

### 应用很多，但评估基础设施仍然碎片化

报告列举了记忆质量评估的相关应用，包括记忆 OS、企业定制、coding agent、搜索与研究等。这些场景对记忆的要求并不相同：有的更强调状态更新，有的更强调长程一致性，有的更强调在复杂任务中调用历史信息。但现阶段 benchmark 仍然呈现碎片化、烟囱化的特点，缺乏统一的记忆质量标准。

| 评估关注 | 要回答的问题 | 当前缺口 |
| --- | --- | --- |
| 状态追踪与演化 | 新信息能否被记住并影响后续行为 | 静态评测多，演化环境少 |
| 长程漂移 | “记得久”是否真正成立 | 长程、长上下文评估成本和环境重建成本高 |
| 交互与策略使用 | 系统是否确实调用了记忆 | 召回指标与下游使用效果可能脱节 |
| 应用外推 | 评测结果能否反映真实应用 | benchmark 碎片化，与真实应用相对脱节 |

因此，报告所说的“从召回走向质量”，并不是否定召回，而是把召回放进更完整的质量框架中：既看能否找到，也看记得是否准、是否稳、是否被真正使用，以及评估结果能否代表真实应用。

### 可写记忆的威胁面

安全问题的前提是记忆可以被写入。报告明确指出，记忆一旦可写，就可能被污染、被注入和被提取。报告反对把记忆变成“不管的地带”，而要做成可控和可信的记忆。

威胁面主要包括三类。第一是投毒写入：恶意内容进入记忆，并在后续检索或使用中影响系统行为。第二是上下文注入：例如无需任何权限就可以查询到许多相关内容，使本不该进入上下文的内容进入模型上下文。这里的关键不只是内容本身，还包括查询权限和检索接口的暴露程度。第三是隐私抽取：攻击者或未授权方可以反向抽取隐私和用户画像。长期记忆会聚合大量历史信息，因而画像泄露和隐私边界问题更加突出。

### 防御链：写入护栏、污点检测、审计与闭环修复

针对这些威胁，报告提出的防御侧能力包括写入护栏、污点检测、审计和闭环处理。

写入护栏（guardrail）作用在记忆进入系统的入口，对写入来源、权限和内容策略进行约束，避免恶意或不可信内容直接进入长期记忆。污点检测用于识别被污染的内容，并追踪其在后续检索和使用中的传播。审计则提供可追溯性，记录写入、读取和使用过程，为事后定位和止损提供依据。闭环处理强调不能只发现问题不解决：不仅要实时判断中毒或污染，还要能够隔离、回滚、修复和进化，使系统在攻击变化时保持自适应鲁棒性。

从通用安全工程的角度看，这类似数据供应链安全：写入是入口，检索是传播面，审计是追溯手段，闭环修复是止损机制。报告还特别提到长期画像泄露与隐私边界，以及安全与可用性的权衡。安全拦得太紧会压缩系统的自由度，并抑制智能性；因此防御不是越严越好，而是要在可控、可信和可用之间取得平衡。

### 质量与安全的耦合

可写记忆使质量评估和安全边界不再彼此独立。评估不能只测干净条件下的召回和真实性，还要看污染、注入和隐私抽取发生时的记忆质量；安全也不能只停留在“拦住”的层面，而要有可度量、可审计、可修复的闭环。报告没有给出统一的记忆质量标准，但指出了一个明确方向：记忆系统的“好”不只是召回高，而是能在状态演化、长程保持和交互使用中维持质量，并在可写条件下守住安全边界。质量评估定义能力边界，安全边界定义可信边界，两者共同构成记忆从演示走向真实应用的基础条件。

## 十项挑战的阶梯与 2027—2028 路线判断

报告没有把十项挑战处理成十个并列难题，而是把它们组织成一条向上的阶梯：底层先把记忆空间建起来，中层让记忆从被动存储走向自演化，顶层让系统从“功能可用”走向“可被信任”。这个顺序很重要，因为上层能力依赖下层设施；没有统一记忆空间，自演化和信任治理都缺少可操作对象。十项挑战因此既是研究议题，也是路线图上的分段路标。

### 三层阶梯：先有空间，再有能力，最后有信任

**基础设施层**关心的是从碎片化记忆走向统一的、可寻址、可检索的记忆空间。碎片化记忆可能散落在对话、文档、设备和个人应用中，彼此没有一致地址和索引，系统只能临时拼接。统一记忆空间不是把所有内容堆到一个库，而是让记忆有位置、有索引、有检索入口，能被定位、组合、更新和追踪。作为背景，可寻址和可检索是记忆从“上下文里的一段文本”变成“系统可管理资源”的前提。

**认知层**则从被动存储走向自演化能力。被动存储只负责写入和回放；自演化要求记忆参与后续推理，系统能根据新经验调整检索、更新和策略。也就是说，记忆不只是“记住什么”，还影响“下一次怎么找、怎么判断、怎么行动”。

**可用与信任层**把目标从功能可用推进到可被信任。功能可用回答“能不能完成任务”，可被信任还要回答“行为是否可预期、边界是否清楚、出错能否追溯、安全能否认证”。这一层与产品落地中的治理和合规直接相关，也是阶梯顶端最容易被低估的部分。

### 质量、协作与信任：三条并行的转变

与阶梯对应，报告提出三条转变。质量上，从“记得多”转向“记得对”。记忆系统的价值不在容量本身，而在正确、相关、时效和冲突处理；记得越多，如果检索不准、更新不及时，反而会放大错误。协作上，从 single agent 走向 agent 社会。多个智能体分工时，记忆需要共享、隔离和治理，否则局部经验无法复用，错误也会跨 agent 扩散。信任上，要形成良性循环，而不是一次性认证：使用产生反馈，反馈进入评估，评估修正记忆和安全边界，再回到使用。报告还呼吁学术界、产业界和投资三方协同推进；从通用创新规律看，学术侧定义问题与评测，产业侧暴露真实约束，投资侧支持长周期基础设施，三者缺一都会让记忆停在演示阶段。

### 2027—2028 的三组判断

报告把十项挑战分成三组来看路线：前三个挑战对应“记忆的新基建”，中间部分对应“记忆能力提升”，后段对应“产品落地中的治理和合规”。这与三层阶梯相呼应：先修路，再提升能力，最后把治理和合规纳入产品体系。

| 时间尺度 | 路线判断 | 重点变化 |
|---|---|---|
| 短期 | 统一记忆空间可能成为开源框架的标配 | 记忆从外挂模块变成框架基础能力，地址、索引、检索接口趋于统一 |
| 中期 | 端侧记忆、联邦落地在主流个人场景和穿戴式设备中体现 | 记忆部署靠近个人设备，隐私约束推动端云协同和联邦式落地 |
| 长期 | 记忆驱动的推理与认知范式成为主流，甚至大家慢慢不再提 RAG | 检索、更新、推理融合为记忆原生过程；评估和安全认证纳入体系 |

短期判断的关键词是“标配”。统一记忆空间一旦进入开源框架，开发者不必每个项目都自己拼记忆层，记忆的地址、索引和检索会成为公共能力。中期判断的关键词是“落地形态”。端侧记忆和联邦落地并不是简单把数据搬到本地，而是按隐私、时延和成本重新分层：敏感记忆留在端侧，需要时再协同。作为背景，联邦思路通常强调原始数据不外传、只交换必要的模型或统计信息，这正好对应个人场景和穿戴设备对隐私的强约束。

长期判断更根本：记忆驱动的推理与认知范式可能成为主流，RAG 作为当前常见的“先检索再生成”做法，可能逐渐不再被单独强调。这里不是说检索消失，而是检索被吸收进记忆系统，成为持续更新和推理的一部分。与此同时，评估和安全认证会纳入体系，以支持长程自演化、“有温度”和隐私保护等“既要又要还要”的目标。所谓“有温度”，可以理解为记忆能贴合个人长期情境、让交互更连贯自然，但这必须与隐私保护和可审计性同时成立；目标不是单点最优，而是多目标平衡。

整体看，2027—2028 的判断不是一张精确到季度的排期表，而是按能力依赖关系给出的方向性窗口：短期先看统一记忆空间能否成为框架标配，中期看端侧与联邦能否进入主流个人场景，长期看记忆驱动的认知范式能否取代把检索外挂的做法，并把评估、安全认证和治理一起纳入体系。阶梯的意义也在这里：十项挑战的数量不是重点，重点是把记忆从“存得多”推进到“找得到、用得对、可信任、可治理”。

## 端侧视觉记忆：从“视频理解缺口”到个人 AI 基础设施

演讲者从自己在 Meta 的经历讲起，给出一个很具体的判断：当时的 AI 有两个能力缺口——没有特别好的视频理解能力，也没有特别好的长视频理解能力。在他看来，这不是一个局部问题，而是 AI 未来进入物理世界时非常重要的功能。正因如此，他在去年年初与伙伴出来创业，公司 base 在硅谷，去年融资近 1600 万美元。

团队配置也围绕这个方向展开：联合创始人 Ben Zhou 曾是 Meta 端侧 Vision Perception 的 Tech Lead；Chief AI Officer Eddie 曾是 Meta Superintention Lab（转写）的 Research Scientist，主要做多模态 AI 模型训练；COO Ryan 有斯坦福 Undergrad 和 MBA 背景，自己创过业。产品线名为 Lucy，全称是 Long Understanding Contextual Intelligence。整体路线偏底层：自己训练 perception model，并把它优化到端侧，围绕“让 AI 记得住”提供端侧视觉记忆的基础设施。

### encoder-heavy：把感知和推理拆开，把索引放到端侧

团队对系统架构有一个基本拆分：未来大致可以分为 perception、reasoning 和 action。现在所有 scaling law 主要在文本上涌现，action 和 perception 也在慢慢进入 reasoning。团队希望与 reasoning 正交，因此几乎只做 encoder、只做 perception tasks，形成了非常 encoder-heavy 的架构。从通用架构角度看，这意味着把计算重心放在视觉编码和感知端，而不是把原始视频直接送进云端大模型做端到端推理；感知层负责把视频变成可检索、可调用的结构化表示，推理和行动则交给上层 agent。

把 perception 优化到端侧，理由很直接：未来视频是 30 帧/秒，不可能 30 帧/秒都在云端跑各种 inference，也不可能把所有视频都放到云端。因此团队在端侧做 on-device indexing，把视频变成结构化数据。转写中把这种结构化数据称为 `logics`，并称 `logics` 可以在 language 和 coding space 里做 scaling；indexing 实际干的就是把数据变成 `logics`。从上下文看，这里的重点不是形式逻辑系统，而是把视频转成能进入语言/代码空间、可被 agent 检索和推理的表示。

这些结构化结果会存入自研的 video database，再把 database 当成 tool 给 agent 使用。团队相信 retrieval、memory 等能力会随着 agentic model 提升而提升；自己要提供的是好的 indexing 和好的 retrieval database，其他部分交给 agent。上层 harness 则非常 application based。也正因如此，团队明确不碰与 agent harness 相关的东西，除非有明确的产品利益和产品需求。他们专注的是更底层的事情：怎么放到 NPU 上、怎么在 NPU 上优化和部署、database 怎么选型、怎么把 retrieve 做得更快，这些与 agent 正交。

模型层面，团队有一个 omni model：input 是 video，output 可以是 embedding，也可以是 caption，通过换不同 heads 实现。报告提到 Omni Retriever 论文，以及另一篇被接收的论文 Special Mem（转写），后者专门做 on-device indexing，并面向 agentic spatial/special memory 和 agentic visual reasoning。团队也做过很多实验，把视频湖通过 MCP 接到 agent 上，试过 OK Astro、Gemini 等模型；这条思路的重点不是自己包办 agent，而是让数据库成为 agent 可调用的工具。

端云分工上，团队的判断是：indexing 一定在端侧，同时围绕具体记录可以完成一些简单 QA；更多 actions 则 leverage 最新 agents 在云端完成。底层基础设施可以端侧部署，也会部署在云端，但索引的位置判断在端侧。

### 产品矩阵：桌面、眼镜、可穿戴、Ring 与企业媒体库

在底层 indexing 和 video data lake infra 之上，团队做的一个重要 application 是 personal AI，核心场景是 memory retrieval。例如用户问“上周跟客户聊的眼镜产品进展是哪些”，系统会找到之前的交互记录，整理进展，并依据记录给出下一步。团队认为传统 QA 并不是 personal memory 的好 use case，因为搜索并不是 C 端很大的需求，用户可能一个月只用几次；这些记录不是给用户看的，而是给 agents 看的。Lucy Desktop 在本地全部 indexing 完之后，相当于给 agents 一个 digital twin 和 digital memory。

| 产品/合作 | 形态与场景 | 端侧做法与已知信息 |
|---|---|---|
| Lucy Desktop | 电脑本地录屏 | 录屏转文字、再转 embedding，本地建加密数据库，所有东西本地跑；可让 Open Cloud、Hermes Cloud、Codex 等通过数据库拿到用户 context；目前每周增长约 40%，但演讲者称它只是公司的 toy product，由一个工程师做出来，底层 infra 和 inference 由整个公司做 |
| Lucy Glass | 智能眼镜方案 | 在高通 Snapdragon Summit（夏威夷）发布展示，跑在高通 AR One 上；所有东西本地 indexing，可实时回答“刚刚过去五分钟 presentation 做得怎么样、能给什么建议”，也可问黑板上做了什么、画了什么 |
| Lucy Pin | 端侧可穿戴硬件 | 已经量产，可收集视频和音频，所有东西都可以跑在端侧；相当于把电脑端能力延展到现实生活。展会场景中 always recording、always on，用户几乎不需要记别人的名字，可让系统列出今天所有的人，并让 agent 通过 computer-use 回复微信 |
| Ring 战略合作 | 家庭摄像头场景 | 演讲者称 Ring 在美国几乎每家每户都有；Ring 几乎所有摄像头都有团队的端侧模型、端侧 infra 和 data lake，用户可以直接接 memory agent，问“今天谁来过”“今天什么时候亚马逊包裹到了”“来的人是谁”等；也可以通过 MCP 接到 Cloud（转写），让 Cloud 自己定义 daily routine；该合作用户量非常大 |
| 企业个人媒体库 | 与联想、三星合作 | 三星也是投资人之一；目标是帮用户把本地多媒体库全部 index 完，再把这些 indexing 结果变成 agent 的多模态记忆 |

Lucy Desktop 的体验很能说明“个人 AI”与“搜索工具”的区别：演讲者说自己每天都会“蒸馏自己一遍”，所以让 Cloud 完成任务时几乎不需要太多 prompt，因为系统非常了解他。Lucy Desktop 现在可以直接下载，本地数据库加密，所有东西在本地跑。它每周增长约 40%，但演讲者仍称它是 toy product；这个反差恰恰说明，上层 application/harness 可以很轻，真正重的是底层 infra 和 inference。由此他给做 harness 的人的建议是：先瞄准 application，再做 harness，因为 harness 非常 application oriented，一个人可能就够了。

Lucy Glass 则把本地 indexing 带到眼镜上：所有东西在高通 AR One 上本地跑，用户可以问刚刚过去五分钟的 presentation 表现如何、能给什么建议，也可以问黑板上做了什么、画了什么，系统可以实时记录。Lucy Pin 把能力进一步延展到可穿戴硬件：它已经量产，能收集视频和音频，所有东西都可以跑在端侧。展会是一个典型场景：佩戴 wearable device，always recording、always on，有视频有音频，用户几乎不需要记别人的名字，可以直接让系统列出今天所有的人，并让 agent 通过 computer-use 回复微信。

不过演讲者对 AI 可穿戴硬件的限制判断也很明确：这个方向仍处于比较早期，还有很多隐私问题要解决，更多是 social product、social problem 和 product problem。技术已经在了，难点是让 personal AI helpers 进入 day to day life 的产品设计和社会问题。与 Ring 的合作则更偏家庭场景和基础设施：Ring 摄像头集成团队的端侧模型、端侧 infra 和 data lake，用户可以直接接 memory agent，问今天谁来过、包裹什么时候到、来的人是谁；也可以通过 MCP 接到 Cloud，让 Cloud 自己定义 daily routine。团队本质上做的是一个大的 inference 和 infra，提供给各种 B 端公司做他们自己的应用。企业个人媒体库方案则与联想、三星合作，帮用户把本地多媒体库全部 index 完，再把这些 indexing 结果变成 agent 的多模态记忆。

### 隐私、功耗与 grounding：为什么本地跑，原始视频为何不删

团队认为视觉记忆在本地跑非常重要，原因有两个。第一是功耗：所有东西跑在 NPU 上，NPU 其实不是特别耗电；反倒是把所有视频都上传到云端非常耗电。第二是隐私。演讲者以 Lucy Desktop 的本地录屏为例：这个录屏最初是上云的，他用了一段时间后总觉得心里有疙瘩，担心工程师可能发现自己电脑上聊了什么、干了什么；所以后面决定全部做本地。现在他每天 24 小时都开着，本地化对隐私保护非常重要。

但本地化并不意味着只保留抽象索引。做 indexing 时，原视频并不会完全删掉，因为很多时候要做 grounding，agent 也会想拿原始图片做 grounding 和 segment/step reasoning。团队会保存一些原始关键片段或关键帧。团队有自己的端侧视频压缩技术，今年在 ICLR 有一篇论文（转写为 Allmark，又称 MARC），会把视频的关键帧、关键片段储存下来，让后面的 agent 能够做 reasoning 和 grounding，同时给用户一层 proof，告诉用户拿到的答案是正确、可验证的。

流程上，团队先保存记录，再做本地 indexing；所有问题、时间条件等都会进入 metadata；最后用 agent 去做 grounding。这里形成一个重要权衡：为了 grounding 和可验证性，不能只留抽象索引，需要保留关键片段或关键帧；团队用端侧视频压缩来控制保留原始视觉证据的成本。

### 原生多模态还是 agentic 视觉推理：两条路径的对照

报告最后把问题提升到模型路线选择：原生多模态模型与 agentic 视觉推理。观察是：Gemini 的原生多模态能力很强，但在真正的 agentic visual reasoning 和 long video understanding 任务上，Opus 或转写中提到的 Azure 可能更强，原因被归结为 agentic 能力更强。另一个发现是，长程任务跑得越长，reasoning 反而越好；输入不一定是完整视频，可以只是 frame，模型通过联想推断出这是怎样的视频。

由此给出的选择建议是：若在多模态与 agent 之间取舍，在 agent 上做 scaling 能带来多模态能力提升。可测试的两条路径是：

1. 把视频直接交给 Gemini 做 reasoning，走原生多模态端到端路线；
2. 先把视频 indexing 成结构化数据，放入视频数据湖，再交给 agentic model 做 agentic visual reasoning，走“先索引、再推理”的路线。

两条路径可以用 MCP 接到 Cloud（转写）上比较，观察哪条路径在 visual reasoning、甚至 speed 上更好。讲者称其研究认为用 agents 更好，相当于给 agent 一个更好的 harness；这一架构还可用于安防监控、个人助手等应用。

整体看，这场报告的核心不是再做一个通用视频理解模型，而是把竞争点放在端侧感知、端侧索引和可被 agent 调用的视觉记忆基础设施上：encoder-heavy 的 perception model 负责把视频变成结构化数据，本地 video database 负责检索与记忆，云端 agent 负责更复杂的 reasoning 和 action。个人 AI 的产品矩阵则从桌面录屏、眼镜、可穿戴硬件延伸到 Ring 和企业媒体库。其限制也很清楚：可穿戴硬件仍早期，隐私和产品设计是主要障碍；原生多模态与 agentic 视觉推理的优劣仍需要通过具体任务路径来检验。

## Agent 成本与三类记忆：执行—沉淀双循环

报告用一个办公场景开场：让智能体生成周报。第一次执行并不顺利，出现错误，需要做数据清洗和查找；第二次只给一个简单提示词，要求“重复上一次的格式”，耗时从 18 分钟降到 1 分 20 秒，工具调用显著减少，token 消耗也少很多。这个对比说明，周报的数据每周都变，但处理方法高度重复。如果每次都从零开始规划、试错和纠错，不保留上一次的记忆，就会反复消耗大量 token。报告要解决的就是在重复场景中保留之前成功的记忆，实现任务复用。

### 成本从哪里来

讲者把 agent 成本拆成三类。

第一是**任务异质性**。一个任务可以拆成很多步骤，各步骤难易不同；如果所有步骤都使用同样昂贵的模型，会很浪费。需要打分机制把步骤分成简单步骤和复杂推理步骤，分别使用不同模型和思考强度。

第二是**过程性开销**。对话历史越积越长，token 消耗和等待时间随之增长。

第三是**经验难以复用**。相似任务反复出现，但成功做法没有沉淀，下一次仍从头再来，重复消耗 token。

由此，研究目标不是单纯压低某一步的模型价格，而是在保证质量和可接受时延的约束下，降低模型的长期总成本。

### 三类用户记忆

为把经验留下来，报告把用户记忆分为三类：

- **情景记忆**：仍以周报为例，上一周用了哪些资料、在哪一步出过错。
- **语义记忆**：用户偏好，例如希望生成什么样的报告。
- **程序性记忆**：这类报告要怎样生成。报告特别强调这是最受关注的一类，因为它直接对应“下次怎么做”。

三类记忆不是彼此孤立地查询，而是统一在一个任务的上下文里调用。从通用认知角度看，情景记忆回答“上次发生了什么”，语义记忆回答“用户要什么”，程序性记忆回答“这类事该怎么做”；三者合在一起，才可能让下一次执行既符合偏好，又避开上次的坑，并复用上次的步骤。

### 执行循环与沉淀循环

整体框架包含两个循环。上层是**执行循环**：任务进来后，先由 Tier Sense 决策模型拆解任务，用打分机制判断步骤属于简单还是复杂，再调用 Tier Flow 调度平台执行，最后做验收检查，确认目标与产物是否符合用户要求。材料提到打分机制总分十分，由五个维度、每个维度零到二分构成，据此决定用简单模型还是复杂模型。这样做的直接目的是避免“所有步骤都上昂贵模型”的浪费。

执行循环之后是**沉淀**。若用户满意，系统留下成功轨迹，并从中提取成功步骤，加入该用户的技能库。技能库之后可被检索复用，节省下一次成本。这里的关键条件是“用户满意”和“成功轨迹”：不是把所有执行记录都固化，而是把被验收通过的做法沉淀下来。下一次遇到相似任务，技能库可以复用，减少重新规划和纠错的 token。技能数据还可通过编译小模型、后训练的方式实现参数层面的能力迁移——作为背景理解，这相当于让技能不只停留在可检索的外部条目，还可能以参数形式进入更小的模型。

因此，这个“执行—沉淀”双循环的核心不是让 agent 在每次任务里更会“想”，而是让它在重复任务里少重复“想”已经成功过的部分；成本下降同时来自步骤级的模型匹配和经验级的复用。需要看到的是，报告的目标带有约束：质量要保证，时延要可接受，长期总成本才是有意义的下降。

## Tier Sense 与 Tier Flow：步骤难度判断、调度与记忆管理

这组报告关注的是 agent 在执行任务时，如何在每一次模型调用前做判断：当前步骤到底有多难，需要多强的模型和思考强度；历史上下文里哪些内容该压缩、哪些该召回。Tier Sense 负责产出步骤级判断，Tier Flow 则把这些判断接入实际调用与成本调度，并用记忆管理研究决定压缩和召回的时机。

### 为什么需要步骤级判断

从通用原理看，agent 的多步任务并不是每一步都同样复杂。若每一步都调用最强模型，成本会很高；若统一使用便宜模型，又可能在需要特定模态、工具或长上下文时失败。因此，调度的前提是先判断“这一步需要什么”，而不是只看模型价格。

Tier Sense 的定位正是面向 agent 的专用判断能力模型，而不是直接执行任务。它已经发布 V1 版本，材料中名称记作“书恒”（转写）。它的作用是为后续调度提供结构化信号：步骤难度、历史压缩候选，以及当前任务是否需要压缩或召回。

### Tier Sense 的三个判断面

Tier Sense 目前衡量三方面能力：

| 能力 | 回答的问题 | 输出 |
|---|---|---|
| score | 当前步骤有多难 | 由五个维度打分得到综合难度，总分 10 分 |
| compress | 历史中哪些步骤可以压缩 | 给出可压缩步骤及候选判断 |
| membrane decide（转写） | 当前任务要不要压缩、要不要召回历史 | 两项判断可以同时成立 |

其中 score 的计分方式是五个维度各 0 到 2 分，合计总分 10 分。按材料描述，可以理解为：

\[
S=\sum_{i=1}^{5} d_i,\quad d_i\in\{0,1,2\},\quad S\in[0,10]
\]

材料没有展开五个维度的具体名称，也没有给出 score 到具体模型档位或思考强度的映射阈值。因此这里能确定的是：Tier Sense 先给出一个 0 到 10 分的综合难度，再由 Tier Flow 结合其他约束决定调用哪个模型、用什么强度思考。

compress 关注的是历史步骤的可压缩性，并给出候选判断；membrane decide 则更像调用前的门控判断，同时决定当前任务是否需要压缩、是否需要召回历史。两项判断可以同时成立，说明压缩和召回不是互斥关系，而是可以并行考虑的两个动作。

性能和发布情况方面，报告给出：单次 API 请求只需 30 毫秒；约两周前发布，目前累计调用 30 万次；按次数计费，一次调用一厘钱。

### Tier Flow：把判断接入每一次调用

Tier Flow 是成本感知调度平台，目前有云端 API 和桌面端两个版本，桌面端支持 Windows。它负责把 Tier Sense 生成的判断接入每一次模型调用：每一步先判断需求，再检查能力约束，最后决定调用哪个模型、用什么强度思考。

这个顺序很关键。调度不是单纯比较模型价格，而是先看需求与硬约束，再在可用模型中做成本与能力权衡。决策环节包括三部分：

- **能力约束**：这是最重要的环节。不能只看模型成本；如果模型太便宜但不支持所需模态或工具，或者上下文不够长，就不能选它。例如，某一步需要读取图像，低成本文本模型即使价格更低也不能入选；某一步上下文超出窗口，同样要被排除。这是帮助理解机制的例子，不是会议实测。
- **记忆管理**：保留必要信息，去掉冗余，避免把不相关的历史继续带入后续调用。
- **历史反馈校准**：根据成本与失败记录给出调整边界和建议，使调度不是一次性规则，而是能参考过去的成本和失败情况做修正。

从机制上看，Tier Sense 给出“这一步有多难、历史是否可压缩、是否需要召回”的判断，Tier Flow 再把这些信号放进调用决策中。能力约束负责排除不可用模型，记忆管理负责控制上下文，历史反馈校准负责给出调整边界。

### 记忆管理：State Comp 与 Memory Control

记忆管理已有两项研究并已开源。第一项是 State Comp，研究历史什么时候可以压缩。它根据当前状态把历史分为“要保留的”和“已经具备压缩条件的”，再形成候选片段。也就是说，压缩时机来自状态判断，而不是随机定时触发。这使压缩更贴近当前任务进展：哪些历史仍然影响当前决策，就保留；哪些已经完成使命、可以被概括，就进入候选压缩范围。

第二项是 Memory Control，进一步研究行动前的状态表征。研究发现，行动前的状态中包含与压缩、召回有关的信号，因此可以结合近期状态和历史证据来提取记忆。换言之，是否压缩、是否召回，不只是看历史长度，还可以看 agent 在行动前的状态里是否出现了需要保留或调取信息的信号。

State Comp 实验中，报告给出的结果是：总 token 花费减少 52%，提取表征的加速提高 12 倍。

### 已披露信息能说明什么、不能说明什么

从已披露内容看，Tier Sense 与 Tier Flow 组合解决的是一条很具体的链路：在每次模型调用前，先判断步骤难度和上下文需求，再排除不满足模态、工具或上下文长度的模型，最后在可用模型中决定调用对象和思考强度；同时用状态驱动的压缩与召回管理历史，并用成本与失败记录校准后续决策。

目前材料没有给出五个维度的具体定义、score 与模型档位之间的阈值、模型清单、压缩与召回的质量指标，也没有给出判断准确率或失败模式的细节。因此可以确定的是这套机制和已披露的运营、实验数字：30 毫秒单次请求、30 万次累计调用、一次一厘钱、token 花费减少 52%、提取表征加速提高 12 倍；更细的泛化表现和可靠性仍需更多评测信息才能判断。

## 从成功轨迹到可复用技能：四项检验与可审查的表达

报告要解决的问题很具体：一次任务做成了，只说明这条轨迹是“证据”，不等于已经拥有了一项能重复使用的技能。从一条成功轨迹走到可复用技能，中间要经过四项检验。

第一项是**跨模态验证**，目的是排除偶然成功：同样的做法要在不同模态、不同材料条件下仍然成立。

第二项是**参数化**。轨迹里往往混着大量个性化内容，比如日期、文件字段。要把这些内容抽取出来变成参数，形成参数化例子，技能才不是只对某一份文件有效。

第三项是**明确契约**：输入是什么、输出是什么、按什么标准验收，必须写清楚。

第四项是**准入审查**：把候选技能放回已有任务中回放，通过才采纳。采纳并不代表结束——采纳后仍要继续观察，每个步骤保留版本，一旦不符合预期就回退到之前的版本。

这四项检验合起来，实际上把“成功”从一个时点事件变成了一条可持续验证的链条：先证明不是侥幸，再剥离个案细节，再写清接口，最后用历史任务做回放审查，并保留可回退的版本。

## 技能的表达：既要能执行，也要能审查

技能写成什么样，取决于它要同时服务两类读者：执行它的程序，和审查它的人。因此一条技能被拆成四个部分：**适用条件和输入输出、执行步骤、验收规则**。

以生成周报为例，可以概括为四步：

1. **读取并清洗**：从文件读进来，整理成表格；
2. **从表格汇总关键数字**；
3. **写稿和出图**：从数字生成报告；
4. **交付给用户**，由用户判断通过还是退回重写。

这四步之间存在严格的衔接要求：每一步的输入都要符合上一步输出的规范，才能进入下一步。围绕这种衔接，报告给出三条组合规则：输入输出衔接**依赖无环**、**版本固定**、**错误可移位**（后一条为转写，指错误可以在步骤间定位和移动）。整个技能以 `skill.md` 写下来，人和程序都能读懂——这既是执行载体，也是审查对象。

## 个性化：公共流程加用户偏好

同一个任务，公共流程往往相似，但每个用户的交互标准不同。周报这个例子里，三类用户的关注点完全不同：

| 用户 | 角色 | 关注点 |
| --- | --- | --- |
| 用户 A | 财务主管 | 按科目汇总、追踪差异 |
| 用户 B | 项目经理 | 风险、负责人下周计划 |
| 用户 C | 研究人员 | 文献引用是否规范、来源是否真实 |

所以个性化技能可以表示为“公共流程 + 用户偏好”。随之而来的是隐私约束：个人技能要与用户隔离，跨用户共享前需要脱敏。

技能也不是一次写好就永远正确，因为用户、需求、工具都在变。当新证据出现——某次失败被纠正，或用户提出新要求——系统会起草一个更新候选，**只列出改动，不直接生效**；候选经过任务回放和人工审查，通过后才决定采用还是回退。

## 两条使用路径与技能小模型

经过验收的技能有两条落地路径。一条是写入技能库，每次使用时通过外部检索调用；缺点是每次都要付出较大的检索计算量。另一条是把技能数据蒸馏到一个小模型上，减少对逐次技能提示的依赖；缺点是需要额外训练一个小模型。报告正在进行的是后一条。

技能小模型的训练目标是三件事：**选择步骤、调用工具、检查和修正产物**。为此设计了一套可放回的练习题。模型规模为 3B，采用 LoRA 监督微调，基座模型冻结。

## 对照实验：把“检验收益”和“训练收益”分开

验证要回答两个问题：小模型是否获得了足够的可迁移能力；以及重新训练小模型的投入与收益相比是否值得。更关键的方法论问题是——效果到底来自哪里。为此设置多组对照，把外部技能库带来的收益和训练带来的收益拆开：

| 组别 | 设置 | 想回答的问题 |
| --- | --- | --- |
| 3B 基座 | 看不到技能样本 | 底线水平 |
| 轨迹微调 | 只用历史执行记录训练 | 不用技能、只靠一般训练能提升多少 |
| 3B 技能训练 | 训练样本由技能编译而来，测试时不提供技能样本 | 若表现仍一样好，说明技能真的学进了模型 |
| 3B 技能检索 | 只做外部技能库检索，模型完全不动 | 外部技能库本身贡献多少 |
| 3B vs 14B | 对标大模型 | 质量持平时能省多少成本 |

其中“技能训练组测试时不提供技能样本”这一设计最能说明问题：如果模型在看不到技能提示的情况下仍能做好，才能说技能被内化，而不是被临时提示出来的。

## 沙箱评测：让 agent 看不见验收区

程序是否完成，不能靠自述，要放在沙箱里跑：每次先恢复任务的初始状态，再让智能体执行动作，结束后由独立检验器检验，最后记录证据和样本。

沙箱的关键是可见性切分。Agent 可见的只是其中一部分：任务指令、允许使用的工具、文档、表格、邮件的初始状态、每一步的动作和结果、错误和重试。独立验收区域对 agent 不可见，包括隐藏目标和预期结果、比对文件、外部状态，以及检查越界写入等。这样既能防止 agent 作弊，也能把失败追到具体是哪一步、哪个版本出了问题。

## 榜单结果与下一步评测

产品侧的目标是降低智能体使用大模型的成本、提高单位成本的智能；平台自国庆期间上线，目前有四万多用户，反馈不错。

公开榜单方面：

- **Word Cloze**：排名第五，任务完成率 57.7%，总费用约 3 美元，强调是榜单方案中成本最省的；
- 针对 Open Cloud 多阶段任务的评测（名称转写为 pinch punch）：完成率 91.6%，比 Cloud 高近 10 个百分点，总成本比 Cloud 省近 5 倍（按原话）。

下一步评测计划有三项：

- **Office Bench**：300 个办公任务，测跨应用完成率，以及每成功完成一单花多少钱；
- **更大规模 workbench**：690 个任务，观察技能能否迁移到新任务；
- **自建 office live 200**：200 道题的保留集，加 100 个顺序观察任务的数据集（转写在此处截断），用来验证“模型不动、只长技能”以及技能能否持续积累。

报告最后说明，3B 模型的后训练和长期演化任务仍在进行中——也就是说，上面这套对照设计与评测体系，正是为了在结果出来之前，先把“什么才算技能真的学进去了”这个判断标准立起来。

## 从无状态 Transformer 到记忆原生模型：MemOS 与经验迁移评估

报告把大模型的发展放在“状态从哪里来”这条线上看。它用 circuit complexity 的视角把 Transformer 描述为 TC0 电路：这类电路可由常数深度、多项式大小的阈值电路刻画，直观上擅长并行、常数步的组合计算。对应到模型能力上，Transformer 的单步推理强、泛化性强、并行度高，这正是它能够支撑当前大量应用的原因；但它的内部没有随步骤持续保存和更新的状态。作为背景，TC0 的类比不是在做严格的架构分类，而是帮助说明一个结构性局限：模型可以在一次前向中完成复杂组合，却不天然具备跨轮次、跨任务的长期记忆。于是“长期状态管理”成为后续一系列工作的核心问题。

### 三条补状态路线

报告给出的发展脉络，本质上是在不同位置补足状态：

- **2022 年 CoT**：Jason Wei 的论文只用一句 “Let's think step by step”，模型能力就有巨大提升。其逻辑是模型内部没有状态，需要提示模型一步步做，并把中间步骤记录下来，模型才能做得更好。也就是说，状态被写进了文本轨迹。
- **2024 年 O1 到 2025 年初 R1**：通过训练让模型记住长思维链，使模型学习内部状态。相比 CoT 把步骤放在外部文本里，这条路线试图把“怎么一步步想”内化到模型能力中。
- **今年的 harness 路线**：在模型外部外挂一套机制，告诉模型当前工作进行到哪一步、状态是什么、接下来应该怎么做。状态管理仍然发生在模型外，只是由外部系统更系统地组织。

这三条路线的共同点是：都在从外部补足状态。CoT 把中间步骤外化，O1/R1 把长思维链通过训练内化，harness 则把进度和状态放在模型外部管理。报告团队从成立起就追问：能否让这一切在模型内部发生，核心是把记忆做进模型内部。报告用“今天的 AI 会推理但不会成长”概括当前处境：模型要借助上下文管理、RAG、memory harness 等外部工具来运用外部状态；而 harness 或“脚手架”存在泛化能力和准确度问题，因此希望把记忆内化。

### 记忆原生：状态、推理与端到端

报告对“记忆原生”给出三个关键词，这三个词合起来才构成完整定义：

1. **状态原生**：管理记忆不再主要借助外部 harness，极少依赖 RAG 或 Memory Harness，让大部分状态或记忆过程在模型内部自发发生。这里不是说完全不用外部工具，而是外部工具从主要机制退为少量辅助。
2. **推理耦合**：记忆进入模型的过程只通过前向推理完成，而不是在应用中再微调、再反向传播才能把记忆写进去。也就是说，记忆写入应当成为推理过程的一部分，而不是额外的训练步骤。
3. **端到端处理**：从记忆抽取、组织、检索，到更新和遗忘，整个过程都由模型自发地做端到端优化；不是外挂一个更大的记忆库，而是训练一个会记、会改、会用的整体基座模型。

这个定义把“记忆”从检索库、提示工程或外部状态管理，提升为模型自身的能力。报告认为，Google Research 的 Titans 等工作，以及持续学习、记忆能力相关路线，正在共同汇向“让记忆成为模型生长的内生能力”。在更宏观的目标上，模型自身要有推理和决策，后面接执行和反思；改进成果要能保留并形成策略，服务于面向 RSI（递归自我改进）的关键基础能力。第一步是大幅提升任务连续性；第二步是让有效经验沉淀在模型中，而不是记录在模型外，改善后续表现；最终不仅沉淀经验，还让模型自发探索方法和策略，实现持续的能力增强。

### 从分层记忆到 MemOS

在记忆技术栈的演进上，团队 2023 年从分层记忆角度切入。当时业界几乎没有人提“记忆要分层处理”，他们训练了 2.4B 的分层记忆模型，超过当时 9B 的模型，并实现对显性记忆 1830 倍的压缩。这说明分层与压缩可以在较小参数下取得较好效果。但记忆原生模型的研发并不顺利，团队随后做了工程化产品 MemOS，可以理解为“记忆的 harness”。2025 年提出时业界还没有 harness 这一说法；现在 MemOS 已是国内调用量最大的记忆云服务平台之一，在 Agent Memory 和 User Memory 上都有较强能力，头部应用企业与其有紧密合作，产品包括开源、云服务和标准化产品。

MemOS 从去年推出以来已更新两代，MemOS 3.0 预计今年年底发布，核心是配合记忆原生模型，作为其运行时体系。这说明团队并没有把工程化产品与原生路线对立：MemOS 负责运行时和工程能力，原生模型负责把记忆能力内化。架构上整体设计迭代过很多次，这一版本才稍有一些技术本身的意味，并基本实现几个目标；架构中的 long memory 记录使用经验。

报告把核心问题表述为：在参数规模和训练固定的情况下，增加内部 storage 和模型参数模块能否带来更好效果。实验曲线显示，容量更大并不意味着经验会更有用，交互轮次更多也不意味着模型会持续变好；需要同时具备记忆容量、经验质量以及更新机制。换言之，记忆不是简单扩容，容量、经验质量和更新机制三者缺一不可。

### 记忆原生模型与两组实验

模型发布方面，团队在 10 月 20 日开源了其称为业界首个记忆原生大模型。目前已训练好 36B 和两百 B 级两个记忆原生模型并全量开源；更大规模模型在与英伟达团队研发，训练管线也在推进。报告还提到 288B 版本与国内外主流模型在代码等任务上的初步对比，但同时承认仍需增强复杂代码任务上的记忆能力。与业界主流 harness 工作对比时，报告承认仅靠记忆原生模型在最初任务上仍有距离，但差距已不像早期那么大，这也是团队继续推进这条路线的原因。

软件工程实验使用 36B 模型，取 500 个 SWE 相关任务，每个任务独立运行三次，比较无经验、文本经验、原生记忆三种方案：

- 平均成功率上，文本经验已经非常有效，记忆原生相对文本经验又有小幅提升；
- 更受关注的是“三次都成功”的比例，用于看执行稳定性：无经验为 54%，文本经验为 61.8%，原生记忆在此基础上进一步提升，但转写未给出具体数值。

报告强调，把记忆写入模型，是为了让复杂任务的重复使用成功率通过模型内化进一步提升，这个实验基本达到预期。另一组实验比较原生记忆轨迹与把记忆全量放入上下文：在 228k 和 256k 历史长度下，原生记忆方案的端到端速度分别是完整上下文方案的 1.86 倍和 3.99 倍，说明长历史下收益明显。报告最后仍把保留成功率或“保值度”的进一步提升列为待解决问题。

### 尚未闭合的评估问题

在报告与讨论衔接处，有两个相互关联的问题被提出：一是如何实现更好的经验迁移；二是如何建立更好的 benchmark，以便进一步测试，并通过 benchmark 把整个闭环带来的好处测量出来。材料中只保留了问题本身，没有给出具体方法、指标、实验设置或回答，因此只能确认讨论关注“经验迁移效果”和“用 benchmark 验证闭环收益”这两个评估难题。

从已有实验看，评测主要集中在单类 SWE 任务上的平均成功率、三次稳定成功率和长历史端到端速度。这些指标能够说明内化记忆在重复使用和效率上的收益，但还不足以回答经验能否迁移到新任务，以及整个记忆闭环是否产生了可归因的增益。经验迁移问的是“在一个任务上学到的经验能否用于新任务”；benchmark 则要能把记忆的抽取、组织、检索、更新、遗忘与后续表现连起来，测量闭环带来的好处，而不只是单点成功率。报告没有声称记忆原生模型已经全面取代外挂式 harness；它承认在最初任务上仍有距离，但认为差距已经缩小到值得继续推进。当前更准确的判断是：MemOS 提供了工程化的记忆运行时，记忆原生模型则试图把状态、推理和经验沉淀收进模型内部，而经验迁移与闭环评测仍是这条路线尚未闭合的部分。

## 从智能体记忆到个人数字分身：下半场的衔接点

下半场开始时，主持人先回到上半场的讨论线索：前面几位专家已经从不同角度分享了智能体记忆的技术进展。这里的“不同角度”说明，智能体记忆并非单点技术问题，而是涉及记忆如何表征、如何检索、如何更新，以及如何在端侧约束和实际应用中落地等多层议题。在此基础上，主持人提出了一个承接上半场、开启下半场的问题：这些记忆能力如何进一步帮助 AI 理解用户，逐步走向个人的数字分身。

这个问题把讨论重心从“记忆系统本身怎么做”推进到“记忆如何服务于对用户的理解”。作为背景，个人数字分身通常指能够持续理解用户偏好、经历和上下文的个人化智能体，记忆是其形成连续用户画像、跨时间提供服务的前提。但会议材料在本段没有给出“数字分身”的具体定义或技术路径，因此这里只能把它理解为报告要回应的方向，而不能据此补写实现方案。

随后，主持人介绍了联想集团研究院李辉研究员的报告，题目为“AI 全景驱动 Agent 走向数字分身”，副题涉及“从人类记忆机制的探索与实践”。从题目看，报告把 Agent 走向数字分身放在“AI 全景”的框架下，并以人类记忆机制作为探索与实践的参照。副题中的“人类记忆机制”与上半场的智能体记忆讨论形成呼应：前者提供类比和启发，后者对应工程实现。不过，材料没有展开报告具体采用了哪些人类记忆机制、如何映射到 Agent 架构，因此不能替报告补写机制细节；“AI 全景”作为标题用语，材料也未给出进一步定义，不宜过度展开。

嘉宾介绍给出的信息是：李辉现任联想集团研究院技术战略与平台主任研究员，长期从事多模态人工智能、智能理解及技术产业化；曾两次获得吴文俊人工智能科学技术进步二等奖，并在多个国际人工智能竞赛中取得优异成绩；其主导的技术已在联想超过两千万台设备上实现规模化部署和应用。这些背景表明，其工作兼具多模态智能理解研究与大规模产业化落地经验。对于“个人数字分身”这类需要理解用户、并在个人设备上持续服务的议题，这种背景与报告主题存在自然关联；但这只是从嘉宾介绍作出的背景判断，不是对报告内容的替代。

从现有材料看，这一环节完成的是议程衔接和嘉宾介绍，没有出现该报告的具体技术内容、架构、实验或结论。因此，关于“智能体记忆如何走向个人数字分身”，目前能确定的只是一个问题框架和报告主题线索：上半场讨论智能体记忆的技术进展，下半场由李辉从“AI 全景驱动 Agent 走向数字分身”的角度承接，并以人类记忆机制作为探索与实践的参照。报告正文中的具体方案与结果，材料尚未展开。
