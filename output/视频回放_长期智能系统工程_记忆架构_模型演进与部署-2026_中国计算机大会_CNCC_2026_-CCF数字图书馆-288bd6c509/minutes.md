# 智能始于记忆：从长程 Agent 到记忆原生模型与评测

本文围绕“记忆为何成为长程智能体的基础设施”展开：先说明 Agent 落地、范式迁移与认知基础，再讨论个人 Agent 的记忆生命周期、系统实现与模型原生路线，最后进入评测、环境记忆、基础设施与严肃决策场景。同一技术路线在不同报告中反复出现时合并展开，模型内化与应用外挂等不同路径分别讨论。

## 从长程 Agent 到记忆为中心的系统工程

这场报告把记忆放在“长期智能系统工程”的范围内讨论，而不只是某一篇论文或某一项研究。报告按偏理论、工程实践、记忆评测与部署演进三个层面展开，三层之间层层递进。贯穿其中的一个基本判断是：Agent 的持续落地，正在把记忆从附加功能推成基础能力。

### Agent 落地如何把记忆推到前台

报告首先给出 Agent 应用的现实图景。当前 Agent 领域有三个被明确称为“杀手级应用”的方向：coding agent、视频 agent 和办公 agent。在此之外，第四类被寄予期待的是 personal agent，也就是个人助理型 Agent；演讲中列举了一些个人助理型产品作为这一方向的代表。

从技术路线看，Agent 的演进可以概括为一条逐步与业务系统深连的路径：模型出现之后，先通过 tool 调用、function call、MCP 协议、skill 等方式连接外部工具和业务系统；面对复杂问题时做任务分解，产生 plan；再执行 action。当任务从短交互走向 long horizon 长程任务，问题性质就变了。一方面，不能所有事情都从零开始；另一方面，不能把用户的偏好、喜好和习惯每次都重新问一遍。企业 to B 侧同样如此，报告用“老师傅有经验”作比：好的流程、方法和经验需要被沉淀下来，而不是每来一个新任务就重新摸索。

这就使记忆成为长程 Agent 的基础能力。报告观察到，几乎所有基模厂商都在更新自己的记忆方案，同时探索新的 scaling law，即 memory scaling：记忆随使用自动生长、自动沉淀，并进入下一轮使用。这条线与 RSI（recursive self improvement）、self-evolving、Harness 等方向密切相关。

记忆形态本身也在演进。早期尤其是 GPT-4 阶段，记忆多是全局记忆，以 plain text 为主，用文本描述“我是谁”“我做过什么事”。后续出现应用商店、插件机制，记忆与更多应用集成；再往后则更强调面向 personal 的个性化。报告把记忆与个性化视为一条迭代主线：从 pretraining 到 posttraining，再到 memory scaling 和 AI for AI，目标是让能力增长的斜率更高。

在这个框架下，以记忆为中心要解决三类目标：

- **个性化**：底层基模可能相同，但用户不同会导致最终行为千差万别。报告用“养龙虾”作比喻——我养的龙虾和你养的是两个龙虾，我的不能直接给你，因为里面是我的偏好。
- **长期一致性**：报告提到中国算力 token 消耗中有一半在视频，尤其是 AI 短剧、慢剧。长剧里常见“一会儿变脸、一会儿服装变、一会儿人设变”的问题，需要记忆去约束。
- **可进化**：不能所有东西都出厂预置，否则系统不会演化。个人侧希望“越用越懂我”，企业侧希望把好经验、好流程、好方法沉淀并传承。

### 范式迁移：从无状态预测到以记忆为中心

报告用一条范式迁移线索解释为什么需要记忆。

早期机器学习系统是 stateless 的，主要做简单的单轮 prediction。没有状态带来一个严重后果：用户没有忠诚度——今天哪个模型好，用户就蜂拥而去。基模厂商因此必须思考如何留住用户。进入 Agent 后，用户的状态、行为习惯乃至数据会形成迁移成本，记忆由此成为留住用户和维持连续性的机制。

深度学习阶段扩展了感知边界，关注点转向统一表征和 representation learning：出现卷积、循环网络、LSTM 等多种结构，也出现各种注意力机制；核心是端到端学习，尽量避免手工 feature engineering。

预训练阶段则强调“在一次交互当中把事情说清楚”，大家持续卷 context，后来被概括为 context engineering 上下文工程。上一年的 CNCC tutorial 介绍过 agent RAG，即检索增强。检索增强其实已经带有记忆的影子，属于短期记忆或工作记忆（working memory），所有内容都放在 context window 里。但这种方式存在问题：context rot、上下文腐化、灾难性遗忘，以及在很长上下文中做“大海捞针”式检索的困难；还会遇到跨源、跨文档、跨设备的使用。从通用原理看，这些问题与注意力机制在长序列上的信息稀释、位置编码外推困难等背景有关，但报告的重点不在于逐项解释机制，而在于指出：只要仍然以 context window 为唯一承载，长期运行就会遇到结构性瓶颈。

报告把演进概括为：从以准确率为中心，到以表征为中心，再到以上下文为中心，最后进入 agentic 系统阶段后以记忆为中心。Agentic 系统强调持续进化，需要长期运行，从开发态走到运行态；记忆成为支撑持续进化的核心对象。这与前面三类需求一一对应：个性化让相同基模因用户不同而产生不同行为；长期一致性用记忆约束长内容、长任务中的前后变化；可进化则让系统在使用中不断沉淀个人偏好或企业经验。

### 记忆缺失的故障链与成本账

报告用“一团乱麻”描述记忆缺失时的系统状态，并拆出一条从内部机制到外部表现的故障链。

长期运行首先带来错误累积；其次是原来记住的东西不再记住，典型是偏好或记忆丢失；再次，长期之后信息被不断稀释，最终容易被忘却。这些内部问题会产生外部后果：前后响应不一致；行为发生漂移，原来是一种行为、之后变成另一种行为；信息混乱；以及成本上升。

成本问题被特别强调。报告引用 OpenRouter 的一份 report，称 Agent 失败尝试所消耗的 token 比成功尝试更高。这意味着 retry 本身可能是无用功，并且是成本的重要来源；长期运行中的各种检查和机制还会继续消耗 quota、额度以及 token plan。换句话说，记忆缺失不只是“答得不好”的质量问题，也会转化为实实在在的推理成本。

在记忆被明确作为研究对象和工程对象之前，业界并非没有做法。报告列出三类替代方案：第一，使用更长的上下文，百万级 token 上下文基本成为标配；第二，使用更强的模型，因为更大的模型容量可以记住更多内容；第三，使用更复杂的 RAG 机制，包括借鉴记忆，或者把记忆当作明文外挂知识库来做 RAG。这些方法很多时候“活得也挺好”，但仍希望更彻底地解决问题。报告还用 Google Trends 的关键词对比说明趋势：用 LLM memory 和 agent memory 两个关键词做搜索，将散点图做可视化和拟合；在 2024 年之后、也就是大模型和 GPT-4 出现之后，两者开始起量。

### 上限与下限：为什么记忆需要系统层面解决

报告最后把问题收束到 Agent 的上限与下限。一方面要“摸高”，探索到底能做到多好；另一方面真正落地还必须考虑下限。如果下限不合格，Agent 基本就没办法用起来，也就无法形成“更好的模型—更好的智能体”的闭环与相互增强。因此需要内外融合，在系统层面同时提升上界和下限。

这也是整场 tutorial 希望传递的整体视角：记忆不是单一模块的优化，而是长程 Agent 从开发态走向运行态时，支撑个性化、长期一致性和可进化能力的系统工程对象。报告随后从记忆这一具体问题展开更细的理论、工程与评测讨论。

## 记忆工程与上下文窗口：从提示、上下文到统一记忆管理

材料给出的一个总体判断是：到 2025 年，LLM memory 与 agent memory 的重合度会非常高。一方面，市场上已经出现专门的记忆框架和记忆解决方案；另一方面，基模厂商也在深入加入这一方向。记忆系统不再只是应用层的附加组件，而被视为基模长期进化的关键能力。Claude、Codex 等产品中已经能看到明显的记忆痕迹，而且这些产品对记忆相关机制持续改版、兼容新内容，说明记忆正在从“可有可无的增强项”变成产品能力的一部分。

在这个背景下，讲者把相关工作界定为“记忆工程”。他没有把记忆工程泛化为 harness 工程，因为 harness 能包含的内容太多，不是一个边界清楚的问题；相比之下，从 prompt 和 context 这条线看，记忆工程与提示工程、上下文工程是一脉相承的：从单轮提示，到动态拼接工作记忆，再到长短记忆调度，对应着提示工程、上下文工程、记忆工程。材料还提到，“记忆工程”这一提法最早是在院士指导下提出的。

### 从单轮提示到长短期记忆调度

提示工程主要处理单轮指令，往往是一次性注入，缺乏状态和积累。现在很多效果更依赖 system prompt 本身的质量，系统提示写得好不好、是否被公开或通过逆向工程被复现，都会影响最终使用质量。但提示工程的基本形态仍然是“把要求说清楚”，它不负责长期运行中的记忆沉淀和按需调用。

上下文工程向前走了一步。它会把记忆分模块，产生模板，把任务指令、角色定义、few shot 示例等内容组织进上下文。作为背景，few shot 指在上下文中给少量示例，让模型按示例完成当前任务；它确实更像短期工作记忆，而不是长期沉淀。材料认为，上下文工程的本质是模拟短期记忆：通过动态拼接，让模型在当前任务里“记得”刚刚给出的指令、示例和检索结果。

但长期运行时，问题会变得更复杂。系统既有短期记忆，也会有好的内容沉淀到长期记忆；真正执行某个任务时，还要从长期记忆里把相关信息取出来。因此需要对记忆进行系统性管理，这就是记忆工程要处理的事情。可以用下表概括三个阶段的差异：

| 阶段 | 主要处理对象 | 状态特征 | 典型手段 |
| --- | --- | --- | --- |
| 提示工程 | 单轮指令、system prompt | 一次性注入，缺乏状态积累 | 编写 prompt、系统提示；深度思考模型出现后更依赖 system prompt 质量 |
| 上下文工程 | 上下文窗口中的多模块内容 | 有模板和短期工作记忆，但长期运行仍需调度 | 任务指令、角色定义、few shot、历史/检索/工具返回建模、冻结系统提示、利用缓存 |
| 记忆工程 | 长短期记忆及多源记忆对象 | 选择性沉淀、按需获取、统一管理 | 统一接口、长短记忆调度、以记忆为中心管理不同类型记忆 |

### 长程 Agent 为什么需要动态认知

材料用“从大模型到智能体”的变化解释记忆为何重要：原来只“动嘴”，是静态对话；现在能“行动”，尤其是长程执行，需要动态认知。动态认知要完成四件事：第一，主动理解“你是谁”，每个人的偏好和行为不同，AI 眼镜等趋势会让这一点更重要；第二，知道“你过去做过什么”，但不是事事无巨细全部存储，而是选择性存储、选择性构建；第三，知道“你当前正在做什么”，也就是态势感知；第四，判断“未来可能需要什么”。

这里还出现了范式变化：大模型的基本范式是 predict next token，即预测下一个词元；在记忆与场景预测中，讲者把它转为 predict next scene，即预测下一个场景；此前 VLA 时代常讲 predict next action，即预测下一个动作。名称不同，核心都是系统要具备预测能力。能预测下一个场景，意味着从 reactive 的被动响应走向 proactive 的前瞻预判，可以预判用户可能需要什么并提前准备。材料总结说，在动态认知和长程多次迭代中，记忆的本质就是完成上述四件事。

### Token 消耗结构变化把上下文成本推到前台

所有交互方式都建立在模型能力提升之上，用户侧基本还是以 conversation 对话为基本形式。但 token 的消耗结构已经发生变化。材料给出的观察是，今年二月、六月时，agent 之间产生的 token 用量首次超过人类；到十月，约为人类用量的七倍。重点不是人类自己在消耗 token，而是 agent 自动调用 agent、自动执行各种任务，产生了更多 token 消耗。

与大模型交互时，人可理解的界面和接口基本就是上下文窗口。context 中通常放 system prompt、user prompt、对话历史、检索上下文以及工具返回；也可能返回 skill 等内容，而且随着 harness 范畴扩展，放入的内容会更多。上下文窗口因此不只是“聊天记录”，而是多种来源、多种生命周期内容的汇聚点。token 用量越大，上下文如何组织、哪些内容可复用、哪些内容需要压缩或缓存，就越直接影响成本和效率。

### 不同工程阶段优化什么，记忆工程统一什么

材料进一步区分了不同工程阶段的优化对象。

在 prompt 工程阶段，尤其是进入慢思考、深度思考阶段后，标志是 GPT 的 o1、o3 以及 DeepSeek 的“阿问”等思考模型出现，大家优化的内容基本上是系统提示。很多 harness 和 system prompt 会通过逆向工程或开源方式传出，这是保证最终使用质量的重要一件事。

到了 context 工程阶段，一个优化点是冻结系统提示，因为系统提示相对变化最小。从通用原理看，稳定前缀更容易被缓存复用，减少重复计算；材料也特别提到，要区分 token 是被缓存的 token，还是能启动的 token，如果 token 被缓存命中，价格和效率会高很多。context 工程还会对历史、来自数据库和外挂知识库的内容、工具库甚至技能库的返回做统一建模。

但在这个基础上，对话数据库、工具库、技能集仍然是被离散、单独管理的。记忆工程要做的，是给它们统一接口，形成统一的记忆管理。对用户来说，不应该关心底层这些分门别类的管理，而应把对象变成以记忆为中心。材料把记忆分成几类：人能看懂的明文记忆；来自 KV cache 或 hidden state 的激活记忆；以及可能人不能理解、或在 agent-to-agent 交互中出现的 parameter 参数化记忆。作为背景，KV cache 可以理解为模型在推理过程中复用已计算的中间状态，从而减少重复计算；材料把它对应的记忆形态归入激活记忆。

这样，记忆工程的任务就不只是“多存一点东西”，而是把上下文窗口中的 system prompt、用户输入、历史、检索结果、工具返回、skill，以及上下文窗口之外的对话数据库、工具库、技能集，收拢到统一接口和统一管理之下。它承接了提示工程对指令的重视，也承接了上下文工程对模块化拼接和成本控制的重视，但进一步要求系统能够区分短期与长期、选择性与全量、明文与激活/参数化记忆，并在长程运行中完成调度。

## 记忆的两条实现路径：模型内化与应用外挂

记忆工程落地时，首先要回答一个很实际的问题：记忆到底做在哪里。报告把实现手段归为两条路径：一条是在模型内部“长出记忆”，通过改架构、加模块、改训练策略，让记忆成为模型能力的一部分；另一条是在应用层外挂记忆系统，把模型当黑盒，用 prompt、agent 流和外部存储模拟记忆过程，让模型“显得有记忆”。报告强调，这两条路径不是非此即彼的对立项，而更像一个融合体：一个决定长期能力边界，一个负责快速落地和场景适配。

### 模型内化：让记忆成为模型能力的一部分

模型内化的基本思想，是在现有模型结构中增加记忆机制，或者直接设计记忆原生的新架构。具体做法可以落在不同位置：在 Transformer 基础上加记忆模块；如果模型采用 MoE，也就是混合专家结构，还要调整 MoE 中的内容；无论稠密模型还是稀疏模型，甚至在注意力层上，都可以增加记忆增强能力，最终目标是强化模型性能。

报告提到，这类工作从谷歌 2022 年提出 memorizing transformer 开始一直没有停止，后续不断出现新的尝试，材料还举到 MemOS 中的 Mantis 等记忆原生系统。这里的时间线只列到 2025 年，原因不是工作消失了，而是文章太多、追不完，重点是看趋势：记忆正在从外挂工具问题，逐步变成模型结构和训练问题。

内化路径嵌入的重点，不是简单地“记什么”，而是“什么值得记、记在哪儿、记的东西什么时候要用”这一类记忆能力和策略。也就是说，模型不仅要存下信息，还要学会判断信息价值、选择存放位置，并在需要时调用。实现手段相应包括新架构、新训练策略和建模策略。材料提到开源 MMT 的 loss function、基于轨迹的大规模数据，以及如何避免幻觉、如何做正则化等内容。其关注点是提升模型能力，让记忆成为模型内部的一种能力，而不是外部系统临时拼上去的功能。

### 应用外挂：把模型当黑盒，用系统模拟记忆

应用外挂路径适合很多做 agent 的团队：不需要动模型，把模型当黑盒，通过设计 prompt 或 agent 流来模拟整个记忆过程，增强模型能力，让它“显得有记忆”。这类系统管理的是交互信息和任务信息，关注点不是模型参数本身，而是系统的连续性和使用体验。

报告以 OpenCrawl 为例：其中会有多个 memory.md 一类 Markdown 文件，这些文件人能直接看明白，社区讨论也会围绕“我的 MD 又更新了什么”展开。它像思维导图一样可读，因此带来一种类似养小猫小狗的喜悦感和成就感。更重要的是，这类工具和框架可以替换各种模型，本身从来不动任何模型。

外挂系统会设计多种机制做模拟，甚至做 dreaming，也就是对记忆进行整理，形成 summary。整理层级可以从 session 级别到天级别，再到周级别、月级别，最后形成全局的 agents.md 或 memory.md 文件。这样一套机制不改变模型内部，却能在应用层维持连续性：哪些信息进入记忆、如何摘要、何时检索、如何组织成全局文件，都由外部系统完成。

外挂路径也有明显边界。它依赖底层模型，缺乏深层的学习能力。报告特别提到 harness 的作用：它不是从内部消解幻觉，而是在外部加围栏，控制幻觉的影响范围和模型行为。换句话说，外挂系统能让模型“显得有记忆”，也能约束使用方式，但不能替代模型内部对知识和记忆的深层建模。

### 两条路径的判断维度、成本与可扩展性

两条路径的目标和手段不同，不能只用“谁更先进”来判断。报告给出的对比如下：

| 比较维度 | 模型内化 | 应用外挂 |
| --- | --- | --- |
| 嵌入位置 | 模型内部，改架构或加记忆模块 | 应用层，模型当黑盒 |
| 核心问题 | 什么值得记、记在哪儿、何时要用 | 管理交互和任务信息，维持系统连续性 |
| 主要目标 | 提升模型能力 | 提升系统连续性和体验 |
| 实现手段 | 新架构、新训练策略、建模策略 | prompt、agent 流、外部文件和记忆系统 |
| 优势 | 参数化读取效率较高，能力可内化 | 落地快，可替换模型，场景适配灵活 |
| 局限 | 研发成本高，落地周期长 | 依赖底层模型，缺乏深层学习能力 |

成本差异很直观。内化路径需要改模型、做训练、调 loss、处理数据和正则化，报告形容研发投入是“白花花的银子直接花出去”，而且模型更新没有那么快，落地周期会比较长。应用路径则可以在现有模型上快速搭建系统，今天设计 prompt 和文件结构，明天就能在 agent 里跑起来。

但记忆不是只有读取。报告强调，记忆是读写密度都很高的事情，不是只有 read intensive，而是 read/write 都 intensive。参数化的好处是读取效率比较高；符号化路径现阶段写入效率很高：写数据库有 CRUD 各种操作，有索引，可以在毫秒甚至更低级别完成。相比之下，模型更新需要 training 过程，continual learning 和 online learning 现阶段还没有做到秒级别或实时。这就决定了两条路径各有擅长的环节：模型内化擅长把能力沉淀到参数和结构里，应用外挂擅长快速写入、检索和组织外部信息。

从可扩展性看，应用驱动通常广度优先，可以较快覆盖多种场景和工具；模型驱动通常深度优先，追求底层能力边界。二者结合时，系统既要有深度，又要有广度，不能只靠一层外挂包打天下，也不能只等模型更新而放弃当前可用性。

### 系统级融合：上限与下限的闭环

报告的核心判断是：内外不是对立过程，而要形成系统级的记忆一体化。智能体最后有了记忆，就对应到“记忆体”这样的系统形态；工程上还要做分层、调度和优化，特别是全局优化，兼顾开发与理论，最后落到系统级。

一个关键 take away 是：模型的长期主义决定整个系统的上限，模型上限高，类似于探索“能做到多好”的摸高；但 agent 落地还要考虑下限，如果下限不合格，就无法真正用起来，也就无法形成“更好的模型—更好的智能体”的闭环。因此，需要内外融合：模型内化提升上限，应用外挂提升下限和场景适配能力，再从系统层面把两者结合起来。

两条路径的关系可以这样理解：应用外挂让记忆系统先跑起来、先用起来，并在真实交互中暴露需求和问题；模型内化则把其中稳定的记忆能力、判断策略和调用方式逐步沉淀到底层。短期看，外挂路径更容易落地；长期看，内化路径决定能力边界。把二者做成融合体，而不是互相替代，才是报告对记忆实现路径的完整主张。

## 记忆的认知基础、时间尺度与工程第一性原理

讨论记忆工程，第一步不是选数据库或设计 prompt，而是先界定“记忆”指什么。记忆并不是一个统一概念：认知科学中的 memory 指人的记忆，计算机系统里的 memory 还常指内存或存储。两个词在英语中相同，含义却不同，容易造成概念混用。对计算机和工程背景的人来说，记忆问题并没有太多现成、直接可套用的“高大上”科学问题，因此需要从脑科学和神经科学中借鉴机制与分层思想。

### 认知科学中的五类记忆

认知科学对记忆的分类较多，容易让人“过载”，但这些分类分别刻画不同内容，不能混为一谈。

| 记忆类型 | 刻画内容 | 时间尺度与特征 |
|---|---|---|
| 语义记忆（semantic memory） | 事实 | 相对静态，例如概念、规则、常识 |
| 情境记忆（episodic memory） | 事件 | 事件驱动，会随时间动态变化 |
| 程序性记忆 | 流程与步骤 | 类似烧菜的第一步、第二步、第三步，带有程序性 |
| 感觉记忆（sensory memory） | 五官受到的刺激 | 毫秒级甚至更短；若延迟很久，就不需要感觉系统持续保留 |
| 工作记忆（working memory） | 在线维护和操作的信息 | 秒级到分钟级 |

这些分类给出的关键启发是：不同内容、不同时效的信息，需要不同机制处理。语义记忆偏静态事实，情境记忆偏动态事件，程序性记忆偏流程，感觉记忆极短，工作记忆则是在线“草稿纸”。

### 脑区基础：前额叶、海马体与新皮层

从脑区分布看，工作记忆主要与前额叶（prefrontal cortex）相关。前额叶沟和回较多，类似思考时使用的“草稿纸”：可以快速写入，但不是持久存储，会消失，讲者用 flash 作类比。长期记忆保存时间更长，最终存在于大脑皮层，尤其是新皮质中，并通过海马体进行处理和巩固。

可以把这一过程理解为一条记忆生命周期：

1. 前额叶皮层进行在线的维护和操作；
2. 信息编码进入海马体；
3. 海马体既有索引作用，也是巩固枢纽；
4. 通过系统巩固进入新皮层，在新皮层形成稳定的记忆表征和语义化。

海马体因此处在记忆流程的关键位置，既是“中转站”，也像“调度师”。老龄化与阿尔茨海默症/认知障碍的例子可以说明这一点：老人可能记不住刚吃过饭、刚见过谁，但以前的事还能记住。原因不是所有记忆同时消失，而是海马体损坏后，最新事件无法被处理和巩固；“草稿纸”被其他东西占满并擦去，所以近期事件记不住。这个例子支撑了从瞬时记忆到长期记忆的分层流程，也说明海马体在记忆巩固中的关键作用。

RAG 中有一个叫 HippoRAG 的系统，名字容易让人联想到海马体。它虽然与海马体没有直接关系，但取名背后有科学机理上的提示，也说明记忆的索引、巩固和检索机制会影响工程系统的设计语言。

### 映射到工程侧：短期、中期与长期记忆

脑科学中的分层流程可以映射到工程中的短期记忆、中期记忆和长期记忆。三者在更新频次、稳定性、写入成本和情境依赖上呈现明显差异。

**短期记忆**需要高频更新，因此更新频次高，但稳定性低；写入成本也相对低，因为要持续修改，如果写入成本很高就不合理。短期记忆有很强的情境依赖，很多时候就在某个 session 里面，内容更新快，也容易受到干扰。当前不少 prompt 投毒、后门劫持，以及已经延展到记忆的攻击，第一块要做的事情就是对短期记忆做安全评估，因为它很容易受到干扰。典型例子包括：钥匙放在哪儿、药盒在哪儿、刚刚放下的物体和物品、临时会议的细节，以及第一次听 memory 时遇到的新词。

**中期记忆**与短期记忆的区别在于突破 session 边界。它不再只属于某一次会话或某一次交互，而是和某一个任务相关。这样的任务可能在时间过程中重复出现，重复出现后会不断被强化，并从中形成一些共性和结构，因此中期记忆是有结构的。例子包括本月的目标与计划、考试准备内容、一次旅行安排等。

**长期记忆**相当于沉淀下去的内容，具有跨情境、结构稳定、可跨情境调用的特点，并且可以影响长期行为和决策。家庭住址不会经常换，至少不会明天就换；语言规则和基础知识可以通过预训练一劳永逸地放进模型里；长期技能和一些核心经验也属于长期记忆范畴。

从短期到长期，更新频次呈下降趋势，稳定性呈上升趋势。到了长期记忆，如果要修改，写入成本会非常高：一方面，长期记忆本身不希望是写优先，而应是读优先；另一方面，一旦写入，就希望它能被很长时间使用。因此，不能把三层记忆做成同一种存储，也不能只追求“记得多”。

### 记忆工程的第一性原理

从理论视角看，记忆工程可以归纳出几条第一性原理。

第一，人脑是分层结构，不同类型和时效性的记忆由不同机制处理。即使最终可以用多层类似神经网络的结构解决很多问题，网络里也会有注意力层、归一化层、前馈网络等不同模块；这些模块的组合可以映射到应对不同类型和时效的记忆。工程系统同样不能把所有记忆压成一层，而要按照时效、内容和用途分层。

第二，海马体处于“C 位”，整个记忆过程要考虑动态的生命周期。记忆不是静态条目，而是从编码、索引、巩固到稳定表征的过程，因此需要研究其工作机制，而不是只做写入和读取。

第三，记忆很多时候需要被主动遗忘、总结、提炼和巩固。“forgetting is learning”，忘记其实也是学习，而且是智能的一种表现。如果什么都不能忘记，就会变成数据库或日志系统，把所有东西都记下来，那就不叫记忆了。记忆工程因此不能只做“全量保存”，还要设计遗忘、压缩、总结和巩固。

第四，要探究记忆之间的关联和深度加工。记忆的核心在于激活和连接，从已知的东西推导出未知。真正自然的、AI 原生的或记忆原生的基模，需要把这件事做到模型里面，而不是只在外挂存储层做检索。

这些原则把记忆工程从“把所有东西存下来”拉回到更本质的问题：如何在正确的时间尺度上形成记忆、更新记忆、遗忘记忆，并在需要时通过激活与连接调用记忆。

## 个人 Agent 的记忆生命周期：判别、构建、检索与使用

个人 Agent 的记忆不应被理解为一个静态的向量库，它更像一条从输入到输出、并在使用中不断回流的过程。以 personal agent（PA）系统为例，底部输入是各类个人数据，顶部输出是各类应用；中间每一层都要回答几个连续问题：这条内容要不要记、记下来如何组织、增删改查如何管理、如何根据当前任务快速找到旧记忆，以及记忆如何与推理结合。记忆不是“存起来就结束”，而是在使用中触发新的检索、更新和再组织。

| 阶段 | 核心问题 | 主要矛盾与设计重点 |
|---|---|---|
| 判别 | 记不记 | 低信噪比下做高效判断，避免复杂机制本末倒置 |
| 构建 | 如何组织、写入 | 长对话信息密度低，召回优先，混合表示与个人 schema |
| 检索 | 找什么、找多少 | 事件粒度、查询粒度、线索与触发条件不一致 |
| 使用 | 如何与推理结合 | 多跳迭代读取，走向事件驱动的 agentic 记忆系统 |

### 判别：把“记不记”做成高效判断

记忆判别看似只是前置的小模块，实际是难点，而且带有悖论。讲者指出，如果用很复杂的机制来判断一条内容是否值得记，容易本末倒置：判别本身消耗了大量资源，但真正要回答的只是“记不记”。近期一些决策模型常把问题做成选择题、是非题或打分，对应“是不是要记”，而不是让模型自由生成一段记忆。大量内容可能百分之九十九都不需要记，因此判别必须足够高效。

难度的根源在于低信噪比。记忆判别面对的环境是大量噪声中夹杂少量信息，类似医疗诊断里的极度不平衡数据：大多数诊断结果是健康，少数才是得病。讲者从两个方向寻找理论支撑：认知角度有布罗德本特的过滤器模型，讨论数据过载、噪声以及场景动态变化下的适应性；信息论角度有信息瓶颈，即在低信噪比环境中保留真正有用的信息。

在机制上，有两个关键点。第一是门控：既然要判别，就需要一个“门”去选择通还是关，类似数字电路和许多网络模型中的门控机制。第二是缓解稀疏性：场景很稀疏，但系统并不需要先知道它属于什么领域，只需要判断是否值得记，因此要从差异化中“求同存异”，把记忆场景和“是否值得记”变成一些典型的高频 pattern，例如通过聚类找到共性。

工程约束同样明确。不能穷举所有内容，只能用少数规则和少数例子，类似 in-context learning 中的 few-shot 示例，或者用少数“宪法式”规则进行限制，而不是枚举所有规则。判别还要在不同场景下保持稳定，包括记忆场景平衡与不平衡、某个场景内数据平衡与不平衡、场景发生变化，以及数据太少时使用大量合成数据甚至自蒸馏数据的情况。它需要良好的可扩展性：随着 context 和 token 消耗变长，应该是线性扩展；如果是指数扩展，就不具备高效判别。由于它只是一个小模块，还需要插件化，能够插入现有记忆框架，并且不能显著增加资源、token 和计算开销。

### 构建：召回优先、混合索引与个人 schema

确定“这件事要记”之后，就进入记忆构建。长对话中真正有价值的信息密度很低，而记忆机制又不能显著增加资源、token 和计算开销。讲者特别强调，衡量记忆是否“抓住”信息时，核心指标不是准确率，而是召回：前面一旦漏掉，后面就完全错过，无法补救。同时，增加 token 或其他 cost 必须控制在可接受的 budget 内。

构建并不只有向量一种方式。大量内容仍通过明文或符号化方式完成，并且存在写入操作和键值对结构。不同索引方式适合不同需求：

- 如果记忆由实体及其周围属性触发，键值对是比较合适的方式。
- 如果使用 plain text 或原始数据，又希望快速、高吞吐检索，就会用到稠密 embedding 检索。
- 如果需要跨实体、跨对象，甚至做多跳因果判断，就需要图结构；图在路径和子图上的可解释性更强，复杂度有明确 bound，并且可扩展、可追溯。

讲者还提到运行时的写入问题：如果来不及把新内容回写到模型，就需要一种机制让内容可以瞬间写入，并像 real-time search 一样直接可用。HyperRAG 和 HyperRAG2 被作为稠密与稀疏结合的方案提及，其链路从 keywords 到 entity，再到 paragraph、document 和 discourse，用来集成单对象、单文档、多段落以及篇章级别的应用。

个人数据的记忆构建还有额外特殊性。数据来自各种设备、不同模态，并跨越 work 和 life 场景；例如开会听 tutorial 属于 work，会后与朋友讨论附近可吃可玩的地方属于 life。个人数据还包括亲朋好友等关系以及大量事件。因此需要制定可扩展的个人 schema，并构建数据集来支持模型训练。这类个人数据抽取不是纯生成式任务，而更接近决策模型，需要控制幻觉，并支持持续更新和迭代。讲者称这一层是在 artifact 层展开，包括邮件、短信、备忘录、图片、相册等来源。

对应要求包括：需要可更新、更全面、层次化、细粒度的 schema；需要针对属性、关系和事件，从不同来源做自适应抽取；很多内容要在端侧运行，因此要在小数据、小参数模型上达到较好效果；pipeline 可能较长，要避免数据在传递过程中被放大。

### 检索：检索什么、检索多少，以及粒度与线索

记忆检索和前面的构建方式一一对应。一方面可以基于 plain text：现在模型能力越来越强，可以把处理和理解过程后置，好处是能支持更多数据更新，尤其是流数据；否则容易产生不一致，尤其当数据存在大量级联更新时，问题会更多。另一方面是键值对、三元组以及图检索。

检索的核心问题可以概括为“检索什么”和“检索多少”，对应 what to retrieve 和 how much to retrieve。前者本质上类似前额叶和海马体之间的交互；后者与数据持续到来、持续构建有关，需要知道记忆的边界。边界并不好确定，因为事件粒度不同，事件中还会套子事件，事件也会演化；今天知道了新的 slot 后，记忆还会发生很多变更。因此存储粒度和查询粒度往往不一致。

回答一条请求需要不一样的线索。线索可能是时态类的，也可能来自单轮或多轮对话。如果没有针对性的模板和对应过程，效果会下降很多。不同请求需要的证据数据量也不一样；query 和 memory 在 RAG similarity 上会呈现不同 pattern，不同请求依赖不同的问题模板，请求与记忆之间也有不同的关联方式。

当关键要素发生变化时，就应该触发长期记忆的记录。不同类型的记忆任务有不同侧重：有些是召回优先，有些是准确优先，有些属于判断类型。系统只应消耗少量额外 token 来判断是否需要记忆，并提高召回线索的质量。讲者还提到，其方案可以在更小 token 开销下达到更好的 F1，抖动更小，对 token 消耗的依赖也更少。

### 使用：从一次检索到 agentic 记忆循环

记忆最终要进入使用环节。现在个人助理、量化交易等场景都会加入 memory；AI for finance 中的各种 trading agent 也在增加 memory。记忆使用会触发推理，尤其在多跳或多步执行任务中，过程不是单向的：系统先读取记忆，得到一些内容后触发推理，推理又发现需要额外的记忆内容，于是形成迭代读取、查询和更新的交替过程。

因此讲者认为，最终需要的是 agentic 的记忆系统。这样的系统符合现在 RSI 的要求，是自我驱动的，并具备类似人类的成长性记忆。记忆系统是多层的，从工作记忆到情境记忆，再到语义记忆：语义记忆相对稳定；工作记忆最临时、最可变；情境记忆是事件驱动的，事件变更会触发记忆构建。

在自我循环过程中，系统不需要用户每一次都告诉它要做什么，而只依赖首次指令，后面基本根据当前状态推进。讲者把 state 视为记忆中最核心的对象，整体做的是一个 state runtime，即状态运行时，不断更新当前内容，包括用户状态、环境状态、任务状态，甚至组织状态。这一运行时还包括多种记忆操作：识别和遗忘无效的短期内容，进行记忆修剪；把部分内容固化、转换；进行自我反思，动态评估记忆的价值，并重新构建对外的思维导图或明文记忆。

这样，记忆生命周期就不是一条单向流水线。判别决定入口质量，构建决定召回上限，检索决定旧记忆能否被当前任务调用，使用则把记忆变成推理的一部分，并反过来触发新的记忆需求。判别、构建、检索和使用之间持续回流，才构成个人 Agent 的记忆系统。

## 跨平台个人记忆与早期技术边界

浏览器里同时开很多 tab，在千问、DeepSeek、元宝、豆包等 AI 平台之间来回切换，是不少人的日常。麻烦在于，即使都用同一个 ID 登录，平台之间仍然不通：用户在 A 平台说过的偏好、在 B 平台留下的事实，到 C 平台又要从头讲一遍。统一账号并不等于统一记忆。跨平台个人记忆要解决的，正是把这些碎片构建成可携带、可调用的完整记忆。MemOS 的 MindDoc 插件是分享中给出的一个工程案例。

### 统一记忆资产：迁移、结构化与可追溯

MindDoc 的切入点很直接：安装后，讲者称可一键迁移用户在各 AI 中积累的历史记忆，自动获取用户在各大 AI 中形成的偏好和事实，并结构化整理为统一的记忆资产。它支持不同 AI 平台，统一存储、随时调用，让用户切换平台后仍能被“秒懂”。

分享中的例子是：用户在 ChatGPT 里说过自己不吃辣，在 Gemini 里有学校地址的历史；即使是第一次使用通义千问，系统也能自动补全这些背景，立刻给出合适的美食推荐。这里的关键不只是“把历史记录搬过来”，而是把偏好、事实整理成可在新平台调用的记忆。

用户还可以随时查看这些记忆。每条记忆以思维导图形式呈现，标明类型和来源，因而可以追溯，做到透明可控。从通用工程角度看，来源标注很重要：跨平台记忆要可信使用，至少需要知道一条偏好是用户明确说过的，还是系统从对话中推断出来的；否则用户很难判断该不该保留、修改或删除。分享还提到 MemCube 的 T value 机制（转写如此），用于支持类似离线记忆与实时同步的能力，但材料没有展开其内部实现。

### 偏好迁移与实体关联：Coco 的例子

另一个例子更能说明跨平台记忆不只是“复制粘贴”。用户在千问聊天中新增“养了一只叫 Coco 的小狗”这一事实，随即跳转 DeepSeek 询问 Coco 是否能吃巧克力。DeepSeek 立即获取“Coco 是一只小狗”的最新记忆，并给出正确回答。

这个例子说明两件事。第一，偏好和事实需要跨平台保持一致；第二，语义层可以做实体或指代关联——用户并没有重新告诉系统 Coco 原来是什么，系统也能找到已有记忆并用于新问题。后者比单纯迁移历史更进一步，因为它要求系统把新事实与已有实体关联起来，并在跨平台提问时调用。

讲者还判断，这类跨平台聚合更适合第三方来做，因为各大平台或系统不会把自己的系统开放给另一个平台，粘合和聚合作用需要第三方承担。这也解释了为什么插件或第三方记忆层有存在空间。

### 跨设备连续与任务接力

分享给出的第一个 case 是知识密集型专业人士的记忆沉淀与转移。行业工作人员会把投资报告分析的偏好形成一段记忆，在持续切换不同智能体、甚至在手机和 PC 等设备之间切换时，记忆不掉线且无缝衔接。流程上先形成一个可复用的框架，讲者把它类比为记忆的 summary；之后用微信的 Probot 手机端完成内容，回到家再切换到 Open Probot 继续做新任务。这对应长期一致性：用户不必在每个设备、每个工具里重新建立背景。

第二个 case 是任务接力。比如在 Codex 中执行任务，结果额度已经用完；如果安装了 MemOS 插件，里面有 CLI 和内置任务命令，可以用一条命令 resume，把刚刚的内容接续下去。这里产生了记忆的 checkpoint，即检查点。检查点可以在不同工具中衔接，例如在 Claude Code 中继续执行，并检查它是否记住了相关事项；记忆还可以快速关联，使整个过程形成数字孪生式的 system of records 来记录任务。

这说明记忆的范围不只是“记住用户是谁、喜欢什么”，还包括接住任务做到哪一步、在哪个工具里中断、下一步从哪里继续。对跨平台个人记忆来说，偏好记忆和任务状态记忆是两类不同但相互关联的资产。

### 仍处早期：多模态与端侧隐私

讲者把当前记忆技术概括为仍处于初步阶段：记忆几乎每一层都有大量事情没有做好，现阶段更像是在“挖坑”。其中一个关注点是多模态记忆，尤其是视频主导的记忆；另一个关注点是随着移动端设备增多，端侧如何做好隐私保护。

团队开源了 Mem Privacy 相关工具，并称已在部分手机使用场景中做到端云协同：云端只处理公共信息，端侧负责隐私信息的还原以及本地化推理；“什么算隐私”由用户自己决定。从通用原理看，端云协同的关键不是简单把数据留在本地，而是划分哪些信息可以上云、哪些必须在本地处理，并让用户掌握这条边界。分享中强调“由用户决定”，说明隐私边界不只是技术侧的静态分类，也涉及用户对个人信息的控制权。

多模态记忆同样被列为关注点，而不是已经成熟的能力。视频主导的记忆会带来更复杂的抽取、对齐和调用问题，材料没有给出具体实现细节，但把它放进了“早期技术边界”之中。

### 评测基准也要进化

记忆系统的更新依赖 benchmark 的进化。分享提到的方向包括：

- 更细粒度的 OpenMem，用于考察更细粒度的记忆能力；
- 面向记忆原生算子和操作层面的 MemOps，关注记忆在操作层面的表现；
- 用户偏好与个性化回复，考察系统是否真正按用户偏好作答；
- 记忆过程中的幻觉判别，尤其是“无中生有”和“张冠李戴”；
- 端到端基准，以及早期 LoCoMo 等基准方向。

这些方向对应不同层面的问题。传统问答评测往往只看最后答案对不对，而记忆系统还要考察事实抽取、存储、检索、操作、偏好遵循和来源一致性；如果记忆本身被错误构建，最后答案即使流畅也可能不可信。“无中生有”和“张冠李戴”正是记忆型幻觉的典型表现，因此需要单独的判别。

讲者最后把目标收束为三件事：token 量要减少、准确性要高、要越用越好。三者分别指向效率、正确性和持续适应性，也对应了当前记忆技术尚未同时做好的地方。跨平台记忆的案例展示了统一记忆资产和任务接力的价值，但隐私边界、多模态记忆和评测体系仍在早期，这些层面的共同进展决定了记忆系统能否从“能演示”走向“可长期依赖”。

## 记忆处理五阶段、共享风险与按读写效率分层

这条记忆技术路线并非一开始就做“记忆原生基模”。团队大约从 2023 年开始投入，最早做的是 agent 相关的 harness 工程与框架，随后进入模型层记忆，之后发布记忆原生计算模型/记忆原生基模。整体路径是从外围基础能力起步，逐步向模型内部靠齐。报告因此带有明显的工程实践视角：既讨论产品和交付中遇到的问题，也尝试从中提炼值得研究的技术问题。

### 从长程任务到记忆环路：为什么需要一层统一管理

在生态位上，大模型处在用户与底层基础设施之间。用户侧、基础设施侧都有大量信息、数据和内容在流通；模型调用 tools、MCP 工具时，调用需求和工具执行结果又会产生新的信息。另一方面，语言模型是“切片式”训练：每个模型版本的知识截止于预训练或后训练时灌入的内容，没有给到的内容大概率答不出来，或者即使答出来也容易产生幻觉。知识库、RAG、知识查询就是用来补充这部分信息的。

报告把这种补充也视为一种记忆，但它更偏静态、经过预处理：企业已有知识库和文档先被预处理、向量化，进入向量数据库，再通过检索进入当前大模型的 prompt/context，参与回答。它与后面讨论的、在持续交互中形成和更新的记忆并不是同一个层次。

应用形态的变化进一步放大了问题。过去更多是单会话、单轮、简单问答；现在可以把一个调研任务交给大模型，人离开去玩，希望一小时或半天后回来收结果。在这种长程、多轮、复杂任务中，动态信息、动态记忆、人与 agent 交互产生的记忆、agent 调用子 agent 形成的记忆都会越来越多，需要一层 harness 框架统一管理。

报告给出的记忆环路大致是：

1. 构建当前 context 时，做 prompt 优化和组装，并补充既定事实约束，交给当前模型推理；
2. 推理过程中产生 sub agent，调用子工具，并与现实世界环境交互，例如查询数据库，或在构造的虚拟环境中执行并观察结果；
3. 结果不符合预期时进入迭代循环，做子任务拆解和再调研，直到满足答案；
4. 当前推理完成后，选择性对结果做 summary 或记忆抽取，更新到记忆层；
5. 下一次构建任务 context 时，再从 memory set 中检索对应结果回到 prompt，形成闭环。

这个图看起来简单，但报告认为，当前很多研究和前沿工作基本都围绕其中某个节点展开。

### 五个基础阶段：抽取、组织、检索、更新、共享

团队从与合作方做业务交付的实践中，抽象出记忆处理的五个基础阶段：**记忆抽取、记忆组织、记忆检索、记忆更新、记忆共享**。递进逻辑是先识别“是什么”，再考虑如何组织存储，使用时如何检索，之后才是更新和共享。

如果只看明文记忆，**抽取、组织、检索**会和现有 RAG 技术栈非常相似；**更新和共享**更能体现记忆相对于 RAG 的独特性。RAG 主要面向已有、固定的知识和文档，以较高效率做知识填充和补充；记忆则持续性强、场景性强。个人普通场景、游戏场景、医疗对话场景需要记住的内容可能完全不同，因此不能像普通 RAG 那样只按切片、语义块或事件来拆分，必须先判断不同场景中哪些事实值得被抽取和记住。

**组织**层面，可以有向量数据库式的切片、打散和向量化存储，也可以有 Graph RAG 这类用较精确的实体和链接关系做图存储的方案，还可以做类似人的脑图式知识图谱组装。但报告提出一个限制：模型本身已经具备世界知识和理解能力时，不一定需要再用非常准确的知识图谱增加模型处理负担和额外开销。**检索**则是一个很大的领域，原有大量文本检索方案都可以在记忆检索中寻找适合场景并适配。

**更新**阶段的工程要求较高，涉及整套记忆版本化管理。报告举了一个会议时间变更的例子：原先预定十点的会议，过一两天后时间发生改变，记忆系统必须准确识别当前对话涉及的是之前哪一段记忆、之前记录的记忆点是什么，并能有效管理两个版本，未来使用时准确抓到所需版本。

**共享**可拆成两个典型场景。面向个人用户时，一个人会使用不同 agent、不同 AI 软件，需要让这些软件之间共享记忆，降低跨 agent 协同成本；共享时不必把此前所有历史对话上下文完整塞给另一个 agent，只需使用当前上下文或当前任务相关记忆。面向组织时，报告举了一家大型制药企业的例子：研发工程师每天使用 AI 产品，会形成大量研发过程性信息。过去像写论文一样，主要记录最终结果；拿到最终配方之前的实验过程、实验决策和争论过程并没有被记录。企业希望把研发过程中的思考、逻辑和探索记录下来，形成组织公共经验。例如在美白功效研发中，增加某个成分后验证确实带来美白效果，这段探索过程可以被同类药品或保健品研发参考，降低另一个新产品研发的思考和迭代成本。因此，不同研发工程师之间的记忆需要共享，但这会涉及隐私保护、哪些员工讨论的记忆可以共享、共享正确性如何保障、不同组织之间的记忆授权如何保障等问题。

### 共享记忆的风险与抽取、更新阶段的记忆幻觉

组织共享记忆除了隐私、授权和共享正确性，还会带来**记忆投毒**风险。这是报告特别指出的研究点：共享范围越大、记忆越被当作公共经验复用，错误或恶意信息的影响面也可能越大。

另一个更普遍的问题是，**记忆抽取和记忆更新非常容易发生记忆幻觉**。抽取时，很多信息甚至没有经过人的确认，就会被大模型抽取成“实际发生过的信息”。报告的例子是：用户问“今天成都有哪些好玩的”，模型推荐了一堆成都景点，最后可能被抽取成一条记忆——“用户在成都去玩过这些地方”。但用户实际上并没有去过，只是问了大模型有哪些好玩的。

更新阶段同样如此：需要把过去的历史信息和既有记忆拉回来，与当前从库里检索到的记忆实体、节点做匹配，再做二次更新和校验，这一过程也会出现同类问题。

因此，报告认为要较好解决抽取和更新问题，方式可能是针对现在的模型重新训练；不必从预训练或 middle 训练重来，至少要从后训练开始，对记忆处理的思路重新校正，而不是像很多 agent 框架那样只调用通用模型、只调 prompt。报告的经验是，仅靠调 prompt 解决不了，幻觉控制效率到某个水平就上不去了。

这对应两个个性化挑战：一是模型如何让记忆准确形成；二是在持续学习时，如何保证整个记忆系统能够被准确更新。报告还判断，从记忆技术研发的历史看，未来百分之七八十甚至八九十的记忆可能会被内化到模型参数空间里，尤其是组织公共记忆，内化后能形成非常高的读取效率。再往上则是低幻觉问题：无论共享、更新还是抽取，都要控制幻觉发生。团队称推出了业内第一个针对记忆幻觉的评估框架，并提到框架推出后相关数据增长较快。

### 按读写效率分层：参数化记忆、激活记忆与明文记忆

团队公开的第一版记忆系统框架分为三层：最底层是存储和治理层，往上是记忆调度层，再往上是对外提供服务/CLI 等形态。报告特别强调，早期提出这个框架时就把“治理”放在非常重要的位置；框架发布后，记忆治理方面也出现了很多文章和研究点。

这套框架与许多现有记忆系统的一个本质不同，是认为记忆应当分层管理。常见分层是长期记忆、短期记忆、working memory，而这里的分层角度是**记忆读和写的效率**：读取效率高、写入效率低的是一类，读取效率低、写入效率高的又是一类，此外还有中间类型。对应为参数化记忆、激活记忆、明文记忆。

| 记忆类型 | 写入效率 | 读取效率 | 主要形态与代价 |
|---|---|---|---|
| 参数化记忆 | 极低，成本极高 | 很高 | 写入通常依赖预训练；训练完成后可由当前 prompt 激活并取出记忆 |
| 明文记忆 | 很高，改几个字再写回数据库即可 | 较低 | 取出一段文字不等于完成读取，还要组装进新 context，走完 prefill、decoding |
| 激活记忆 | 介于两者之间 | 介于两者之间 | 可理解为明文记忆经过一次 prefill 和 decoding 形成的 KV cache，可预测和复用 |

**参数化记忆**的写入成本非常高。对现在的模型而言，写入参数化记忆通常只能通过预训练；报告认为后训练主要用于对齐，模型本身并不容易靠后训练记住东西。几十 B 的模型已经难做，扩展到几百 B、动辄两三个 T 的开源模型更难以承担。但一旦完成高效写入，读取成本会非常低：完全训练进去之后，模型能根据当前 prompt 激活，并从参数中拿到之前的记忆。

**明文记忆**与参数化记忆形成对照，写入效率非常高，这也是绝大多数团队或大模型刚开始做记忆时选择明文记忆的原因：从数据库里把一段明文记忆摘回来，改两个字再塞回数据库，就完成了写入，速度可以很快，很多数据库支持的并发和效率也已经很高。但它的读取效率可能不高。报告强调，“把一段文字从输出里拿出来”并不意味着它已经被读取；它还要组装成新的 prompt、新的 context，再放进模型推理流，走完 prefill、decoding 的完整过程，直到输出结果，才能称为完整的读取过程。如果 context 很多，且未来被使用频率很高，每次都要走完整过程；虽然有 KV cache 等缓存化管理手段能降低部分成本，但本质上仍要走完这个过程。报告用早期问模型“今天星期几”或“今天天气怎么样”也可能消耗两三块钱作例子，说明大量无关上下文进入且复用效率不高时，读取成本会很高。

**激活记忆**是中间状态，某种意义上就是明文记忆经过模型一次 prefill 加 decoding 过程形成的 KV cache。如果能良好预测和复用这部分 KV cache，就能降低一部分原本属于明文记忆的读取成本；它的读取和写入成本因此处在参数化记忆与明文记忆之间。

既然存在这样的效率差别，调度系统就能体现优势。比如今天突然发生一条新闻，近期可能被大家广泛、高频地问到，就可以把这部分内容适当往激活记忆里调；通过激活记忆的管理和调度，使针对这个问题的缓存命中率或激活记忆命中率在近期保持较高水平。再进一步，如果某个东西已经成为大家公认的事实，或者在将来会被非常高频地使用，就有动机和动力把这部分记忆再写到参数化记忆里。由此形成一套针对不同场景、不同记忆使用频率的调度体系，使面向这些场景的整体读写效率达到最优。

这套拆法的重點不只是把记忆分成三类，而是把**写入成本、读取成本、复用频率和场景预测**放在同一个调度问题里：五阶段界定了记忆从形成到共享的处理链路，共享与幻觉揭示了链路中的风险，按读写效率分层则给出了为什么需要调度、以及调度可以在哪些层次之间迁移记忆。

## 记忆调度工程与图式组织

记忆系统的一个关键工程矛盾是：如果等用户真正要用的那一刻，才去完成记忆检索、准备和召回整条链路，时延会很高。报告把这个问题放在调度层解决，并把调度工程拆成触发、管理和执行三层。

### 把准备工作提前：调度触发层

调度触发层的目标不是替代真实查询，而是不要让系统一直被动等到“要用时才查”。系统提供调度触发的操作和算子，允许用户自定义触发调度行为的 trigger。也就是说，什么时候提前准备、提前准备哪一部分记忆，可以按场景配置，而不是固定成一条规则。

报告给出的典型例子是用户输入 prompt 的过程：当用户输入到一半时，系统预测用户完整输入的 query 是什么，并提前做一部分记忆准备工作；等用户真正完成 query 输入后，再用真实输入去召回和补充。由于预测版本与真实输入所召回的信息可能匹配度很高，后续补充就可以用更高效的方案完成。这样既在时间上有所保障，也在效率上有所保障。这个例子说明触发层的价值在于“提前量”：类似提前预热，但这里预热的对象是记忆准备和召回链路。报告也强调，实际系统可以面向自己的场景做各种主动性的准备，预测 query 只是其中一种。

### 管理层与执行层：从触发到落地

触发之后，还需要管理和执行。调度管理层包括记忆自身生命周期的管理、调度编排系统的管理、调度队列的管理等；再往下是调度执行层，涉及异步队列、负载均衡、分布式优化预测等偏系统执行和工程化的内容。

这三层形成分工：触发层决定“何时提前做、提前做什么”，管理层负责记忆生命周期、编排和队列，执行层则用异步、负载均衡和分布式手段把任务真正跑起来。报告没有把调度层描述成单一算法，而是把它作为记忆系统中的工程化基础设施来处理。

### 为什么采用图式而非高精图谱

在记忆的组织形态上，报告认为“脑图”式组织是一种较好的形式。报告提到，Graph RAG 在 2025 年前后非常火，也有大量派生工作围绕它展开。作为背景，Graph RAG 大体是把检索到的知识以图结构组织起来再供生成使用，以便利用片段之间的关系；但报告关注的是记忆层如何工程化地组织这些关系。

团队的背景影响了这一判断。团队来自阿里巴巴业务中台数据智能团队，曾构建整个阿里巴巴的商业知识图谱，即商品、商家、会员的知识图谱。其中商品知识图谱挑战很大：商品数量非常多，信息非常杂，要把商品以较好的知识图谱形态组织起来、构建起来，需要非常大的努力。大模型出现后，也有知识图谱与大模型互相增强的方式，例如基于大模型增强知识图谱，或基于知识图谱反向增强大模型。

但从偏工程化、偏应用的算法角度看，报告认为可以采取折中状态：大模型本身已经具备较好的理解和推理能力，是否还需要构建非常高精、具有实体和关系链接边的推理逻辑结构？至少在记忆这一层，从当时的结果看，依赖模型本身的推理已经能做好许多事情。因此他们构建的是一种折中的图式逻辑结构：让边与边之间、实体与实体之间保持一定的逻辑关系和组织能力，但不需要像图那样构建非常准确的逻辑结构，从而避免过度增加模型处理负担。这里面也涉及从抽取到构建图、构建关系边的一系列算法方案；这些方案在业务上线后，也有对应的学术研究成果发表。

### 开源与版本演进

这套系统从第一天起就是开源的，报告提到 GitHub 上的开源框架目前大约有 12K、一万两千多 star。第一版之后还会持续做 3.0 版本；报告说明，需要配合记忆原生基模的一套记忆框架，才能取得最好的性能。2.0 版本的具体架构没有在这次材料中展开。整体来看，调度层解决“提前准备”的时延问题，图式组织则试图在模型已有推理能力的前提下，用不过度精确的关系结构承载记忆组织，这两条线共同构成了报告所说的记忆工程化方案。

## 运行态记忆中枢、状态管理与版本化分支

报告把记忆系统的演进放在 Agent 能力变化的背景下讨论。2024—2025 年间，行业关注点更多集中在模型自身能力优化上，尤其是推理、数学等题目；当时 Agent 还不成熟，多 Agent 任务所依赖的 harness 工程和配套工具体系也不成熟。因此，记忆讨论多集中在单轮任务或单个会话内，重点是把一次交互中的内容和上下文管理好。

到 2025 年之后，模型自身的 Agent 能力明显增强，能够在较长周期或较复杂的问题中取得较好结果，coding 任务上的突破尤其受到关注。这直接提高了对记忆系统的要求：过去是围绕记忆本身做调度，追求特定场景下读写效率最优；现在则要求整个记忆系统承担长期状态管理，成为长期可进化的框架和体系。记忆系统不再只是“使用时查相关信息、组装成新 prompt 再交给模型”的被动组件，而要转向“7×24 小时 ready”的运行态中枢。

从通用软件系统的角度看，运行态意味着系统不只在请求到来时被调用，而是持续维护和更新状态。报告所说的运行态记忆中枢，正是要随时管控用户状态、任务状态、环境状态、经验状态和组织状态；状态与状态之间的变化，通常通过记忆状态的版本化管理来实现。报告把 1.0 总结为“让记忆可管理、可调度”，2.0 的目标则是让记忆系统随时可用，并在使用过程中形成模型记忆能力和经验的进化。

| 维度 | 1.0 的关注点 | 2.0 的要求 |
| --- | --- | --- |
| 核心目标 | 记忆可管理、可调度 | 随时可用，并在使用中持续进化 |
| 系统形态 | 使用时检索信息、组装新 prompt | 7×24 小时 ready 的运行态中枢 |
| 管理对象 | 主要是人跟 Agent 对话形成的记忆 | 增加 Agent 与 Agent、子 Agent 与主 Agent 之间的记忆，以及行为记忆、环境反馈记忆 |
| 优化重点 | 特定场景下的读写效率 | 长期状态管理、长期可进化的框架和体系 |

管理主体也发生了变化。1.0 更关注人跟 Agent 对话形成的记忆，例如日常客服对话、游戏中人与 NPC 对话形成的记忆管理及体系化。2.0 要解决更复杂的任务，因此还要处理 Agent 与 Agent 之间、子 Agent 与主 Agent 之间的记忆管理；除主体对话记忆外，主体行为记忆、主体与环境反馈形成的记忆也需要被系统化管理起来。

围绕运行态记忆管理，报告将其概括为四件事：

- **感知记忆状态**：不同主体的状态应如何定义，不同场景下状态是否需要重新定义。
- **状态判定**：不同记忆何时需要更新，需要判定逻辑；更新之后不同版本之间如何切换，也需要切换逻辑。
- **状态调度**：面向运行态的整个生命周期如何执行，面向不同场景、不同环境时频率如何设置。
- **状态进化**：对应 RSI 技术路线中一条重要方向——基于明文的 RSI，即从明文角度总结不同经验，让不同经验的 Agent 之间形成协同和共享，实现持续经验积累和进化。

在记忆持续性管理过程中，还会涉及不同版本之间的迭代，例如用户偏好变化、任务目标更新，甚至拉出不同分支。报告提到的分支包括会话分支、增强分支和任务分支。其例子是 ChatGPT 的分支对话功能：用户在主的对话流中聊到后面，发现前面不对，可以拉起一个分支，再进入该分支进一步沟通。此时分支里的对话大概率看不到后面的 memory 内容，这就会产生所谓的“记忆穿越”问题——分支处在一个较早的上下文位置，而主对话后续形成的记忆不会自然出现在该分支里；如果记忆系统仍按全局最新状态供给，分支时间线与记忆版本就会不一致。

因此，记忆系统也需要具备任务分支管理、会话分支管理和增强分支管理能力。既然有分支和管理，就会涉及记忆合并、历史老旧记忆淘汰机制以及记忆沉淀。报告表示，这些能力都期望通过版本化管理来实现。为此，当时设计了一套 memory 的 react 框架，本质上希望通过分支验证和管理机制，快速实现记忆版本化管理的功能。这样，记忆系统就不只是保存和检索内容，而是把用户偏好、任务目标、会话演进和 Agent 经验都纳入可管理、可切换、可分支验证的长期状态框架中。

## 模型层记忆的动因：版本知识落差、一立方与企业落地成本

报告先交代了一条清晰的时间线：团队一直到 2025 年年中之前，主要在做完整的记忆系统；之后把重心调整到“记忆原生”的模型层。这个转向不只是研究方向的切换，背后是两个现实问题：模型发版越来越快，但版本之间的知识落差仍然存在；记忆如果只作为模型外部的系统工程，企业适配成本会很高。于是问题变成：能不能让记忆进入模型的计算与学习过程，降低持续学习成本。

### 发版提速，为什么仍有“版本知识落差”

模型侧最明显的变化是发版节奏。2025 年之前，模型可能三个月发一个版本，更早甚至六个月一个版本；现在一些大厂一个月发一个版本，更激进的可能一到两周就发一个版本。

但发版快，并不意味着知识更新问题自动消失。报告指出，版本和版本之间仍存在明显的“版本知识落差”。核心原因是时间一直在演进，而模型从训练到发版之间存在时间差；即使加快后续流程，发出来的版本之外仍然有时间差。这种落差会导致事实性问题，也包括幻觉性问题。

补知识当然有路径：可以通过后训练，或者预训练加后训练，把新知识补进去。但报告强调，这并不是每个公司、每个团队都有能力做的事。面对开源模型，并非每个团队都训得动；而且后训练出来的模型，也未必能在自己的场景中获得正向收益。因此需要一种更高效的继续训练或持续学习方式，让模型补足这部分能力。这正是记忆原生模型层要回应的直接动因。

### 读写成本：记忆不是“有或没有”，而是“怎么写、读多少次”

报告还给出了衡量记忆读写成本的方式，大致可以写成：

\[
C \approx C_{\text{单次写入}} + N_{\text{使用次数}} \times C_{\text{单次读取}}
\]

对大规模模型而言，参数化写入的成本非常高，但写入之后读取效率会比较高；在多次复用的情况下，单次使用分摊的成本会下降。明文检索则相反：写入成本较低，但读取成本较高。

因此，讨论记忆不能只看“有没有存下来”，还要看单次写入有多贵、会被使用多少次、每次读取有多贵。报告希望通过架构层面的改进，让模型跟上世界的发展，真正实现一定意义上的持续可学习。

### “一立方”：让记忆进入模型的推理计算流

报告介绍了团队 2023 年年底开始训练、2024 年发布的“一立方”工作。报告称，这项工作首次向业界证明：不同类型的记忆可以参与模型整个推理过程，或者参与模型整个计算流，而不只是作为外部检索存在。

具体做法是把 Transformer 的层区分为两类知识：一类是抽象知识，即日常理解中比较固定的 pattern 性内容；另一类是具体知识，例如某个具体数值、今天的天气、某个人物对应的父母或孩子叫什么等细节性知识。通过这些句子层面的拆分，可以把记忆从不同层次拆成隐性记忆、显性记忆和外部记忆。

| 记忆类型 | 报告中的类比 | 在模型中的使用方式 |
|---|---|---|
| 隐性记忆 | 学会骑自行车后，踏上自行车自然往前蹬，不再主动回想怎么骑 | 已经内化的表达和能力，使用时比较自然 |
| 显性记忆 | 在意 GPA 的学生即使开卷，也会提前翻书，把关键知识形成线索和记忆编码 | 高频内容提前预编码，放入显性记忆库，使用时快速取出 |
| 外部记忆 | 开卷考试时现场翻书，找到知识点位置，再组装回来作答 | 现场查找外部知识，再参与推理和生成 |

报告用“学骑自行车”解释显性记忆内化为隐性记忆：刚学时要想着怎么骑，学会之后就不再主动回想，表达会非常自然。用“开卷考试”解释外部记忆：考试时现场翻书，找到问题对应的知识点位置，把知识组装回来再进行推理和作答。用“GPA 学生提前翻书”解释显性记忆：即使开卷，也会提前把书翻一遍，把关键知识形成线索和记忆编码，真正考试时能更快找到考点，形成答案的效率更高。对应到模型，报告把这一过程与 self-attention 已有的计算过程作类比。

在工程上，可以把高频知识和内容提前做预编码，放进显性记忆库；使用时从巨量显性记忆库的缓存中取出已经预编码的信息，与当前推理流联合，例如放到推理队列最前面，一起进行联合推理和生成。这样模型就能以某种形态参考之前理解过的内容和“书”，再响应当前回答。

报告还把这一思路与 DeepSeek 的 ngram 工作、Qwen 把 ngram 用到其 next 框架中的工作作了类比，但指出一个不同点：一立方除了在预训练时做预编码，在推理时也可以根据当前信息做编码，然后放进库里调用；而 ngram 在预训练做完之后，后面大概不会太变。

### 企业落地：真正贵的是每个行业重训“怎么用显性记忆”

“一立方”证明了记忆参与模型计算流的可行性，但报告也坦言，真正想把它推给企业使用时遇到了很多难点。一个重要问题是：要把模型用到不同企业、不同行业，必须针对该行业、该企业重新训练显性记忆的使用过程。换句话说，不同行业对显性记忆的调用和使用方式不一样，这会导致成本变得很高。

因此，现在记忆原生方向的一个想法或要求是：尽可能不再做训练这件事，或者尽可能降低把模型部署到企业之后做持续学习的成本。

报告进一步说明了记忆原生要补的 gap：现在大多数模型仍处于无状态状态，需要通过 context 管理、RAG、memory 系统等一系列外部 harness 工程来保障能力。但团队希望模型在完成大版本训练之后，依然能在长期时间内进行性能和能力的增强。

从这个角度看，从完整记忆系统转向记忆原生模型层，核心动因不是否定外部记忆系统，而是外部 harness 难以消化版本知识落差和企业适配成本。一立方证明了不同类型的记忆可以进入模型的推理计算流；企业落地又暴露出“每个行业都要重训显性记忆使用方式”的成本问题。记忆原生要解决的，正是让模型在大版本训练之后仍能长期增强能力，并尽可能降低部署到企业后的持续学习成本。

## 记忆原生模型：状态原生、推理耦合与三项能力

讲者从人的成长切入：同一批人毕业时基础相近，后续能力差异很大，除了“出厂规模”，很大一部分来自工作中学习能力的内化差异。对应到模型，预训练负责学习世界基础知识、补齐基础能力；后训练负责推理和对齐，让模型按期望形态输出，并在复杂问题上具备思考能力。再往后，讲者认为需要寻找的是 **memory training，即记忆的 scaling 曲线**。此前行业主要推的是推理 scaling 曲线，但继续推进无论对大厂还是小研究团队都很费劲；从企业部署看，比较有突破性的方向是从记忆角度，把实践中形成的经验和知识内化到模型参数空间。

### 什么算“记忆原生模型”

讲者提出，至少有三个关键词需要澄清：

1. **状态原生**：记忆不再以明文状态或明文形式管理。如果仍然以明文管理，那还是一套 Agent 系统、一套外部 harness 工程。
2. **与模型推理耦合**：记住的内容不只是作为事实呈现，而要能影响模型推理过程，包括影响推理性能，以及影响模型对事实性内容的遵从情况。
3. **支持端到端优化**：不是单独为了把某些事实性知识训进去，而是整个记忆相关能力可以端到端训练。

由此，记忆原生模型希望实现三个目标：

- **可学习**：模型能从当前经验过程中识别哪些东西值得记、哪些可以学。
- **可持续**：记忆状态不会随当前 session 结束就关闭，而能跨 session、跨对话，甚至在很长时间范围内内化知识和经验。
- **可进化**：例如越来越懂用户；在用户关注或企业响应的特定问题上效率越来越高。讲者举例，模型部署到金融行业公司，起初在企业内部金融 benchmark 上可能 50 分，期望运行一段时间后到 60 分甚至 70 分。

一句话概括目标：不是给现有基座挂一个更大的记忆库、再叠更复杂的记忆框架，而是训练一个真正的模型，让它自己知道记什么、知道怎么改、知道怎么使用已经内化到参数中的记忆。这个模型本身仍是通用基座，差异在于除了通用能力之外，还具备针对记忆的较好处理能力；这部分能力从训练开始就和模型长在一起，使用时也能较好地更新和使用。讲者用“给通用基座装上一个记忆层”作类比，类似海马体，但也说明这个类比未必完全合适。

### 原型阶段的三项能力

讲者把记忆系统的需求映射到模型内部，认为原型阶段至少要具备三项能力。

**第一，学会什么是值得记住的。** 这对应记忆的抽取和组织，而且要在模型内部完成。例如日常对话、金融行业形成的信息、agent 做代码任务形成的信息，模型应能自主识别其中哪些值得记住，也就是哪些可能在未来影响模型推理性能。讲者明确不想继续依赖这样的流程：用户主动写 prompt 让模型“帮我记住这些东西”，再让模型拆成记忆片段，模型输出后再塞到上下文工程里。目标是模型能针对输入信息自主压缩编码，并形成长期记忆状态。

**第二，学会如何更新记忆。** 记忆是实用性的东西，很重要的一点是状态会变化。如果模型不具备更新记忆的能力，就不能做跨 session 或更长期的任务。讲者希望模型具备较好的更新机制，或者自己学会更新能力，把旧状态更新为新状态。

**第三，学会如何调用记忆。** 在 Memory T 1.0 基座原型中，讲者提到做了两件事：一是模型在当前记忆空间或当前版本记忆中，能够调用较好的 attention 回来参与当前推理流计算；二是当存在多个参数化记忆模块时，模型应学会从多个模块中选择最匹配当前问题的模块参与计算。

### 训练复杂度与 native memory block

这件事并不简单。仅“学什么值得记、怎么更新、怎么调用”每一点下面，围绕架构就有很多探索分支，例如使用什么注意力机制、注意力模块的参数化空间矩阵怎么设计、调用的 loss function 怎么设计。仅围绕这些点做探索性工作就有几百组实验，而且还要适配不同基座架构的特点，例如千问和 DeepSeek 各有自己的架构特点。当前第一个版本 Memory T 1.0 适配了千问 35B 模型和 DeepSeek 的 Flash 模型，还在做更大的英伟达 NeMo 系统 550B 模型。

Memory T 1.0 的原生架构核心，是在现有 Transformer block 里加入 **native memory block**。可以类比为给现有 Transformer 加一个“外挂海马体”，但它必须高效参与整个计算。其核心点包括：

- **推理与记忆同层融合**：基于当前信息和历史经验，共同参与当前推理计算流。
- **上下文驱动的更新**：模型在前向计算过程中就能实现记忆的擦除、写入和遗忘。
- **训练中区分 hyper memory block 与 local memory block**：

| 模块 | 作用 | 训练与更新 |
|---|---|---|
| **hyper memory block（超记忆）** | 管理和处理记忆，例如知道什么时候写入、什么时候擦除、什么时候遗忘，以及遗忘什么内容 | 在记忆原生基础模型训练时更新这部分参数，形成记忆管理能力 |
| **local memory block** | 负责内容记忆本身，例如记忆存在哪里、怎么存、存完怎么拿回来用 | 训练完成后，后续更新主要更新这部分 |

这套设计带来的效率差异是：训练时主要搞定 hyper memory block；训练完成后，后续更新只更新 local memory block。讲者称，相比需要做后训练的模型，效率会高很多，成本也更可控。技术报告也从成本角度，与基于后训练的方法、LoRA、RAG、全上下文范式做了完整对比。

这里还有一个关键辨析：原生记忆并不意味着要把所有明文内容、明文经验都写到模型主干参数里。如果这样做，就和现在大家做微调、做后续训练没有差异，也不是他们想做的方向。从落地成本看，企业做后训练至少要配算法工程师，还要准备预训练数据、通用后训练数据以及面向企业的专有后训练数据；这一套流程下来可能需要“千百万”级投入，而且收益不确定，很多公司很难承担。因此他们希望以更高效的形式让模型学会记忆的形成、更新和调用，但不一定做全参数更新。

### 不依赖外部明文记忆的增删改查

在这个架构下，“增删改查”不是在一个外部明文记忆库上做检索和拼接，而是在模型前向计算和内部记忆状态中完成：

- **增／写入**：模型基于上下文，在前向计算过程中决定写入记忆。
- **删／遗忘**：同样在前向计算中完成擦除和遗忘。
- **改／更新**：把旧状态更新为新状态，支撑跨 session 和更长期任务。
- **查／调用**：通过 attention 让当前记忆空间参与当前推理流；存在多个参数化记忆模块时，选择最匹配当前问题的模块参与计算。

其中，hyper memory block 负责“什么时候写、什么时候擦、忘什么”的管理策略，local memory block 负责内容本身“存在哪里、怎么存、怎么取回”。这样，记忆的形成、更新和调用被纳入模型计算，而不是停留在一套外部明文 harness 中。

当前 Memory T 1.0 仍是原型：第一版适配了千问 35B 和 DeepSeek Flash，英伟达 NeMo 550B 还在推进；围绕架构、注意力和 loss 的探索有几百组实验。讲者的核心判断是，记忆原生模型的关键不在于再做一个更大的外部记忆库，而在于把“记什么、怎么改、怎么用”变成可训练、可持续、可进化的模型能力。

## Memory T 1.0、MemOS 3.0 与 memory scaling 路线

这一部分讨论的是记忆原生模型从“能跑出结果”走向“可迭代、可扩展”的路线问题：Memory T 1.0 Flash 给出了什么，MemOS 3.0 准备怎样调整分工，以及更长期的 memory scaling 想解决什么。

### Memory T 1.0 Flash：先看纯基模能做到什么

报告展示的结果基于 **Memory T 1.0 的 Flash 版本**：在 DeepSeek V4 Flash 上做后训练，并加入记忆原生改造。讲者对整体性能的评价是“也还行”，但没有给出具体数字，因此这里不宜推断具体提升幅度。

一个需要特别注意的设定是：**这一版结果没有搭配记忆框架**，测的是纯基模。也就是说，它回答的问题是“模型自身被改造后，记忆能力到了什么程度”，而不是“模型加外部记忆系统后能达到什么程度”。转写中配套框架出现了 Hindsight、哈里斯、HANIS 等不同称法，按后文的说法，配套框架指 HANIS。

训练范围被明确划成两段：

- **已经训练的部分**：记忆原生基础模型学习对记忆本身的增删改查能力，即模型层面如何写入、读取、修改、删除记忆。
- **尚未训练的部分**：哪些信息值得放进记忆、哪些信息需要进一步做经验提炼和抽取。这部分判断与筛选能力没有放进基模训练，而是希望交给配套的 HANIS 框架完成。

这实际上是一种有意的能力切分：模型负责记忆操作的“底层动作”，框架负责“记什么、怎么提炼”的上层策略。从通用系统设计角度看，这类似把存储引擎和策略层分开，便于分别优化，但也意味着纯基模的评测结果不能代表完整系统的上限。

跨 session 能力是评测中很有挑战性的一项。设定是：当前一轮上下文给模型 10K 内容，下一轮问相关问题时不再提供任何上下文，希望模型能回忆出上一轮 10K 内容里的关键信息。讲者称，相比一些参数化记忆方式或类似参数化记忆的模型，这一版有“非常大的代际提升”。但同时承认差距：相比当前一些 SOTA 记忆框架，或者相比他们自己的 MemOS 那套“明文记忆加激活记忆”的管理框架，仍然有一点差距。

这里的目标并不只是追平外部框架，而是希望进一步优化后，**由模型层面替代现在复杂的明文记忆系统**。动机在前文痛点中已经出现：明文记忆系统的增删改查、从记忆中更新和共享等非常复杂，希望不再由 agent 或人工去定义这些事，而是让模型自己完成。

### MemOS 3.0：把明文记忆层做薄

围绕模型与框架的分工，下一步的重点是 **MemOS 3.0**。可以用一个比例来理解变化：

- 如果 MemOS 2.0 是把整个记忆以 100% 的“重型”方式管理；
- 那么 3.0 会把这一层做薄，可能只有 **10%—20%** 的明文记忆管理信息在 3.0 框架里流转；
- 剩下 **70%—80%** 的内容在模型里面流转。

这并不意味着明文记忆被取消，而是把框架从“承载全部记忆管理”退到“保留必要部分”，更多职责交给记忆原生模型。它与前一小节的训练切分相呼应：模型已经具备记忆增删改查能力，框架就可以少做一些底层管理，更多承担信息取舍、经验提炼等模型尚未训练的部分。

### memory scaling：让记忆模块成为可增长的版本维度

更长期的设想是找到一条 **memory scaling 曲线**。讲者提出的发版形态与现在不同：不再每次都先做主模型后训练、再发一个主模型版本，而是主模型在一段时间内基本稳定，**发布的是 memory 模块版本**。

具体设想是，最终模型可能由 **1T 主干加 1T memory 参数**组成；过一段时间再加入 **200B memory 参数**，再过一段时间加入 **100B memory 参数**，形成线性的或 scaling 式的增长，并让模型性能随 memory 参数增长而增长。

这个设想的核心不只是“参数更多”，而是把记忆从一次性训练进主模型的能力，变成可以持续追加、按版本发布的独立维度。作为背景，常规做法中模型能力更新往往依赖重新训练或继续预训练主模型；memory scaling 试图把“记忆”拆成可独立扩展的部分，从而降低每次发版对主模型的扰动。当然，这一设想能否成立，取决于记忆参数增长是否真的带来可预测的性能增益，这正是需要实验回答的问题。

讲者强调了投入量级：仅前面做的记忆模块就已经花掉非常多的人力和算力，才有了当前结果；要继续做到目标，按现在的评估，需要在现有算力和人力投入基础上**再乘以十倍**。接下来会有更多同学投入这个方向，也欢迎讨论哪些方向值得做。

报告最后回到 slogan“智能始于记忆”：人类能持续发展、持续提升能力，是因为有记忆；记忆有多种形式，包括纸质性的记忆、融入脑海的记忆、写入基因的记忆。讲者还提到希望 tensor（最小的计算单位）能真正形成未来的核心方向。

### 监督信号：继续往上拉性能的关键变量

在问答部分，讨论补充了一个训练层面的判断：继续提升记忆相关模型的性能，事实表明需要**构造更多、更丰富的监督信号**；**长短期记忆的引入**，以及**针对不同类型问题构造相应信号**，会带来更好的效果。转写在这里转入提问环节，没有展开具体模型结构或实验设置，因此这部分更适合理解为方向性判断，而不是已经给出的完整方案。

把这几部分放在一起看，路线是比较清楚的：Memory T 1.0 Flash 先验证记忆原生基模在纯模型条件下的能力边界；MemOS 3.0 通过把明文记忆层做薄来重新划分模型与框架的职责；memory scaling 则希望把记忆变成可持续扩展、可按版本发布的参数模块。三者共同指向同一个目标——让模型自己承担更多记忆管理，减少对复杂外部明文记忆系统的依赖。

## Memory 评测的对象与出题：agent 原生、事实抽取、时序演进与拒答

### 为什么记忆评测不能直接沿用 RAG 的尺子

发言者先把评估这件事的必要性摆在最前面：任何场景都需要把评估做起来。原因在于记忆系统的趋势已经发生变化——外挂的记忆体并不本质，做遗忘、更新时传统系统要定很多规则，换到新场景很难靠人手工调方案，模型学习这类经验变得重要；任务越来越长程，思维 bench 变成 deep 思维 bench，而且可能跨语言，这些长程任务背后很多要靠记忆能力解决。这类记忆区别于 harness 内置的记忆模块：原生在环境里的系统本来就应该有一套做大存储、做长程业务管理的机制，不应该放到 harness 里；这类记忆或环境管理对模型能力和整体智能提升非常重要。

由此，记忆评测与 RAG、long context 有本质区别。记忆体本身应该是 agent 原生的，应该服务 agent。很多 bench 以 chatbot 为中心、做 QA，导致状态维护等关键问题没有被很好评测：中间推理过程中哪些关键信息要保留、做了哪些交互、做了哪些图调用、后面怎样复用这些维护信息，以及已有更新答案后怎样把老答案消歧。这些都属于记忆能力，需要专门评测。

另一面是事实性证据提取。简单 RAG 可以算召回、精度、F1 或 EM score，只要把 evidence 召回即可；但 memory 要服务 agent，不能把所有信息都丢给模型，否则大量噪声会让模型做不好。做个性化 agent 的产品提出输入信息的信噪比：允许进来有噪声，但要保证真实数据信噪比在 70% 以上，这样强模型才可能有好的自主回答、自主完成任务能力。业务场景的数据一直流转，有不同版本、不同更新或类似多版本并发控制（MVCC）的机制，还有一些护栏，需要评测这套记忆系统是否足够完备。因此要设计一套区别于 RAG 的新评测协议：评测的 base 知识库不同，memory 涉及关键知识维护和改进，核心操作也不同。memory 有很多读操作和写操作，与传统数据库最大区别是读往往没那么复杂，而一系列更新操作比较 heavy，例如知识点一和知识点二属于相容 topic 时怎样 merge（consolidation），以及怎样做消息遗忘；更新是重点评测对象。跨 session 的记忆保持能力、典型 score 等也需要专门的 memory bench 设计。

### bench 的三层设计：数据、协议与指标

发言者把 bench 的核心要素拆成数据设计、协议设计和 metric 设计。

数据设计要设计历史 session、历史会话、历史知识点，情景模拟要足够好，包括跨 session 历史记录和增量数据流实时进来。带环境的 agent bench 本身很难：要在业务场景里面对几千上万个文件做日常型操作，如日报或方案优化，而配环境的范式现在很少，动态环境、自我演进的范式更难模拟。还要做可控更新，专门注入关键事实冲突，用这些冲突考验记忆体识别能力；并 enrich agent 历史轨迹，因为记忆要记录 agent 轨迹，如果轨迹都是纯文本或很简单、没有垂类专用专业工具，评测难度会降低，所以要丰富轨迹的模态、数据和工具丰富度，进一步提升评测难度。

协议设计方面，不同 memory 系统架构需要不同的评测协议：有流式、带 reflection 的 memory 系统，有 hybrid（可做 RAG、可做简单 agent search 的混合），还有 MemOS 这类一整套完整系统。协议要模拟前述数据流，根据数据流生成 query 和 gold evidence，gold evidence 本身也要更新；还要做单独模块检查。这里有一个值得注意的现象：在一些偏事实性或长程流式场景下，用原始文本存储可能比各种复杂的 memory 设计系统更好，因为复杂 memory pipeline 前面用 LM 做 extraction 的小误差，会在后面多跳推理时累积成很大错误，反而不如简单纯文本的 plain-only 存储。因此需要精细的模块化 check，以及对抗性的随机扰动，避免模型在固定协议下过拟合，也就是 hacking 问题；还希望 memory 能在 bench 里自主迭代：评测完之后再演进环境、再评测 memory 系统。整套协议设计很难，bench 演进也需要自主演进能力；否则模型发版从之前三到四个月一版，到现在四十天发一版，未来可能到周级，而一个 bench 做三四个月，肯定跟不上模型迭代速度。怎样自主迭代 bench 协议和难度，是很重要、很关键的卡点。

metric 设计上，2023 年做模型训练时很多 NLP 指标已经失效，分数非常高但人用下来体验很差；memory 系统里也一样，简单 RAG 指标不足以评测前述几个维度的 memory 操作和机制，所以要设计专门 metric。大致列四个方面：

| 维度 | 关注点 |
|---|---|
| performance | 不单看 evidence 提取准确度，还要看 agent 完成任务的成功率 |
| evidence fidelity | 证据是否有完整思维链、版本是否正确、关键噪声扰动有没有引入 |
| 更新 fidelity | 细粒度评测事实性更新是否准确、是否及时 |
| 诊断报告 | 不单从系统级别分析，还能从模块级别分析 |

这四个方面合起来，才构成一套能满足 memory 评测需求的 bench 系统。

### 四类操作如何落到具体题面

落到评测执行，要针对 memory 四类典型操作设计各类任务和典型场景：原始数据进来后提取成 memory 要存的信息；决定存成什么格式或形式，最简单存文本、Markdown，也可以结构化存储成表、分层树或图；retrieval，即用各种信息检索策略做检索；维护和更新。四类操作背后要覆盖典型场景，例如 personal agent、个性化智能体，memory 已成为核心模块。个性化智能体很重要的事情是自主完成任务：现在 agent 能力可能很强，但用户不会用，所以新范式是用户把权限给 agent，让 agent 主动帮忙完成一系列任务；有的专家一天要完成上百个不同 task，如果 agent 能在背后自主完成日常操作，就可以无感提升能效。要把成千上万的 API 及其历史使用 context 管理起来，离不开 memory 的贡献。评测上要验证四类操作，例如验证从原始数据中提取关键 facts 是否准确，需要通过相应评测来检验。

出题时，讲者用典型 context 考察事实抽取与记忆。比如问“过去六个月平均每周工作多少小时”，相关事实分散在两段话里，要求把两段话与工作时长关联并提取、记住。另一个方向是 story：在不同输入语境下评测记忆管理方式，比较更高效的管理与存储组织，包括基于树的层级/组织关系、静态 trace、时序 graph 存储，以及金融场景中用表单/表格管理数据。

### 维护：时序演进与静态冲突

维护是 memory 设计中投入精力最大的部分。事实演进用“用户原来住北京，下一版本住上海并有新工作”来测；问住哪儿时必须抽取最新地点，系统要能表达随时间变化的地点。静态冲突则如一个人既有真名又有绰号/玩笑名，时间不变但场景需求不同，要识别真名；还有不同场景需要抽取不同 facts 的情况。这些都需要大量场景设计。

讲者由此提出分工：这类事不应主要由做 AI/计算机的人包办。计算机/AI 应提供范式、评测维度和平台；领域专家更懂业务场景中真实、可复现的动态变化、静态或带条件的事实冲突，应让专家遗留大量上下文并由其提取场景。memory 与领域专家协同是很重要的一块。

### 拒答与 toy 护栏被强模型攻破

retrieval 部分展示了“拒绝回答”的例子：材料说鱼缸有多少加仑水，但没给鱼的数量；问鱼的数量时 agent 应学会拒答，而不是编。类似设计还包括对冲突做消歧。

但讲者提醒这些例子都很 toy。转写中提到较强的 Astra 一类系统可在其中迭代几千轮；三四轮或几十轮时答案可能不准，但叠到一千轮、两千轮以上，toy 护栏很容易被最强模型攻破。因此怎样把题迭代得更难，是当前做 benchmark 的人非常苦恼的问题。

## Memory 操作维度与 benchmark 分层：从抽取、检索到维护

这套讨论没有把 memory 简单等同于“更长的上下文”或“一个向量库”，而是按操作把它拆成抽取、存储、检索、维护几个环节，再把这些环节对应到不同类型的 benchmark。这样做的原因很直接：长上下文评测只能说明模型能不能在长文本里定位信息，却不能说明一个记忆系统能否在跨时间、跨 session、多任务交错的情况下持续积累、更新和使用信息。记忆评测因此需要从“能不能找到”推进到“能不能把该记的记下来、该取的取出来、该改的改正确”。

### 抽取：从长程时间流中留下可复用事实

extraction 的核心，是提取真正需要被 memory 下来的事实知识点，而不是把所有原始文本原样堆进存储。这里至少有两类任务。

第一类是 long context 中的关键信息提取。agent 完成一件事往往不是一次性的：今天做某公司竞调，拿了 20 个文件；明天又收集 5 个文件，继续丰富同一个竞调压缩包。信息分布在长程、多事情交错的时间流里，系统需要做 trace 提取。这里的 trace 可以理解为任务过程中留下的轨迹与证据链，它不只记录“结论是什么”，还要保留哪些操作、哪些材料、哪些中间状态支撑了这个结论。

第二类是事件 summary 或压缩。很多事件不需要记录全部信息，只需要管理元信息或关键事实。记忆系统要判断哪些内容值得保留、以什么粒度保留，而不是默认全量保存。

出题时要先分场景。个性化助手场景可以考察静态信息、关键压缩、用户偏好及其形成过程；也可以考察用户完成事情时跨 session 的关键对话，以及哪些对话与哪些任务相关联。不同 benchmark 会为不同角色设定相应场景。落到具体操作上，包括关键操作、信息提取、事件提取和单跳事实提取。因为抽取这一步多数还是在处理原始信息，所以大量任务表现为单跳关联：从一个片段或一次对话中提取一个事实，再把它挂到对应的记忆对象上。

### 存储：语义组织、版本关联与成本约束

存储不只是“把文本写进去”，它主要考验三件事：文本进来后如何做语义组织，是层次化组织还是其他分块方式；不同版本之间如何跟踪关联；以及存储效率。

这一点在大规模数据上尤其明显。上海 AI Lab 要把接近 500 TB 的科研数据或科学语料组织起来，直接复用现有数据库基本搞不定。现实约束是存储非常贵，算力卡很多，存储反而成为瓶颈。未来要做大规模支撑，必须解决存储压缩和高效组织问题。

对数据智能体这类专门做数据处理的 agent，存储还要跟踪其整个行为轨迹中的操作，收集可溯源的证据，回答“为什么做这些操作”；同时记录状态信息，以及内部 balance、收益类信息。把这些信息提取出来之后，再告诉模型：不同场景的信息分别应采用什么组织形式、跟踪策略，以及怎样的 layers 或护栏设计。也就是说，存储层承担的是“让记忆可组织、可追踪、可约束”的职责，而不只是保存原文。

### 检索：从单跳 RAG 到多跳 trace 与拒答

retrieval 比简单 RAG 复杂，因为记忆检索要和 agent 配合。简单 RAG 是单跳的：问今天天气，直接召回某地区天气即可。记忆系统面对的关键问题在多跳操作：当前问题可能关联历史 trace，系统要能召回历史相关 trace，这就需要 trace 跟踪；还包括时序 retrieval、证据 ranking，以及最后的 abstention，也就是在证据不足或冲突时选择不强行回答，并对一系列冲突做消歧。

因此，评测不能只出“给定一段文本回答问题”的题，还要生成多跳检索 task、检索 task 和工具调用 task。检索在这里不是一次性的召回动作，而是和 agent 的决策过程绑定：先判断需要什么记忆，再决定查哪里、按什么时间关系查、如何比较证据，最后判断是否足以回答。

### 维护：更新、矛盾、遗忘与反思

memory maintenance 有几类核心操作。第一是更新，做新版本迭代；第二是面对大量矛盾信息时，如何在评测中复现这些矛盾，并考察系统能否识别和处理；第三是支持 forgetting，对过时旧版本信息做消歧，或处理重复消息；第四是 reflection，对记忆机制本身进行复盘和迭代。

这类操作在 workplace agent 上尤其重要。现在不少 workplace agent 具备角色扮演能力，也有可使用的文件权限和自有空间，背后需要更细粒度、分角色、分层级的记忆管理。不同角色能看到什么、能改什么、哪些记忆属于个人空间、哪些属于任务空间，都会影响维护策略。维护因此不只是“改一条记录”，还涉及版本边界、权限边界和冲突处理。

### Benchmark 的三类评测与不同设计层级

从现有 benchmark 与操作维度的对应关系看，大类上可以分三类：

| 评测类型 | 主要考察 | 代表例子 |
|---|---|---|
| long context 评测 | 长文本下的信息检索与定位能力 | LoCoMo 一类 |
| 跨 session 评测 | 跨 session 的记忆能力 | Memory Agent Bench |
| agent procedure／过程性操作评测 | 更新、维护、访问系统细节等精细操作 | lifelong memory、lifelong agent bench |

这三类的切分点并不完全相同：前两类更偏记忆材料的时间跨度和上下文长度，第三类更偏 agent 是否会把记忆操作做对。也就是说，长上下文分数高，并不自动代表跨 session 记忆强，更不能代表会维护记忆。

benchmark 设计也有不同层级。有的在一个赛事里设多个 task；有的在不同赛事、跨赛事之间设 task；Memory Arena 则用竞技场方式做评测。lifelong agent 会评测 agent 调用不同存储引擎的能力，例如 database、OS 或知识库。因为记忆本质上是一个“大号工具”，agent 要能精细写出复杂命令，才能真正访问和操作外部记忆。

GUI 场景的 memory 也是很大的痛点。现在长上下文可以做到几百万 token，但主要还是文本形式；把图片拼成很长的 context 后，模型在空间推理和图像关系上的能力比较差。除此之外，还有流式等不同场景设定下的一整套评测方式。

这套操作维度与 benchmark 分层的价值在于：它把记忆评测从单一的“长文本问答”拆成抽取、存储、检索、维护多个可考察环节，并指出不同 benchmark 各自覆盖哪一段。只有把评测对象、任务场景和操作过程对齐，才能判断一个记忆系统究竟是在“记住更多”，还是在“更会组织、检索和维护记忆”。

## Fusion 聚合评测：用一套平台看记忆系统的差异与不足

报告介绍的 Fusion 是一个聚合评测平台，目标不是再做一个单点 benchmark，而是把分散的评测能力组织起来，较全面地反映各类 memory 系统的差异与不足。这个出发点来自一个现实：各家 benchmark 都有自己的场景设定和局限，单独看某一个任务，容易只看到局部能力；只覆盖某一类负载，也难以判断一个记忆系统在真实使用中的综合表现。因此，Fusion 强调“聚合”而非“单任务排名”——它要回答的是系统在多个能力维度上分别处于什么水平、短板在哪里，而不是给出一个孤立的分数。

### 五个评测维度

平台把评测拆成五个重要维度，分别对应记忆系统从“能不能记住”到“用起来贵不贵、稳不稳”的不同问题：

| 维度 | 关注点 |
|---|---|
| memory 有效性 | 记忆是否真正被建立、保留并在需要时发挥作用 |
| 检索 evidence 精度 | 检索到的证据是否精确、是否足以支撑当前任务 |
| 运维鲁棒性 | 系统在更新、维护和不同运行条件下是否稳定 |
| 整体开销与运维成本 | 操作 cost、存储开销、维护与运维成本是否可接受 |
| 模块级评测分析 | 把整体表现拆到抽取、检索、路由、更新等模块，定位能力来源与瓶颈 |

其中，模块级分析很关键。一个记忆系统表现好，可能是因为抽取做得好，也可能是因为检索或路由设计得好；只看端到端结果，很难知道该改哪里。Fusion 希望把能力拆细，看到具体模块的贡献和不足。材料中还提到提取有效性、routing 到具体模块、不同维护和运维成本能否改善，这些都属于“不只看效果，也看代价和可运维性”的评测思路。

### 主要发现：评测结果反馈到系统设计

报告给出的结论更适合理解为“评测平台对系统设计的反馈”，而不是一张简单的排行榜。几个比较有代表性的发现如下。

**1. 图结构记忆在多跳任务上有优势。**  
graph based memory 在多跳 task 上表现很好。多跳任务要求把多个实体、事实或关系串联起来，从通用原理看，图结构天然适合表达关系路径和跨节点连接，因此在这类负载上更容易发挥作用。这是评测中观察到的能力差异，不意味着图结构在所有任务上都占优。

**2. 带时间戳、跨分层时间流的事实抽取设计效果较好。**  
在事实抽取类任务中，特别是涉及时间戳、跨分层时间流的 memory 设计，表现相对更好。这说明记忆系统不能只存“事实是什么”，还要处理“事实在什么时候成立、随时间如何变化”。时间信息如果能在抽取和存储阶段被结构化，后续检索和推理会更稳定。

**3. 精细时序与跨关联设计能提升细粒度指标。**  
当 memory 系统在系统级做较精细的时序设计、跨 reasoning 的关联设计时，在一些细粒度指标上表现较好。这里的重点不是单一模块的强弱，而是系统层面能否把时间关系和语义关联组织起来，支撑更复杂的查询与推理。

**4. 时序级与语义级同时组织状态，更新鲁棒性更稳定。**  
跨不同事件时，如果系统既按时序级别、又按语义级别做状态组织，更新鲁棒性会更稳定。换句话说，只按时间流水记录，或只按语义聚类，都可能在某些更新场景下失衡；两者结合，更有利于处理事件之间的冲突、覆盖和演进。

**5. backbone 鲁棒性反映 memory 的实际价值。**  
平台还会换不同存储引擎、换不同模型，观察系统在较差模型或较差存储方式下是否仍能保持较好效果。这一点很重要：如果 memory 只有在最强模型和最优存储上才有效，它的独立价值就有限；如果在 backbone 变弱时仍能托住性能，说明记忆机制本身在分担一部分能力。这是评测 memory 价值的重要角度。

**6. 难度上升时要看性能是否稳定。**  
当测试难度增长，证据跨时间或跨空间区域的距离变长时，平台关注 memory 性能能否保持稳定。时间跨度变大、空间区域变远，往往意味着证据链更长、关联更弱，对记忆组织和检索提出更高要求。此时不只看峰值效果，还要看衰减是否可控。

**7. 成本与模块级运维能力同样纳入评价。**  
除效果外，报告还关注操作 cost、存储开销、提取有效性、routing 到具体模块的能力，以及不同维护和运维成本能否改善。记忆系统不是一次性建好就结束，持续更新、清理、迁移和定位问题都会产生成本；这些成本如果过高，会影响系统能否长期运行。

### 这些发现应怎样读

Fusion 的结论不应被读成“某个系统全面领先”。更合理的读法是：不同记忆设计在不同维度上有各自的长处和代价。图结构在多跳关系上强，时间流设计在带时间戳的事实抽取上更有优势，时序与语义结合的状态组织在更新鲁棒性上更稳，而 backbone 鲁棒性和成本维度则提醒人们：记忆系统的价值不只在最强配置下的上限，也在较弱条件下能否保持可用、可维护和可负担。

因此，这套聚合评测的意义在于把“效果、精度、鲁棒性、成本、模块归因”放在同一框架下观察，帮助设计者判断某种 memory 架构究竟适合哪类负载、短板出现在哪个环节，而不是用单一任务或单一分数替代对系统的理解。

## 自演化 benchmark 的独立性、区分度与专家数据

学生提出的问题触及自演化评测的关键风险：当 benchmark 的任务生成、难度调整和评判标准越来越多依赖大模型或其他 agent，评测体系本身可能继承生成模型的认知偏差；如果生成方与被评方能力同源，还可能形成共同能力盲区。这样即使 benchmark 能自主迭代，也可能失去独立性、区分度和有效性。周老师的回答没有停留在“让另一个模型来校准”，而是把校准锚点放到业务场景数据和外部专家轨迹上。

### 问题不在自动化本身，而在数据来源

现在很多业务场景里的数据没有被用起来，而造 benchmark 的人往往不是做这摊事的人。有些团队让一堆标注人员冒充金融专家、法律专家出题，这并没有真正切入业务场景，也没有把业务场景中的文档、工具、轨迹、历史、做过的任务提炼出来。这样造出的题容易只有“专家口吻”，缺少真实任务约束和过程信号；如果把它交给模型自动扩展，只会把薄弱来源放大。自演化评测要获得独立性，首先要求题目和评分标准来自被评模型之外的真实活动，而不是由同源模型自产自评。

### 滚动式专家数据：把轨迹和评判标准沉淀下来

周老师提到，已有团队采用滚动式招专家的方式：如果每三个月要提升数学题能力，就招一批数学家，三个月给一百万，让他们在限定周期内做题；再把历史轨迹、整个评判标准提炼出来，本质上是做蒸馏。现在他们做的是把这件事自动化起来。这里的重点不是简单收集标准答案，而是把专家如何理解任务、如何走中间步骤、如何调用工具、按什么标准判断对错，沉淀为专家数据，再蒸馏进 benchmark。这里的“蒸馏”可以理解为把专家轨迹和评判标准提炼成可复用的评测数据，而不是泛指某种模型压缩算法。

| 数据来源 | 主要提供 | 对自演化评测的意义 |
|---|---|---|
| 标注人员冒充专家出题 | 题面、答案 | 容易脱离业务，独立性弱 |
| 业务场景文档、工具、轨迹、历史、任务 | 真实约束、过程路径、评判依据 | 提供外部锚点和区分度 |
| 滚动式专家周期 | 专家解题轨迹、评分标准 | 可沉淀、可蒸馏、可周期校准 |

这种做法的价值在于：专家数据独立于被评模型的生成过程，业务轨迹又提供了真实分布和过程性信号。自动化的角色应当是采集、整理、提炼和规模化，而不是替代外部专家锚点；否则“自主演化”容易变成模型偏差的闭环。

### 独立校准与人的角色

从通用评测原理看，benchmark 的独立性至少要求题目来源、评分规则和目标模型解耦；区分度则要求难度和信号不会被模型已有能力同化。因此，一个能自主持续演化的 benchmark 仍然需要独立于模型生成过程之外的校准机制。周老师给出的路径表明，这种校准可以主要来自外部专家周期和真实业务轨迹，而不只是另一个模型判分。这里需要区分“模型辅助整理”和“模型作为唯一来源”：前者可以提效，后者会带来共同盲区。

再往后，当业务里的数据都被吃掉了，就要考虑整个 agent 的可通能力，这需要更强的模型能力提升；同时还要考虑人是否参与、扮演什么角色。周老师给出的判断是，未来一定是专家不如 Agent 好，但这时候专家应该扮演什么角色，需要回答。现实限制是，现在很多 agent 的输出人自己看不懂，或者没有精力去做“榨汁”或检验。因此人的角色可能从直接出题，转向定义任务、审核轨迹、校准评判标准和补充新业务场景。这样自演化 benchmark 才能持续获得外部数据，而不是在模型内部自我循环。

## 环境记忆与模型—环境协同进化

报告最后把问题从“做一个 memory 模块”推进到“Beyond the Memory”：只做记忆模块已经非常拥挤，商业化上还要面对高估值公司的竞争；更重要的是，静态的文件存储并不等于模型整体能力变强。要让 Agent 或 AI 系统在真实任务中持续进步，需要把记忆放回环境中考虑——维护好一系列环境组织，让环境记忆与模型协同进化。

### 为什么只做 memory 模块不够

当前很多记忆工作集中在“把信息存下来、检索出来”，但报告指出两个限制。

第一，静态文件存储是“死”的。模型可以读取文件，却不等于能理解文件之间的关系、判断哪些证据关键、按什么顺序使用。只增加存储容量或检索接口，未必带来 Agent 整体能力提升。

第二，在嘈杂环境下做文件检索和经验提取时，当前最强模型的表现也比较差，环境级任务的成功率更低。报告认为，本质原因不完全是模型能力不行，而是背后一系列文件的“语组织”做得不够好——更准确地说，是文件之间的语义组织、任务组织和证据组织不足。模型面对的不是一份干净文档，而是一堆跨时间、跨来源、彼此关联的文件；如果没有好的组织方式，强模型也会被环境拖住。

因此，Beyond the Memory 的重点不是再做一个更厚的“文件柜”，而是设计模型或系统，把环境中的文件组织成模型可执行的结构。

### 核心：从文件堆到任务级证据链

报告提出的关键做法，是把一系列文件做**任务卡片级别的聚合**，并跨时间线完成**证据链关联**，再识别哪些文件需要读取、按什么顺序读取。

| 静态文件存储 | 环境记忆 |
|---|---|
| 以文件、片段为单位存放 | 以任务卡片为单位聚合 |
| 关系弱，依赖相似度检索 | 跨时间线建立证据链 |
| 重点是“记住” | 重点是“支撑任务执行” |
| 模型自己判断读什么 | 系统规划读哪些、按什么顺序读 |

这意味着环境记忆至少包含三层工作：

1. **任务级聚合**：不是把文件简单切块，而是围绕任务把相关材料组织成卡片，让模型知道这些文件共同服务于什么目标。
2. **跨时间线关联**：同一任务的证据可能分散在不同时间、不同来源的文件中，需要把前后关系接起来，形成可追踪的证据链。
3. **读取规划**：识别哪些文件是必要证据，哪些可以跳过，以及先读什么、后读什么。环境越嘈杂，读取顺序和证据筛选越重要。

这样，环境记忆就不只是“外部存储”，而是模型在环境中行动时的组织层：它把环境中的文件转化为任务可用的证据结构。

### 从失败任务到模型—环境协同迭代

报告进一步强调，要处理模型真正做不好的 task，而不是简单把信息记录好。材料中举到两个例子：办公场景里的“发表提示不一致”，以及室外场景中关键场景线索提示较差。对于这类任务，仅靠外挂记忆或提示工程不够，需要做模型后训练。

但后训练不是终点。报告给出的闭环是：

1. 找到模型在环境级任务中真正失败的环节；
2. 针对这些 task 做模型后训练；
3. 继续迭代环境，而不是停在“信息已经记录好”；
4. 迁移其他环境中的噪声或更难的交付物，提出更高标准；
5. 再用新环境训练模型、考验模型，如此循环。

这个循环的关键在于：环境不是固定不变的测试集，模型也不是一次性训练完的静态系统。环境可以变难、变嘈杂、变复杂，模型则通过后训练适应；模型变强后，环境又可以提出更高要求。二者相互施压、相互塑造，形成报告所说的“孪生能力演进”——模型对环境的理解能力和环境对模型的考验强度一起演进。

### 关键卡点与限制

这条路线最关键的卡点不是单纯训练一个更大的模型，而是**维护好一系列环境组织**。任务卡片如何划分、证据链如何跨时间维护、读取顺序如何规划、噪声和更难交付物如何迁移，都是重工程问题。环境组织得不好，模型再强也会在环境级任务上表现不佳；环境迭代如果只是增加难度而没有组织好证据，也可能变成单纯“加噪声”，难以形成可迁移的能力。

总体看，报告给出的不是某个孤立算法，而是一条系统路线：以任务卡片聚合和证据链组织为基础，把模型后训练与环境迭代接成闭环，让模型不再依赖静态文件存储，而是在不断变难的环境中与记忆系统共同进化。

## 外部记忆与参数化内化的分工及部署形态

很多 agent 目前仍采用外挂外部记忆模块的方式，一个重要原因是模型不训练、或事后改写参数的成本较高。围绕“是否要把记忆做成原生、把记忆状态放进模型内部”，讨论没有把外部记忆与参数化内化看成简单的替代关系，而是把它们放在一个按读写效率分层、按复用价值分工的长期架构中理解。

### 分工依据：按读写效率分层，而不是所有记忆都内化

报告者把目标逻辑追溯到记忆的理论建模：早期做记忆分层，以及现在做记忆原生基础模型，核心之一都是按读写效率做分层。也就是说，不同记忆的读写频率、复用范围和更新节奏不同，不适合用同一种存储和调用方式处理。

从这个角度看，外部记忆与模型参数更新之间会形成动态分工和协同机制：

- 变化频繁、具体、长尾、隐私敏感或暂时不确定是否复用的信息，更适合留在外部记忆或用户侧记忆模块中；
- 稳定、高频调用、能够泛化为模型能力的经验，更适合持续学习并内化到参数中；
- 企业内部的公共经验，如果会被组织成员高频使用，可以进入参数化模块，以换取更高的读取效率；
- 个人侧则通过隔离的 local memory 模块承载个人记忆，避免把个人隐私直接写进共享参数。

作为背景，这类似于把“查得到但变化快的事实”和“已经稳定下来、反复使用的模式”分开管理；但会议中的具体判断标准并不是泛泛的知识分类，而是下面要说的性能收益与调用频率。

### 判断什么值得内化：性能收益与高频复用

判断什么样的经验或记忆值得被模型内化，报告者给出的重要标准是：内化到模型内部后，究竟期待它给模型带来什么。具体说，要看内化之后是否能带来性能提升，并且这种性能提升在对应应用场景中是否会被非常高频地调用。

金融场景的例子很能说明问题。如果用户只是说“我昨天买股票亏了多少钱”，这个亏钱的具体信息非常不值得内化到参数空间：它是一次性的、具体的事实，复用价值低。相反，如果对话涉及股票决策过程中的一系列决策逻辑和经验，而且这些逻辑经验确实带来了收益，能够帮助下一次选股，或帮助公司的量化算法选股，并且这种帮助在未来较长一段时间内会被反复使用，那么这样的内容就明显值得内化。

这里的分界不只是“个人还是公共”，也不只是“事实还是知识”，而是更接近：

- 内化后能否提升模型在目标任务上的表现；
- 这种提升是否对应高频应用场景；
- 相关经验是否会在未来长期复用；
- 内化收益是否足以覆盖训练、存储和调度成本。

讨论没有给出一个已经完全自动化的统一判据。报告者明确认为，判断内容能否被内化，需要一套配合的 Harness 框架。

### Hyper Memory Block 与 Harness：谁决定训练和调度

这套 Harness 框架取决于两个方面。第一，判断和调度逻辑能够由人参与建设；第二，训练整个记忆原生模型时，除了训练通用的记忆能力，还会训练 Hyper Memory Block。Hyper Memory Block 如果能针对行业做泛化，可能在该行业的记忆原生效果上更好。

换言之，Hyper Memory Block 不是孤立的一个模块，它和 Harness 的关系体现在训练与调度层：Harness 负责组织和决定记忆的训练频率、训练逻辑以及训练调度逻辑；Hyper Memory Block 则承载面向行业泛化的记忆能力。未来架构不排除朝这样的方向改变：记忆模块本身也能被训练，在企业内也能被训练，但其训练和更新频率不会像 local memory 那么高。哪些模块需要更新、以什么频率更新、如何调度，都会由 memory 的 Harness 框架决定。

这也解释了为什么“内化”不是把全部信息一次性写进权重。更合理的形态是分层：local memory 更新频率高，Hyper Memory Block 或企业侧记忆模块更新频率较低，Harness 在中间做判断、训练和调度。

### 部署形态：to C 的隔离与企业公共经验

落地时，讨论把记忆使用形态分为 to C 的记忆和 to business/group 的记忆。

对 to C 而言，核心点是保障内化到模型参数里的这部分记忆不是个人隐私。报告中提到的一种 scaling 方案是：不同用户有不同的 local memory 模块，这个模块本身可以像明文一样基于用户 ID 分开存储。每个用户有自己的 local memory 模块，但效率比类似 LoRA 的形式高很多，成本低很多，因此从成本上看应该可以接受。

这里的部署含义是：个人记忆并不是直接混入所有用户共享的模型参数，而是通过用户 ID 隔离到各自的 local memory 模块中。这样既保留了参数化读取的效率，又避免把个人隐私写进公共参数。代价是每次推理可能需要加载用户自己的模块，这会改变现有调度方式。因此，这次开源除了模型本身，还会开源对应的推理框架。当前受研发团队规模限制，推理框架性能不一定有现在大厂推理框架那么高；这部分除自己研发外，也在跟英伟达国内研发团队一起做算子层面的优化。原因是这套推理逻辑与通用大模型的推理逻辑明显不同，需要对推理框架做改造。

对企业使用，参数化模块里大概率不会存非常私有性的信息，只会存组织的公共经验，并且这些公共经验会被高频使用，例如公共政策或新形成的经验内容。放进去之后，读取效率会比单独以明文、以 context 上下文管理更高。报告者做了一些测算：无论存储成本还是显存消耗成本都会低很多。

原因在于这部分参数化模块可以被调度：如果预测某部分参数化模块未来不会被用到，就可以从显存中 drop 掉，放到 SSD，甚至可以放到冷备硬盘或外部硬盘中管理。磁盘里的成本远低于显存和 GPU 里的成本。这样，企业侧就形成“公共经验参数化、按使用频率分层调度”的部署形态；个人侧则形成“用户隔离的 local memory、按用户 ID 分开存储”的形态。

### 技术瓶颈与未解问题

从讨论看，主要瓶颈不在“要不要内化”这一句话，而在配套系统能否成立。

第一，判断标准需要工程化。哪些经验值得内化，要看性能提升和高频调用，但具体逻辑需要 Harness 框架来承接，并且需要人参与建设。怎样把这种判断从人工经验变成可运行的调度逻辑，仍是关键。

第二，Hyper Memory Block 的行业泛化能力。它能否针对不同行业训练出有效的记忆能力，直接影响记忆原生模型在行业场景中的效果。

第三，训练与更新频率的调度。local memory、企业记忆模块和 Hyper Memory Block 的更新频率不同，训练逻辑和调度逻辑要分开设计，不能把所有记忆都按同一节奏更新。

第四，推理系统改造。to C 场景下每次推理加载用户自己的模块，会改变现有推理调度；这套推理逻辑与通用大模型不同，需要在推理框架和算子层面做优化。当前推理框架性能不一定达到大厂水平，研发团队规模也是现实限制。

第五，成本与效果的边界。报告者测算参数化模块在存储和显存消耗上有优势，但讨论没有给出与 RAG、数据库方案的逐项基准；企业共享一套 memory 是否在所有场景下都优于现有方案，仍需结合具体负载判断。

整体上，外部记忆与参数化内化更可能形成一种按读写效率、复用频率和隐私边界分层协作的架构：高频、可泛化、能带来稳定性能收益的经验进入参数化模块；具体、低频、个人隐私或暂时无法判断价值的信息留在外部或隔离的 local memory 中；Harness 负责判断、训练和调度，Hyper Memory Block 与企业公共经验模块承担行业化和组织级复用。技术瓶颈则集中在判断逻辑、行业泛化、训练调度和推理系统工程化上。

## 数据库与数据厂商做记忆基础设施：语义层、商业化与避免过度设计

### 问题的起点：数据不出库，记忆能否都放进数据库

讨论从一个很具体的产业场景切入：一家老牌数据库厂商的客户分布在金融、医疗、能源等行业，很多数据不能出库。在 AI 负载增加后，这家厂商开始扩展产品线，做数据智能体，并在其中加入记忆功能。它的一个自然愿望是：既然自己做数据库，能不能让所有信息都存在自己的数据库里？

提问者把困惑拆成三层：第一，怎么看“把记忆信息都存在数据库里”这种做法；第二，数据库在记忆上到底能支撑到什么程度，数据库厂商的上限在哪里，甚至是否根本不上牌桌；第三，面向金融、医疗客户，如何证明“智能体加记忆”的价值。目前的小测结果是：加入记忆模块后，智能体调用次数少了，token 消耗少了，准确率“貌似高一些”。这些都是看得见的变化，但还不足以构成完整的客户价值说明。

### 回答的主线：先做语义层，而不是在记忆层内卷

现场回答首先判断，智能体进企业、进行业是大势所趋，符合企业或行业数字化转型的方向，也符合从消费互联网走向产业互联网的趋势。数据库、数据湖、大数据厂商基本会做两件事：一是 AI for DB，即做数据治理；二是 Data for AI，即把治理完的数据进一步用于 AI 服务，形成闭环。产品层面上，大家基本都在做 data agent，国内外厂商看起来差不多，Snowflake、DataBricks 以及国内厂商的产品形态有相似性。

但关键判断是：当前竞争的赛道不在记忆层，而在 semantic layer，也就是语义层。企业里不同团队对同一个指标的口径可能完全不同。比如做金融时，市场团队和销售团队对“收入”的定义口径不一样；口径对齐是 data align 里最重要的一块内容。这个例子说明，企业 AI 的难点往往不是“有没有记忆”，而是“记忆和查询所依赖的业务语义是否一致”。从通用原理看，语义层负责把表、字段、指标、口径和业务概念组织成可被智能体稳定理解和调用的中间层；没有这一层，记忆越多，反而可能把错误口径固化下来。

数据库厂商进入记忆存储也很自然：很多时候会从向量数据库往记忆存储延伸，因为记忆涉及存储和管理；查询是很大一块，RAG 是数据库厂商自然要做的菜，RAG 之后的延伸是 MAG，即记忆增强生成。从底层 infrastructure 角度看，数据库厂商天然应该做这件事：从原来“用 AI”，到“AI ready”，再到迈向 AI 原生数据库或数据基础设施。记忆会或多或少被当作一种管理单元，需要考虑生命周期、增删改查。

### 数据库厂商的上限：能做、被用、做好、生态

对“数据库厂商的上限在哪里”这个问题，回答并没有简单给出“能”或“不能”，而是拆成了几个层次。

一方面，数据库厂商确实有天然位置：记忆需要存储、管理、查询、生命周期维护，这些都与数据库能力相邻；向量检索、图查询、RAG 乃至 MAG 都可以成为产品延伸。另一方面，当前数据库厂商更多站在明文记忆或符号化一边，因为 SQL、GraphQL 基本仍属于明文范畴；而“记忆原生”更多涉及参数化内容。PostgreSQL 有 PG Vector 等能力，理论上可以做各种东西，但“能做”“别人用不用你做”“最后做得好不好”以及生态构建，是完全不同难度的事。想做就做，但是否能起来并不确定。

这实际上给出了一个分寸：数据库厂商不必因为“记忆”热就否定自己的基础设施位置，但也不能把“我能存”直接等同于“我能赢”。存储能力只是入场券，语义层、业务口径、生态和客户采用才是上限所在。

### 避免过度设计：应用驱动、能力沉淀与内外协同

讨论中一个很重要的提醒是：不要过早使用太 elegant、太 unified 的方式管理记忆。做底层架构时很容易想到一个统一抽象，但当前技术发展太快，基模能力升级太高，任务的通用性定义还没有快速定型抽象，过早做很可能 over design。更建议以应用驱动为主，通过演化和进化，慢慢想清楚哪些东西应该沉淀下来。

这里还有一个容易被混淆的点：不会把个人的具体记忆存到模型里面，真正要沉淀的是记忆的能力——学会 understand、学会 update、学会 utilize。能力这件事不变，不管是个人的、企业的还是其他形态。换句话说，重点不是把某人的某段经历塞进参数，而是让系统具备理解、更新和利用记忆的机制。

在形态上，也不必太纠结一定要外化还是内化，最终肯定是内外协同。不太可能纯用一个内化的东西做完所有事情；即使是智能体之间进行通讯，也需要外化的东西来处理。系统中总是有松耦合或解耦的部分，也有紧耦合或耦合在一起的部分。松耦合的东西一定会定义一种 protocol 和 message 交换方式；紧耦合的东西不一定用一种大家能看明白的方式。材料中还提到 Mem Privacy 这类工作，关注过程中的隐私保护和端云协同，这类事情可以基于应用做，也可以基于现有基础设施做。

### 商业化与评测：中间态、业务属性与“减碳”比喻

从商业化角度看，数据库厂商有一个尴尬点：想卖给中小企业、卖比较高价时，很多开源数据库就能满足需求；想卖给大厂时，大厂又会在开源上魔改和自建，于是处在中间状态。现在很多数据库厂商跑出来做记忆类型的创业，核心原因是把记忆加上去之后，再加一层业务属性，这时能展现商业化价值；如果反过来把它变成更底层的中间件，商业价值可能又没那么高。能加业务属性进去，并从记忆角度做更多底层能力提升，比如让时序上更准，可能是比较好的方向和切入点。

这也解释了为什么“评测指标”很重要。给甲方看加了记忆模块有多大收益，核心是成本下降与效率提升。发言者用“减碳”作了一个比喻，不是环保意义上的减碳，而是看上了记忆模块后，工作流里减少对人这个“碳基生物”依赖比例的降低程度——说白了就是可以减少多少人参与这件事。目前小测中调用次数减少、token 消耗减少、准确率貌似提高，都是可见指标；但要让客户信服，还需要把记忆带来的收益组织成更完整的评测：不只是单点准确率，而是工作流层面的成本、效率和人工介入比例。

### 底层选型与前瞻：图+向量、时序、联邦学习与新型表示

在 MaaS 底层选型上，有发言者提到自己也纠结过数据库或存储系统选型，最终选择类似同时支持图加向量化数据库的形态，以支持面向记忆的多种能力；后续合作还会引入时序检索能力。判断是：面向记忆机制做准备和突破的数据库厂商，可能更具竞争力。这与前面的语义层判断一致——记忆不是单一向量检索，还涉及关系、时序和业务口径。

更前瞻地看，记忆基础设施还可能影响联邦学习。数据不能出库，出库的东西要尽量保护；权重出库，甚至此前梯度出库再去交换，会成为新的点。在 agent 消费 token 或以 agent 为主的过程中，也可能产生一种新型 DSL：decode 出来是符号，但人可能看不懂，不一定是人现在的语言，也可能发生在隐空间或 embedding 空间。材料中举了 embedding 空间语言流的例子。这类方向是否成立，仍要看性价比和它本身适合的场景。

整体上，这场讨论没有把数据库厂商做记忆基础设施说成一条必然成功的直线，而是给出了一个更现实的组合：数据库厂商有底层基础设施的天然位置，但当前竞争焦点在语义层；记忆可以作为管理单元进入数据库，但不要过早追求统一优雅的抽象；商业化要避免只做底层中间件，最好把业务属性和底层能力提升结合起来；评测则要把“加了记忆”翻译成成本下降、效率提升和人工依赖减少。这个分寸，比单纯回答“数据库能不能做记忆”更接近企业落地的实际问题。

## 世界模型、agent 轨迹与连续记忆

这一部分讨论的是 agent 与世界模型结合时的两个具体接口问题，以及由此延伸出的一个方法论主张。提问者正在做智能体与世界模型结合的项目，关注两点：世界模型的隐状态应该放在记忆系统的哪一层；agent 执行轨迹能否直接作为世界模型的训练信号。回答在第一个问题上给出了框架现状的边界，在第二个问题上指出验证是真正的瓶颈，随后主动把话题引向“用连续记忆替代离散属性”来提升模拟多样性。

### 隐状态放在哪一层：目前没有形成完整 pipeline

提问者的设定是：用 GPT 那一套方法训练 world model，模型会在 latent space 里学习，那么与 agent 结合时，这个隐空间应该挂在记忆系统的哪一层去学习。

回答没有给出一个确定的层级划分，而是先说明现状：在 MemOS 2.0 这套框架里，针对参数化记忆、或者说针对隐空间的记忆训练，投入并不多。这部分目前仍以比较人工的方式推进——由算法工程师针对企业的特定场景做后训练来实现，并没有一条完整的 pipeline 去承接。至于可能的结合点，回答提出的是：基于原生基座的模型，配合 MemOS 3.0 框架去做一些训练。

这个回答实际上划出了一条边界：记忆系统在“上下文/外部记忆”层面的工程化程度，与“隐空间/参数化记忆”的训练管线并不在同一成熟度上。前者有框架可依，后者还停留在项目制交付。作为背景补充，参数化记忆指把信息写入模型权重，而非在推理时以文本或结构化的外部存储注入；隐空间学习则意味着模型在内部表征上完成压缩与预测，二者都比外挂式记忆更难观测、更难验证，这也解释了为什么它更难被标准化成 pipeline。

### 轨迹能否成为训练信号：难点在正确性验证

对第二个问题，回答的态度很明确：agent 的执行轨迹可以为世界模型提供信号，但最难的一环是**对轨迹正确性的验证**。无论是从记忆角度还是从训练角度，轨迹与环境交互产生结果之后，判断这条轨迹对不对，都是最难的。

难度随环境类型分化：

- **现实机器人场景相对好一些。** 例如问“这个球拿不拿得起来”，结果是可以直接观察到的，对错有物理落点。
- **虚拟环境里则非常难。** 当任务很长程时，中间某一步解决得正不正确，往往无法判断，要一直等到最终结果出来。更麻烦的是归因：中间反复的思考有可能恰恰就是它最终正确的原因，但这一点事先并不知道。

由此引出两个连带难题：一是中间结果的验证环境如何构建；二是从记忆角度看，哪些内容属于“符合最终正确性结果”的有效记忆，同样难以判定。

理论上存在一种做法：比如生成十条轨迹，其中 top three 是正确的，再把这些当作 signal 去监督模型。但回答的判断是这么做太难，很难找到有效信号。这也被列为当前训练记忆原生基础模型的难点之一。现有的尝试方向是：在训练 hyper memory 时构建更丰富的监督信号，例如在构造数据时滚动地让它做记忆拉取，给它一个答案，再把窗口扩长，然后再给一次答案，通过这种逐步扩展的方式获得可用的监督。

### 从离散属性到连续记忆：多样性从哪里来

回答随后提出了一个自己认为比较有意思的观点，针对的是当前很多 agent 做世界模型模拟的方式。

现在的常见做法是**基于属性定义 agent**：定义它是一个金融专家、30 岁、学历如何，再基于这些属性去定义行为，并附加一些行为约束。回答把这种做法类比为传统推荐系统里基于属性做离散化特征——本质是离散的。离散带来的问题是：由共同离散属性定义出来的 agent，行为会偏相似。

替代方案是把离散属性变成**连续记忆**：给每个 agent 配一套历史的、完整的、连续的记忆过程。以 30 岁金融专家为例，可以把他 18 岁甚至出生之前的经历、长短期记忆都给他。虽然都是 30 岁金融专家，但成长线不同、学校不同、看过的书不同，决策行为和路径就应该不一样。这样构建出来的世界模型或模拟，多样性才会足够。

| 维度 | 离散属性定义 | 连续记忆定义 |
| --- | --- | --- |
| 表示形式 | 若干属性切片，离散化特征 | 跨时间的完整经历序列 |
| 同属性个体的差异 | 行为偏相似 | 因成长路径不同而产生分化 |
| 对决策的解释力 | 由静态标签约束行为 | 由历史经历影响决策路径 |
| 模拟多样性 | 受限于属性组合 | 来自连续经历的分叉 |

### 具体怎么构造：切片加记忆连线

回答介绍了他们正在尝试的做法：当前属性只是 30 岁这个切片的静态状态，于是向前倒推——28 岁、20 岁毕业前、出生前、家庭形成前，每个阶段的属性切片是什么；再用记忆把每个切片之间连起来，使它成为一个连续的东西。判断是：这种连续记忆对行为多样性和决策的影响，会比属性切片式的行为更丰富，模拟出来的真实性也更好。

同样的思路被迁移到工业机器人：不只是给最终状态来定义现在的行为，而要喂它一些历史经历过的事情，让它真正经历过一遍。具体可以把过去每个阶段的行为、状态、决策串起来，生成行为到行为之间的决策路径，再把这些记忆作为它决策的参考来源之一。

提问者把这一思路理解为类似 context learning——把 experience 当作 context，去预测 policy 或某些状态。这一类比有助于把握要点：记忆在这里不只是检索素材，而是作为决策的条件输入，让相同的当前状态在不同历史条件下导向不同的动作。

## 严肃决策场景中的知识图谱、本体优先与神经符号融合

### 医疗场景：先问“错得起吗”

讨论从医疗知识库的提问切入：创伤救治等场景对逻辑性、时效性和可追溯性要求很高。提问者关心的不是大模型有没有隐式逻辑，而是隐式逻辑与知识图谱显式结构化逻辑各自的适用边界、如何协同；以及是否应把知识图谱从“逻辑表达的主载体”转为“约束、校验和审计层”，作为长期记忆架构中的结构化记忆。

回答先把医疗定位为“最不敢做”的场景。原因不是泛泛的准确性，而是后果：推荐错误、配药或药物冲突处理错误可能死人。对话摘要少一个知识点问题不大，但药物冲突这类逻辑关系建立不准确、召回不准确会出大事。因此，医疗知识组织和记忆组织需要强依赖、强逻辑关系。回答者更建议使用具有强依赖、强 schema 约束的知识图谱，并在这个基础上引入多重 agent 校验加人工复核校验；知识召回和图谱召回要结合。讨论没有展开具体的融合算法。

对于“是否把知识图谱转为约束、校验和审计层”，回答没有给出完整的是/否结论。可以确定的倾向是：医疗场景下强 schema 约束不可少，约束、校验和人工复核是兜底手段，不能把结构化知识当成可有可无的附属。

### 最小知识闭环：记忆能不能入库

在记忆抽取上，回答者尝试“最小知识闭环”的抽取判断：是否把记忆存入数据库，取决于当前组织的小块记忆是否自闭环，即其中的内容和信息是否足够为接下来的回答做推理。如果不够，就不存这套记忆，或至少完整存储当前上下文而不做抽取。

例子是用户说“请帮我约一下之前吃饭的老地方”。“老地方”是抽象指代；当这个指代不能被消融时，就不能贸然记进去，或者需要反复问用户“老地方”指什么，等用户把记忆填充完整后才能填充。医疗领域这类指代和需要消融的地方会更多。这个判断与知识图谱的角色直接相关：长期记忆中的结构化记忆不能只追求“记下来”，还要保证指代可消融、逻辑链可追溯、后续推理可用。

### 从知识图谱到本体优先

另一位回答者把问题放到 mission critical 或严肃场景：不能犯错，一旦犯错后果严重，医疗是明显例子。此类场景要求免幻觉、有依可循、可解释、可审计，以及做大量决策推演。

在决策智能上，讨论分出两条路。第一条是 model first，以大模型为中心，由各种智能体按需调用工具；回答者认为这条路不太适合构建 reliable、可信赖的 agent。第二条是本体优先，企业世界模型等采用此路，保证所有环节都有守门员、可被 harness、有明确评价。作为背景，本体优先不是先堆一个更大的知识库，而是先明确概念、关系、约束和评价边界，让模型在这些边界内运行；它也不是传统意义上的 knowledge graph。

### 四类 runtime 图与“绣花针式精准”

新的图谱形式不一定把所有东西都结构化，更多考虑 runtime 时产生的内容。讨论中提出会出现四类图：

- scene graph，场景图；
- skill graph，技能图；
- process graph，过程图；
- memory graph，记忆图。

图是内化还是外显没关系。关键不是跟模型比知识量，而是保证东西像绣花针一样精准。因此需要符号化内容给 hard constraint，或做明确的 judge。这正是神经符号融合的落点：不是用符号系统替代模型，也不是让模型替代符号系统，而是让符号约束、校验和评价在关键环节发挥作用。

### 传统知识库的问题与新语义层

传统知识库的问题是手工构建，构建一次全抽，抽完就没有然后；最原始 KBQA 时知识库永远不全，也解决不了自然语言交互，效果不好。现在要通过更好的、更加语义对齐的语义层和 RSI；讨论把二者比作“长坡厚雪”，壁垒不断滚动。可关注 OpenKG 以及企业智能体、企业世界模型相关工作。

本质上要解决大模型两个痛点：context scaling，通过记忆串接很多东西；environment scaling，造环境，如医疗场景环境、各种工作流环境。没有数据驱动、过程、关联的 reward 或结果，模型不可能变好。医疗还有很多可做，而且之前已构建大量知识库，不应弃用从头开始；应处于灰度的神经符号融合状态，而不是大模型火了就只用大模型、以前只用知识图谱的非黑即白思路；后者在现阶段会遇到较大问题。

### 协同边界：不是二选一

综合讨论，医疗等严肃场景不是“隐式逻辑”与“显式逻辑”二选一。隐式逻辑适合语言理解、上下文组织和交互，显式结构化逻辑适合硬约束、冲突检查、追溯和审计；但讨论没有给出按任务切分的具体算法边界。更明确的落点是：医疗场景下强 schema 约束不可少，知识图谱的约束、校验和审计职责很重要，同时要用多重 agent 校验加人工复核兜底；知识召回与图谱召回结合；“最小知识闭环”决定记忆能否入库。另一个回答进一步把方向推到本体优先和四类 runtime 图，强调符号化 hard constraint 或 judge 与神经符号融合。

若问是否把知识图谱完全转为“约束、校验和审计层”，讨论没有给出完整的是/否。可确定的是，结构化知识在严肃决策场景中不能退成可有可无的附属；其形式会从传统知识图谱扩展到本体、runtime 图和记忆图，角色则更强调精准约束、可审计与可评价，而不是与模型比知识量。
