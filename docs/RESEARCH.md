# 飞书式会议纪要调研与实现取舍

调研日期：2026-10-26。只依据产品和模型的官方公开资料。飞书没有公开完整内部推理流水线，以下处理架构是本项目的工程设计，不声称还原其内部实现。

## 可见的产品能力

飞书官方说明：开启会议 AI 总结或录制后，可以获得会议总结、待办、章节纪要和文字记录；妙记让用户从结构化摘要回查原文。产品页还展示了发言人及观点整理等功能。[官方帮助](https://www.feishu.cn/hc/zh-CN/articles/244959839578)、[妙记产品页](https://www.feishu.cn/product/minutes)、[智能会议纪要功能介绍](https://www.feishu.cn/content/article/7577317993749269689)。

对当前 CNCC 论坛，最有价值的是：先快速了解全场，再按时间和主题阅读技术内容，最后能回听具体观点。会议素材以讲座、主题报告、圆桌和问答为主，不能默认都有项目责任人、截止时间和行政决议。

## 能力对照

| 体验目标 | 本项目实现 |
| --- | --- |
| 一页了解全场 | 综合概要、核心方法、观点差异、明确决议和待办 |
| 有结构的长会议阅读 | 连续时间窗口的详细章节 + 跨章节综合去重 |
| 回查证据 | 每条摘要携带原始片段 ID，Markdown 引用定位逐字稿 |
| 可阅读的逐字稿 | ASR 原文、保守纠错稿、时间范围、可选声音标签 |
| 多人发言 | 可选本地声音聚类，按最大时间重叠匹配说话人，姓名人工映射 |
| 行动提取 | 只提取明确执行事项，责任人/期限缺失时标为“未明确” |
| 长时任务可靠性 | 音频/片段/API 请求缓存、失败隔离、状态与批次清单 |
| 便于服务器迁移 | 相对路径配置、独立环境脚本、多 GPU 动态队列和多服务器分片 |

章节的切分边界由字符预算和转写时间确定，章节标题由 LLM 提炼。它不是自动识别真实议程边界，也不是已经实现飞书的全部协作功能。当前范围不包括投屏/PPT OCR、真实身份声纹注册、云端权限共享、会中实时字幕、飞书任务同步。对本次“视频→完整 Markdown 纪要”目标，这些不是必要依赖。

## 为什么采用这套流程

1. **先导出标准音频。** 避免每次 ASR 重复解码视频，便于缓存和人工回听。
2. **在停顿附近切分。** 不把数小时波形一次送给模型，保留连续采样区间，减少截断风险。只有保守数字静音判断才跳过识别，静音本身不从时间轴删除。
3. **ASR 后独立对齐。** Qwen 的识别和时间预测是不同模型，通过官方包装 API 组合；对齐结果不能被当作 ASR 置信度。
4. **先纠错，再提炼。** 同音术语错误进入总结后容易被放大；纠错需要前后文和术语提示，但禁止重写观点、删除否定或补充内容。
5. **分段提炼，再分层合并。** 长达四小时的论坛不能依赖一次超长请求；每层限制输入和输出，详细局部纪要保留，避免综合摘要压缩后所有细节消失。
6. **结构化生成，再固定渲染。** LLM 返回 JSON，经 schema、ID、字符预算和输出终止状态检查后，由程序生成 Markdown，避免文档格式漂移。
7. **保留疑点和证据。** 数字、人名、争议和缺少责任人的事项不做强行补全；改动过大时拒绝采用，并保留建议文字供复核。

这些是可审计的工程约束，不是事实准确性的数学保证。词义替换、否定丢失、错字后的错误理解仍需抽样回听。记录中出现“没有发现待办”，也不能证明原始会议中绝对不存在待办。

## ASR 与推理实现选择

Qwen3-ASR 官方同时提供 Transformers 与 vLLM 推理方式，并提供独立的 ForcedAligner。这里选择官方 Python 包的 Transformers 后端：单卡常驻一份模型，小批次推理，减少服务端部署、网络传音频及版本组合的复杂性。[官方仓库](https://github.com/QwenLM/Qwen3-ASR)、[技术报告](https://arxiv.org/abs/2601.21337)。

四张卡优先用于同时处理四个视频。没有为一个模型做四卡张量并行：当前模型规模不需要以此作为部署前提。精确吞吐量和显存要由服务器短样本试跑确认，不引用模型官方的高并发吞吐值作为本项目实测。
